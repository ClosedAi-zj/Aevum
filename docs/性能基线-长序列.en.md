# Long-sequence end-to-end baseline (2026-11-04)

[中文](性能基线-长序列.md) · **English**

## Why this page exists

"How long does 1000 frames take", "is the bottleneck decode or encode", "does the export use
the cores" -- all three had only scattered single-frame / first-screen / 8-frame figures and
**had never been measured end to end**. Without a baseline no optimisation can be judged:
"go streaming", "swap the encoder", "add threads" are all guesswork. This page gives the
numbers and the tool that produced them.

## How to run

```
cargo run --release -p aevum-core --example export_bench -- --frames 1000
```

- Default source: the first JPG under `samples/cameras/` (`PANA0198.JPG`, 6000x4000 here).
- `--source` picks another sample (RAW works too); `--width/--height` set the output frame;
  `--fps/--crf` set the encoder.
- **Cold by default** (the metering ledger `<seq>/.aevum` is deleted first); `--warm` reuses it.
- Work directory defaults to `E:/tmp/aevum-export-bench`; **nothing is deleted without
  `--clean`** (deletion lands in the Recycle Bin on this machine and piles up faster than the
  files do).

Stage boundaries come from the export's `progress` callback, not from wall clock guessed
outside:

| Stage | What it is |
|---|---|
| decode + meter | `measures::measure_sequence`, **the same implementation the UI and headless use** (parallel, long side 512, reads and writes the ledger) |
| render + encode | `Stage::Frames`, until the last frame is written |
| pipe flush | encoder saw its first frame -> final file on disk |

## Measurements

Machine: i5-12600KF (8 physical / 16 logical cores), 31.8 GB RAM, Windows 11, release build.
One run each (minutes long; the differences are far larger than the jitter).

### 1000 frames of 24 MP JPEG -> 6000x4000 H.264 / CRF 20 / 30 fps

| Run | decode + meter | render + encode | pipe flush | total |
|---|---|---|---|---|
| cold (first open) | 36.08 s · 36.1 ms/frame | 176.84 s · 176.8 ms/frame | 5.90 s | **218.84 s · 218.8 ms/frame** |
| warm (ledger hit) | 0.10 s · 0.1 ms/frame | 176.27 s · 176.3 ms/frame | 5.61 s | **181.99 s · 182.0 ms/frame** |

### 100 frames of Canon CR3 RAW (6982x4654) -> same frame

| decode + meter | render + encode | pipe flush | total |
|---|---|---|---|
| 14.27 s · 142.7 ms/frame | 27.91 s · 279.1 ms/frame | 7.93 s | **50.12 s · 501.2 ms/frame** |

Extrapolated to 1000 RAW frames this is roughly **8.4 minutes** (143 s decode / 279 s render).

## Conclusions

1. **The bottleneck is rendering, not decoding.** In the 24 MP JPEG sequence render + encode is
   **81 %** while decode + meter is 16 %. RAW decoding costs four times as much (142.7 vs
   36.1 ms/frame) but still only 28 % of the whole sequence. => To go faster, work on the render
   path (grading / scaling / writing the pipe), not on decoding.
2. **The metering ledger is worth 37 s per 1000 frames (16.8 %).** Warm, the decode stage drops
   from 36.08 s to 0.10 s. => Re-exporting does not re-decode; any proposal that changes the
   `measures` cache convention must account for those 37 s.
3. **Encoding is not a bottleneck.** It overlaps rendering through the direct pipe, with a
   5.90 s flush. => Swapping encoders or changing CRF barely moves the total; conversely, a
   slower render back-pressures the pipe (the encoder waits on stdin), so "encoding is fast"
   does not mean rendering may be slowed down freely.
4. **The export uses 5.7 physical cores on average (71 %).** One 1000-frame export burns
   1243.5 s of CPU time over 218.4 s of wall clock on 16 logical (8 physical) cores. The missing
   headroom is **deliberate**: `export::worker_count` caps frames above 12 MP at 4 workers
   (about 0.6 GB working set each), and the frame loop's `out_tower` f32 accumulation order
   cannot be parallelised -- doing so changes results bit for bit.

## Why not push further

- **Memory**: 8 workers x 24 MP is about 4.8 GB of working set, while the UI still needs half of
  RAM for previews and the encoder. The gauge `examples/pyramid_bench.rs` measures the pyramid
  side separately: 8 frames cost a **1558 MiB fusion delta**, with a 1102 MiB floor and +92 MiB
  per extra frame (see the O2 entry in the ledger) -- the same order of magnitude as a second
  gigabyte-scale cost once four workers run side by side.
- **Correctness**: the serial part of the frame loop is the premise of the bit-exact check; any
  change to the floating-point addition order turns the `T10_DUMP` md5 red. That is not a
  performance trade-off, it is "exports must be reproducible".

## Reproduction

- Same machine, same samples (samples are not committed; see
  [`samples/cameras/README.md`](../samples/cameras/README.en.md)).
- A cold run must really drop the ledger: not passing `--warm` is cold.
- CPU utilisation has to be sampled outside (the tool will not pull in windows-sys for one
  counter):

```
powershell -c "1..600 | % { $p = Get-Process export_bench -EA 0; if ($p) { $p.CPU } else { break }; Start-Sleep -Milliseconds 500 }"
```

The difference between the first and last CPU seconds divided by wall clock divided by physical
cores is the average utilisation.

## No assertions, but a method

Performance numbers change with the machine; turning them into assertions would only go red on
someone else's box. What is pinned here is the **method**: `crates/aevum-core/examples/export_bench.rs`
is the only entry point, stage boundaries come from the progress callback rather than from
outside guesses, and after touching the render or decode path you rerun the three tables above,
replace the numbers and update the date.
