## 1. Fixes (residual correctness risks)

| # | Item | State and why it matters | Where | Done means | Cost |
|---|---|---|---|---|---|
| R1 | Thumbnail cache counts a "replaced" file as a hit | Files whose long edge sits between `max_side` and 4×`max_side` still count as a hit; downstream only uploads them as textures so no layout depends on it, but semantically it is unclean (ledger C8, residual risk 1) | Cache-hit check in `crates/aevum-core/src/metrics.rs` | The cache key or the check carries size/mtime evidence; a constructed same-key file with an in-between size must miss | S |
| R2 | Very long filenames never hit the cache | Paths around 235+ characters are recomputed every time -- a performance issue only (ledger C8, residual risk 3) | Same as above | Truncate plus hash still hits; a 240-character name hits on the second run | S |
| R3 | `focus_merge` cannot receive a cancel | The MCP side is synchronous, so the `cancelled` closure is always `false` (the ledger decided on 2026-11-03 **not** to wire it). Not a bug, but from the user's side "I pressed cancel and nothing happened" | `crates/aevum-mcp/src/tools.rs` plus `session.start_background` (turn it into a background job) | A cancel returns `cancelled: true` and **no dirty result**; the main loop can still read the next line while it runs | M |
| R4 | RAW format coverage gaps | Sony `arw6`, Nikon HighEfficiencyStar, HEIC, iPhone LinearRaw (unsupported by rawler 0.8.0 / panic already self-contained) all fall back to the embedded preview, and the UI labels it honestly. Whether to fill them depends on real-user demand | Start from the list in `docs/RAW兼容性-根因与防线.md`; filling them means upgrading rawler or patching a fork (LGPL-2.1; sources already ship in the bundle) | Per format: sample into `samples/cameras/`, the matrix test goes red once, then the code changes | L (plus upstream risk) |

Recommendation for R4: **do not start it proactively**; wait until three real samples of the
same body pile up. Before starting, establish whether the upstream has no decoder at all or we
simply never wired one.

## 2. Optimisations (performance and resources)

| # | Item | State | Where | Done means | Cost |
|---|---|---|---|---|---|
| O1 | Long sequences have no end-to-end wall clock | Every measurement so far covers a single frame, first screen, or an 8-frame fusion; the "open → deflicker → export" run over a 1000-frame sequence has no numbers, so we cannot tell whether the bottleneck is decode or encode | A probe in `tools/` (same conventions as `--bench-*`), or an extension of `acceptance/ux_budget.sh` | Median wall clock for 1000 RAW frames plus the split (decode / metering / encode), recorded in the ledger | S |
| O2 | Pyramid peak memory 3.86 GB (8×24 MP) | 2.32 GB of that is the eight input frames; the fusion delta is 1.54 GB. Lowering it further means touching the per-frame streaming structure | `pyramid.rs` (already streams per level) | Delta ≤1.0 GB with `T10_DUMP` output md5 unchanged | M |
| O3 | Parallelism of decode/export never re-measured | `align` and `ai_denoise` use rayon; video encoding goes through external ffmpeg (parallel by nature), but how well the per-frame render loop uses the cores was never measured | The render loop in `export.rs` | Above 70% CPU utilisation on an 8-core box, or evidence that it is already waiting on ffmpeg | S |

O3 may well measure "no problem at all" -- then write the number into the ledger and close it
rather than leaving it open.

## 6. Three decisions needed

1. **Whether v1.6.0 carries R3**: moving to a background job changes the MCP scheduling model (sync → async). The gain is a working cancel; the cost is more concurrency and state-machine complexity.
2. **The R4 stance**: wait for upstream (rawler) or fork? A fork can add `arw6`/HE*, at the price of LGPL source distribution and ongoing merge cost.
3. **Rename and migration**: once the name is fixed, run `tools/rename_brand.py` (see [Rename & Version Reset](改名与版本重置.en.md)); whether v1.6.0 ships from the new repo or the old one has to be decided first.
