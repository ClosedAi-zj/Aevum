# Aevum Studio 0.5.0-beta.1 release notes

[中文](发布说明-v0.5.0-beta.1.md) · **English**

Released: 2026-10-31
Previous version: `0.4.0-beta.1` (released as "光时 / Lumen Studio")

---

## In one sentence

**The product is renamed to "恒晷 / Aevum Studio".** That is the only breaking change in this
version; everything else is the accompanying compatibility layer, documentation and packaging
work. **Not a line of algorithm changed**: every numeric golden (`oracle/golden/`, 10 files) is
byte-identical by sha256, and the eight layout shape counts from `--selftest` match 0.4 exactly.

---

## Upgrade notes (three sentences)

1. **An old project's `.lumen/` is moved to `.aevum/` automatically the first time you open that
   sequence.** If the move fails (read-only volume, antivirus holding a file), the app **keeps
   working in the old directory** — no data is lost and nothing turns read-only. For a whole-disk
   migration see `scripts/migrate-to-aevum.sh`.
2. **The `LUMEN_*` environment variables still work**, but each process prints one deprecation
   line to stderr the first time it touches one. Prefer `AEVUM_*`; when both are set, `AEVUM_`
   wins.
3. **MCP clients should re-fetch `tools/list` after upgrading.** The server still accepts the old
   `lumen_*` tool names (silent aliases, byte-identical results), but **only `aevum_*` appears in
   the list**. Some clients validate "this name must appear in the list" before calling; for those
   the old name is rejected **by the client**, and re-fetching fixes it.

## 2. Compatibility policy (**old data is not lost, old calls do not break**)

This version implements three levels of backwards compatibility: `.lapse → .lumen → .aevum`.
Every migration **moves, never deletes**.

### 1. Old projects open directly

- Opening a sequence moves `<sequence>/.lumen/` to `<sequence>/.aevum/`; the older
  `<sequence>/.lapse/` migrates the same way.
- Parameters, ratings, flags, keywords, stacks, keyframes, alignment results, deflicker curves,
  crop boxes, camera motion and watermark settings are **restored verbatim** (the project file
  format is unchanged).
- When both old directories exist: **only `.lumen` is used** (the newer one) and `.lapse` is left
  untouched — there is no way to tell which one the user is actually working with, and guessing
  wrong means overwriting data.
- **A failed move does not degrade to read-only** (read-only volume, antivirus holding plugin
  files): the app keeps reading and writing the old directory and prints one warning line to
  stderr. A silently failing "Save" is far worse than a failed migration.
- **If `.aevum` happens to be a regular file rather than a directory** (user slip, another tool):
  do not migrate; keep using the old directory and say so. This sounds redundant, but on Windows
  `rename` onto an existing file **wipes it** — the F8 regression test was written for exactly
  this scenario, after the first implementation actually hit it.

Migrating a whole footage disk in one go:

```bash
scripts/migrate-to-aevum.sh 'F:/2025'           # dry run: shows what would move
scripts/migrate-to-aevum.sh 'F:/2025' --apply   # really move
```

### 2. Old environment variables still take effect

**12 runtime variables fall back to the old names**, with **the new name winning** (plus one
packaging variable, explained below):

```
AEVUM_LENSFUN      AEVUM_FFMPEG      AEVUM_LIBRARY     AEVUM_SETTINGS
AEVUM_PLUGINS      AEVUM_DCP         AEVUM_LCP         AEVUM_RENDER_QUEUE
AEVUM_FRAMES       AEVUM_DEV_CASES   AEVUM_REAL_RAW    AEVUM_ICC_DUMP
```

For example, `LUMEN_FFMPEG=D:/tools/ffmpeg.exe` still uses that ffmpeg; if `AEVUM_FFMPEG` is also
set, `AEVUM_` wins. **Each process prints one deprecation line to stderr the first time it uses an
old name**, and the line names the replacement.

**The thirteenth variable is the exception: `AEVUM_FFMPEG_SRC`.** It exists only for
`scripts/package.sh` at packaging time and has no old-name fallback — from this version the
packaging script **no longer reads** `LUMEN_FFMPEG_SRC`, so setting it changes nothing. The
"old names still work" sentence above does not cover it.

Portable-drive behaviour is unchanged: setting any override (`AEVUM_SETTINGS` / `AEVUM_PLUGINS` /
`AEVUM_LIBRARY` / `AEVUM_RENDER_QUEUE`) selects portable mode, which **never touches `%APPDATA%`**.

### 3. The old config directory is adopted on first launch

- `%APPDATA%/lumen-studio` (or the older `lapse-studio`) moves to `%APPDATA%/aevum-studio` on the
  first launch.
- When the new directory does not exist yet it is a **whole-directory rename**: the old path is
  gone, but not one file was deleted — the contents simply moved.
- When the new directory already exists it is **per-item fill-in**: whatever the target lacks is
  copied, **the new directory wins for same-named files** (letting the old one win would push the
  user's settings in the new version back), and the old directory **stays as it was**, ready to be
  inspected at any time.
- No file is ever deleted; the worst case is that nothing moves.
- Migration happens once, tracked by the `aevum-studio/adopt-sentinel` marker. That detail cannot
  be skipped: otherwise a plugin you deleted in the new directory would be carried back from the
  old one on the next launch.

> The previous generation, `scripts/migrate-to-lumen.sh`, moved only `render_queue.json`, which is
> how users upgrading from the Python era lost `settings.json` / `galleries.json` / `plugins/`.
> This version migrates **at directory level** and adds the `lapse-studio` fallback that the Rust
> side had been missing.

### 4. Old MCP tool names remain callable (silent aliases)

`lumen_open_sequence`, `lumen_grade_set` … all 34 old tool names still work and return results
**byte-identical** to their `aevum_*` counterparts (pinned by tests). The write-operation journal
still records them — `is_write_op` normalises the old name first, so nothing is silently dropped
from `op_journal.jsonl`.

**But `tools/list` only lists the new names.** Old names are "accepted but not advertised".

> ## ⚠️ Re-fetch `tools/list` in your client after upgrading
>
> Some clients validate "this name must appear in the list" before calling. Holding a cached old
> `tools/list`, those clients reject a `lumen_*` call **themselves** (the server would have
> accepted it). Re-fetching restores everything.
>
> Note also that `serverInfo.name` changed from `lumen-studio` to `aevum-studio`, so clients that
> remember permissions by server name will ask for authorisation once more — that is expected
> behaviour, not a defect.

### 5. Launcher compatibility

`恒晷.bat` looks in this order: `dist\aevum\aevum.exe` → `dist\lumen\lumen.exe` →
`target\release\aevum.exe` → `target\debug\aevum.exe`.

Anyone who already unzipped the 0.4 green package changes nothing and can still double-click the
new script (it will use the old `dist/lumen/lumen.exe`). No copy of `光时.bat` is kept: a filename
is the brand, and leaving two would only make people wonder which to click.

### 6. Plugins are unaffected

A plugin manifest's `id` prefix **is not parsed** (validation only requires "contains a dot, plus
lowercase letters/digits/dots/hyphens"), so installed third-party plugins load as before. The only
change is the repository's **sample plugin**, renamed to `aevum.example-invert`. If you have both
`lumen.example-invert` and `aevum.example-invert` installed, two entries appear in the menu
(different ids) — delete the old one. We do not rewrite a user's `plugin.toml` automatically.

## 3. Changes in this version

- Rename: 16 replacement rules across the repository, covering crate directory names, package
  names, binary name, window title, about box, three colour-space description strings, XMP
  `x:xmptk`, the default watermark signature `© Aevum Studio`, 34 MCP tool names, the 43-entry GUI
  command ID table, `恒晷.bat`, `scripts/*.sh`, `apps/make_icon.py`, the plugin sample and the
  README.
- New compatibility layer: `aevum-core::brand` (the single source of truth for brand constants),
  `::env` (environment-variable aliases with a test seam), `::config_dir` (first-launch config
  migration with a sentinel).
- Three-level guard directory chain: `project::guard_dir` (read-only probe) /
  `project::adopt_guard_dir` (one-shot move).
- Four MCP alias landing points: headless `server::call_tool`, `lib::dispatch`,
  `tools::dispatch`, and attach-mode `attach::resolve_command`.
- Version: `0.4.0-beta.1` → `0.5.0-beta.1` (`Cargo.lock` changes only four package names and
  version lines — **zero third-party version changes**, zero new dependencies).
- Test infrastructure: `.cargo/config.toml` pins the four config overrides to
  `target/test-home/`, so `cargo test` cannot trigger a real `%APPDATA%` migration on a developer
  machine.

**Algorithms, golden data and UI layout are untouched.** The frozen file
`crates/aevum-ui/src/layout.rs` has no diff.

## 5. Known issues

1. **The default ffmpeg path in `scripts/package.sh` is dead**: `$ROOT/../pythonProject4/.venv/...`
   does not exist on most machines (**it was like that before the rename, this version did not
   introduce it**). This version only improves the failure message — when it cannot find ffmpeg it
   prints the probe order and the next command, then `exit 1`, instead of a bare "not found".
   **The fix is undecided**; three candidates: look for a venv path, look on `PATH`, or prefer an
   exe next to the binary. That is a separate dependency-resolution decision and does not belong
   in the rename round. For now pass `AEVUM_FFMPEG_SRC=<absolute path to ffmpeg.exe>` explicitly.
2. **clippy / rustfmt are red on this machine's toolchain anyway** (rustc 1.98, four lints and 197
   fmt hunks, one of them inside the frozen `layout.rs`). This version deliberately **guarantees
   zero difference** rather than "forcing everything green". A separate round should pin the
   toolchain with `rust-toolchain.toml` and then fix them together.
3. Users coming from 0.3 or earlier (the Python era) who already lost `settings.json` /
   `galleries.json` to the old migration script **cannot get them back** — only a backup can.
   What this version does is "never lose them again".
4. **`tools/split_step1.json` / `split_step2.json` point at directories that no longer exist**
   (`F6`): they are the input records of a historical refactor script, and editing them would be
   falsifying the record, so they stay as they are.
5. **In attach mode 9 of 34 tools fail to resolve, and `xmp_read`/`xmp_write` versus
   `xmp_import`/`xmp_export` are named inconsistently across modes** (`F10`): **pre-existing, not
   introduced here**. A later round adds an exhaustive two-way tool-name coverage test and unifies
   the naming; this round does not touch the tool set in the middle of a rename.
6. **The read-only fallback state exists only on stderr, invisible in the GUI** (`R3`): when a
   project lives on a read-only volume and the guard directory cannot move, the UI says nothing and
   the user still believes parameters are being saved. Fixing it needs a UI warning, which is a
   product change — separate ticket.
7. **A broken portable path silently falls back to defaults** (`R4`): when `AEVUM_SETTINGS` points
   at an unwritable location, the app reports nothing and uses the default configuration. It needs
   a piece of diagnostic output — separate ticket.
8. **Cross-process race when two instances launch for the first time simultaneously** (`R6`): two
   processes can both decide "`aevum-studio` does not exist" and migrate independently, in theory
   overwriting each other. Extremely unlikely; no cross-process lock this round.
9. **If a regular file named `.aevum` sits in the project directory, saving fails with only
   `os error 183`** (`F8` sub-case b): rare (usually a user slip or another tool's file). Opening
   and reading parameters works, **saving reports "cannot create a file when that file already
   exists"** and the message gives no clue what to do. This version **does guarantee that the file
   is not deleted** — `adopt_guard_dir` notices the target is occupied by a same-named file, skips
   the migration, keeps using the old directory and prints a line. This was a real bug found by QA
   Round 1: the first implementation renamed onto that file, and Windows'
   `MoveFileEx(REPLACE_EXISTING)` wiped its contents, while stderr still printed "migrated". But in
   the case of "no old directory, only that file" saving still fails. Workaround: rename or delete
   the file and retry. **This is a gap that already existed in 0.4, not introduced here.** A later
   round adds a `ensure_guard_dir_usable()` style pre-check with readable error text and tells the
   user explicitly "your data is in `.lumen/`, nothing was lost" — deliberately out of scope here,
   because it would grow the diff from "rename" into "rename plus fault tolerance", and the review
   cost is not worth it.

## 6. Rollback

- Green package: swap back the 0.4 `lumen.exe` / `dist/lumen/`; both the old and the new
  directories are still there.
- Project: `project.json` is **identical** in `.aevum/` and `.lumen/`, so renaming `.aevum/` back to
  `.lumen/` makes it openable by 0.4.
- Configuration: rename `%APPDATA%/aevum-studio` back to `%APPDATA%/lumen-studio`; if the old
  directory still exists, simply delete the new one.

### ⚠️ Do not open the same sequence back and forth between versions

Once 0.5 has moved `.lumen/` to `.aevum/`, if the user opens **the same sequence** again with the
0.4 shortcut:

1. 0.4 finds no `.lumen/` → **creates an empty one** → the UI shows default parameters. The user
   sees "all my parameters are gone", though they are all still in `.aevum/`.
2. Believing they must redo the work, they make changes in 0.4, which are written into that **empty
   directory**.
3. Switching back to 0.5 → 0.5 prefers `.aevum/` (it exists) → the 0.4 changes are **silently
   ignored**, the two sides never agree again, and nothing warns about it.

**A rollback must be done in one step**: change the directories/configuration back as described
above, confirm 0.4 behaves, and only then keep using 0.4. Never cross-open in between. This is the
classic "the data is not lost but the user believes it is" failure, and it is harder to diagnose
than genuine loss.

`lapse/` and `oracle/` have **zero** `lumen` hits: the old name `lapse` survives only as a

Verification script one (the same one as design §6.2.7; it must print `白名单外：0 个`, i.e. zero
hits outside the allowlist):

```bash
allowed() { case "$1" in
  lapse/*|docs/*|oracle/*|tools/split_step1.json|tools/split_step2.json|tools/fix_visibility.py) return 0;;
  crates/aevum-core/src/brand.rs|crates/aevum-core/src/env.rs|crates/aevum-core/src/config_dir.rs) return 0;;
  crates/aevum-core/src/project.rs|crates/aevum-core/src/journal.rs|crates/aevum-core/src/sequence.rs) return 0;;
  crates/aevum-core/src/exif.rs|crates/aevum-core/src/queue.rs|crates/aevum-core/src/library.rs) return 0;;
  crates/aevum-core/src/lcp.rs|crates/aevum-core/src/dcp.rs|crates/aevum-core/src/export.rs) return 0;;
  crates/aevum-core/tests/project_roundtrip.rs|crates/aevum-core/tests/export_stills.rs) return 0;;
  crates/aevum-mcp/src/attach.rs|crates/aevum-mcp/src/server.rs|crates/aevum-mcp/src/lib.rs) return 0;;
  crates/aevum-mcp/tests/tools.rs|crates/aevum-mcp/tests/mcp_stdio.rs) return 0;;
  crates/aevum-ui/src/settings.rs|README.md|CHANGELOG.md|scripts/migrate-to-aevum.sh|scripts/package.sh) return 0;;
  恒晷.bat|.cargo/config.toml) return 0;;
  *) return 1;;
esac; }
bad=0
while IFS= read -r f; do
  grep -qi lumen "$f" 2>/dev/null && { allowed "$f" || { echo "白名单外命中：$f"; bad=$((bad+1)); }; }
done < <(git -c core.quotePath=false ls-files -co --exclude-standard)
echo "白名单外：$bad 个"
```

Verification script two (reproduces the `227 occurrences / 29 files` above):

```bash
total=0; files=0
```
