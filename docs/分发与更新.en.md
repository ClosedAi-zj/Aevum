# Distribution and updates

**English** · [中文](分发与更新.md)

How the program reaches users, how they move to the next version, and which checks stand in
between. One page: the current state, the three roads, the trust chain, what signing costs,
and finally what is explicitly not done yet.

## 1. Current state: one road

After `scripts/package.sh` finishes, `dist/` holds exactly two things:

```
dist/aevum/                                       the portable tree
dist/Aevum-Studio-vX.Y.Z-windows-x64.zip          what users download
dist/SHA256SUMS                                   <64 hex>  <zip file name>
```

`SHA256SUMS` has a single line — the zip — in the format `sha256sum -c` accepts, so users can
verify it themselves:

```bash
sha256sum -c SHA256SUMS
```

The strength of this road is that it needs no server at all: no installer, no registry, no
administrator rights. The weakness is just as clear — users have to notice a new version
exists, and upgrading means manually unzipping over the old copy.

**From v1.9.6 on, this package no longer comes from one machine.** Pushing a `vX.Y.Z` tag
triggers `.github/workflows/release.yml`, which runs **the same** `scripts/package.sh` on a
clean `windows-latest` runner (six gates + release build + selftest + real export + zip +
unzip-and-verify), publishes the zip and `SHA256SUMS` as a GitHub Release, and reads the API
back to confirm `draft=false`, `state=uploaded` assets and a `digest` matching the local
sha256. `workflow_dispatch` runs the same chain before any tag is pushed, uploading an
artifact but publishing nothing. `acceptance/check_release.py` (gate 0, R1-R9) guards against
CI quietly turning into a different chain. The bundled ffmpeg is not in git: CI downloads the
pinned 7.1 essentials build and verifies the sha256 of **the exe that actually ships** —
upstream publishes no checksum for the zip and GitHub's asset digest is empty, so the check
targets the distributed bytes themselves.

**Note for the next release**: the v1.9.6 tag run used the old `--verify` (a missing digest was
printed as "skipped" and still returned 0). The current version requires a digest that exists
and equals the local sha256, plus a `tag_name` assertion, and has not yet run inside a real tag
release. A simulated `v1.9.7` API JSON (with `tag_name` and both asset digests) passes, so the
new assertions do not block a normal release; but `release.yml` reads back with `gh api`
immediately after `gh release create`, and whether GitHub has computed asset digests at that
exact instant cannot be reproduced locally. Watch the first `--verify` read-back on the next
real tag. If an immediate response occasionally omits the digest, the right fix is a backoff
retry of `gh api` in the workflow -- **do not loosen `verify()`**: skipping an unverified byte
reconciliation is exactly the weak failure this round removed.

## 2. Three roads, each covering one gap

| | Portable zip | Installer (`scripts/install/aevum.iss`) | Built-in updater (`crates/aevum-core/src/update.rs`) |
|---|---|---|---|
| Solves | single machines, nothing installed, USB sticks | findable in the Start menu, `/SILENT` bulk deployment, uninstall knows what to remove | users no longer watch the releases page |
| For | workstations, temporary machines, reviews | labs, training rooms, company-wide rollout | long-term individual users |
| Needs admin | no | yes by default (`/CURRENTUSER` opts out) | no (when installed under the user profile) |
| State | **in use** | script ready, **never produced a build on a real machine** | **wired up** (v1.9.2: menu entry, silent startup check, update/rollback window; v1.9.3 eight-scenario real-machine test, see §6.2) |

All three roads produce **the same program**: the same `aevum.exe` and the same
`tools/ffmpeg.exe`. The installer adds no installer-only features, and the updater does not
assume it runs on an installed copy (it only cares where the new exe comes from and where the
target exe lives).

The shape of the updater deserves one sentence: it **adds no HTTP client**. Downloads go
through the OS-provided `curl.exe` (Windows 10 1803+), falling back to
`powershell -NoProfile -Command Invoke-WebRequest`; when neither exists it reports
"no usable download channel on this machine" together with a manual download URL rather than
failing silently. Offline builds and the dependency audit therefore do not carry a TLS stack
just to check for updates.

## 3. The trust chain

An update request passes five gates; failing any one stops it:

1. **HTTPS**: `curl -fsSL` and `Invoke-WebRequest` both use the system certificate store, and
   `-f` turns a 404 into a non-zero exit code — otherwise a 404 HTML page would be written
   into the exe as a "successful download".
2. **The tag must be a three-part version**: `v1.8` and `v1.8.0-beta` are rejected. Comparison
   is **numeric** (`1.10.0 > 1.9.0`), not string-based — byte-wise `"1.10.0" < "1.9.0"`, and
   users would never receive anything after 1.10.
3. **Assets are picked by suffix**: `windows-x64.zip`. No match means "no asset for this
   platform", not a guess.
4. **SHA256SUMS comparison**: a manifest that **lacks the line is a failure**. Treating
   "not found" as "no checksum needed" is the most common hole in this kind of code.
5. **Signing (decided against)**: see the next section. This gate does not exist in the current
   release chain; the first four are all there is.

Be honest about the limits of gate 4: the manifest and the zip come from **the same origin**,
so it proves "the transfer was intact and the mirror did not tamper with it"; it **cannot**
prove "the publisher is who they claim". Only code signing gives that — the one chain where
you trust a certificate instead of a download URL. This project is MIT-licensed, free, made
for photography enthusiasts, for learning and personal use, with a zero budget: that gap is
an **explicit trade-off, not a to-do**.

## 4. Signing: what it costs, three options

`scripts/sign.ps1` is the hook, and it **never blocks packaging by default**: with no
certificate it prints one line and exits 0, and the build carries on; only "configured but
failed to sign" returns non-zero. Signing is always SHA256 plus an RFC3161 timestamp —
without a timestamp, the moment the certificate expires **every build already shipped**
reports an expired signature while not a byte has changed.

| Option | Cost | SmartScreen | Fits |
|---|---|---|---|
| **No signing** | 0 | the first few hundred downloads warn "unknown publisher"; reputation builds up over time | where we are today |
| **Self-signed** (own root) | 0 (you generate it) | **almost no improvement** for public users; only machines with your root installed accept it | internal rollouts |
| **Azure Trusted Signing** | ~$9.99/month | needs a verifiable organisational identity; warnings disappear once approved | the serious choice for public releases |

Conclusion (decided 2026-11-05): **no certificate, no signing**. This project is MIT-licensed,
free, made for photography enthusiasts, for learning and personal use, with a zero budget; the
three options above document the costs, they are not a to-do list. The free open-source route
(SignPath Foundation) requires builds to come from the repository's automation and manual
approval for every release — `release.yml` now satisfies the first half, but per-release manual
approval is still not worth it for a learning tool, so it is parked. Both free precautions are
already in place: `SHA256SUMS` ships with the Release (CI publishing reconciles it) and the
release page is pinned to the repository's Releases page.

## 5. How to run it

```bash
# Portable build (zip + SHA256SUMS, with an unzip-and-selftest pass at the end)
scripts/package.sh

# CI release: pushing the tag builds and publishes; scripts/release_body.py generates the
# notes from CHANGELOG.md
git tag vX.Y.Z && git push origin vX.Y.Z
# Before tagging, run workflow_dispatch in Actions to verify the chain (artifact only,
# no Release)

# Installer (needs iscc from Inno Setup 6; the version is passed explicitly)
iscc /DMyAppVersion=X.Y.Z scripts/install/aevum.iss
# -> dist/installer/Aevum-Studio-X.Y.Z-setup.exe

# Signing (optional; a single line when no certificate is configured)
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sign.ps1 -Path dist/aevum
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sign.ps1 -Path dist/installer
```

Silent install: `Aevum-Studio-X.Y.Z-setup.exe /SILENT /NORESTART`; `/VERYSILENT` removes the
progress window too. A silent uninstall **always keeps** `%APPDATA%\aevum-studio` (nobody can
answer that dialog, and a wrongly deleted configuration is unrecoverable); an interactive
uninstall asks once.

## 6. What is still missing

### 6.1 Wired up (v1.9.2)

The pure logic in `update.rs` used to have no caller at all; there is now a full path in
the UI:

- **Help → Check for updates...** opens the update window and checks immediately; when an
  installable version is found, the menu item itself becomes "new version vX.Y.Z ...".
- **Silent startup check**: once per process, and only if the previous check is more than
  24 hours old. A failure pops nothing and interrupts nothing; it leaves one line of reason
  in the update window.
- **Update window**: current version, remote version, release notes, real byte progress, and
  "restart and install now". Download, verification, unpacking and writing the replacement
  script all run off the UI thread; the app never blocks for a second. The restart is only
  offered once everything is *prepared*, so a mid-way failure (offline, bad checksum, an
  antivirus lock) is visible while the user is still in the app.
- **Rollback**: the install script no longer deletes `*.old`. When it sits next to the
  program, Help shows "Roll back to the previous version...", which (after confirmation)
  moves the current build to `*.failed` as evidence and puts `*.old` back.

### 6.2 Real-machine run: done once (2026-11-05)

`crates/aevum-core/examples/update_e2e.rs` is the harness for this chain. Against a **local
fake release** (`python -m http.server` plus a zip built with `tar.exe`, a real `SHA256SUMS`
and a GitHub-shaped `latest` JSON) it walks 检查 → 下载 → 校验 → 解包 → 替换 → 回滚, with the
install directory deliberately placed under a path containing both spaces and Chinese
characters (`E:\tmp\upd-e2e\install\恒晷 程序\`).

```bash
# Four modes: install (default) / prepare / rollback / locked
E2E_API=http://127.0.0.1:8788/latest \
E2E_TARGET='E:\tmp\upd-e2e\install\恒晷 程序\aevum.exe' \
E2E_WORK='E:\tmp\upd-e2e\work' \
cargo run -p aevum-core --example update_e2e
```

Every row below was checked at byte level:

| Scenario | Result |
|---|---|
| Silent startup check (real exe, local server) | `settings.json` records `last_update_check`; the server logs `GET /latest 200` |
| Download progress | Real byte callbacks (0 → 23,740,830); on-disk size equals the declared size |
| Verification | Manifest fetched over HTTP, `verify` passes; a manifest/package mismatch stops the chain |
| Unpack choice | The zip holds both `aevum.exe` and `tools/ffmpeg.exe`; the **matching name** is picked |
| Replacement | Target becomes the new build (sha256 identical), `.old` keeps the old one, the script deletes itself |
| Waiting | With the app still running nothing happens: four seconds later the target is unchanged and there is no `.old`; once the app exits the swap finishes within a second |
| Rollback | Target returns to the old build, `.failed` keeps the new one, the script deletes itself |
| Locked file | `share_mode(0)` on the new exe → fifteen retries → `.old` is moved back (the user still has a working build) |

**This run found two real bugs**, neither of which a judgement could see (all of them were
green at the time):

1. **A Chinese path inside the batch body turns into mojibake.** `cmd` decodes a `.cmd` with
   the OEM code page (936 on Chinese Windows) while Rust writes UTF-8: one Chinese character
   in the install path (`D:\软件\...`, `C:\Users\张三\...`) makes `if exist` and `move` miss
   everything, and `>NUL` swallows the errors -- the user sees "clicked update, nothing
   happened", followed by a silent rollback after fifteen retries. Isolated experiment: the
   same script stored as UTF-8 prints `MISSING`, the same content converted with `iconv` to
   GBK prints `FOUND`.
   Fix: **no path is written into the body**; all of them arrive as command-line arguments
   (`%~1`/`%~2`/`%~3`, and the command line is UTF-16 and immune to the code page), leaving
   the body pure ASCII.
2. **`tasklist | find` depended on PATH.** With a Unix `find` on PATH (any developer with
   Git/MSYS, or launching the app from Git Bash), `find /I` fails with
   `No such file or directory`, the wait loop stops waiting instantly, and the replacement
   starts while the app is still running. Fix: system tools are always spelled
   `%SystemRoot%\System32\...` (`tasklist`, `find` and `ping` all switched).

**Still uncovered**: UAC elevation under `C:\Program Files` (the test directory is not in a
protected location), a real antivirus (`share_mode(0)` simulated "file in use"), and
Authenticode signing (decided against). A real GitHub release is covered by `release.yml`
from v1.9.6 on, see §1; that item was closed on 2026-11-05 by the final section of
`docs/遗留台账.en.md`. Signing costs are in §4.

### 6.3 Not done (each needs something external, not more code)

- **Real signing: decided against, not pending.** The project is MIT-licensed, free, for
  photography enthusiasts, for learning and personal use, with a zero budget. No certificate
  is purchased and no Authenticode signing is done. A SmartScreen "unknown publisher" warning
  on first download is a known, accepted consequence. `sign.ps1` stays as a hook for anyone
  who later volunteers to bear the cost; by default it still prints one line and exits 0.
- **A real GitHub release through CI**: covered by `release.yml` from v1.9.6 on
  (tag -> build -> publish -> read-back reconciliation). The local fake-release run in §6.2
  remains the irreplaceable real-machine behaviour check; neither replaces the other.
- **Update scope**: the updater swaps `aevum.exe` only -- not `tools/ffmpeg.exe`,
  `licenses/` or `third-party-src/`. An ffmpeg upgrade needs the full package or the
  installer. That is deliberate: replacing a whole directory tree while files are in use has
  far more failure modes than swapping one exe, and the gain does not justify the risk in
  this release.
- **`.aevum` file association**: not done, because a project is not "one file with an
  extension" but `<sequence root>/.aevum/project.json` inside every sequence folder. `.aevum`
  is a directory name, and Windows has no "open a directory with program X" mechanism;
  association would first require a single-file project format.
