# 新功能调研（2026-11-02）

**中文** · [English](新功能调研-2026-11-02.en.md)

> 结论：下一版做 **F1 长延时筛选台 + F3 逐帧时间戳叠印 + F2 星空堆栈**。前两个是 S 成本的「核心人群日用刚需」，第三个用现有对齐/合并基建吃掉星空工作流里最后一处「两跳中间文件」。

---

## 1. 调研范围与方法

- 基于 v1.2.1 现状（README「功能特性」）与 `docs/遗留台账.md` 的 B 组、「不做」条目划边界。
- 竞品调研以 2026 年公开资料为准：LRTimelapse 官方教程与论坛（2026-04 起）、darktable 5.6.0 发布说明（2026-06）、Lightroom 用户社区（2026-01）、中文创作者教程（CSDN / 头条 / 微信公众号，2026）。
- 不罗列功能清单，只找三类结构性空白：换软件重做、参数不能复用、预览与成片不一致。

## 2. 竞品与环境（2026-11 现状）

### 2.1 延时/序列专用

| 工具 | 现状 | 结构性问题 |
|---|---|---|
| LRTimelapse 7.x | 事实标准。关键帧必须进 Lightroom 编辑，靠 XMP 元数据往返 + 专用同步脚本 | 往返链脆弱：XMP 忘存/自动写入没开就断；圣杯向导在跨度极大的序列上失效（官方论坛 2026-04 建议「直接扔掉圣杯，靠多轮去闪」） |
| LRTimelapse 内部导出 | 不装 LR 也能出片 | 显影能力受限，仍要先落 JPEG/TIFF **中间序列**再渲染——磁盘翻一倍、画质多一跳 |
| StarStaX / Sequator | 星轨/夜景堆栈免费标准件 | Sequator 仅 Windows 且长期不更新；两者都**不读 RAW**，必须先在 LR 出 16bit TIFF——又一次两跳 |
| After Effects / Premiere | 大范围延时（hyperlapse）稳定、物体闪烁帧融合 | 200 帧手动补追踪点 20–40 分钟（中文教程原话）；稳定→去闪→回 LR 导出→再进剪辑，全链条最碎的一摊 |
| Time-Lapse Tool / Flicker Free | 单点去闪/去抖 | 只认成品序列，没有 RAW、没有调色 |
| qDslrDashboard / Sequence（iOS） | 拍摄端 | 与后期无衔接 |

### 2.2 通用修图/RAW

| 工具 | 现状 | 结构性问题 |
|---|---|---|
| Lightroom / ACR | AI Denoise、AI 蒙版（同步时逐帧重检）、Super Resolution | **AI Denoise 至今不能批量**（社区确认 2026-01：批量只应用到第一张），且与 Super Resolution 互斥；同一批参数 × N 帧恰恰是延时的形状 |
| Capture One | 联机拍摄最强、X-Trans 口碑最好 | 无序列概念 |
| darktable 5.6（2026-06） | 新增可选 AI 子系统（ONNX：SAM2.1 蒙版、RAW 降噪/放大，批量分块推理，GPU 失败回退 CPU）、HEIF 导出 | 单帧工具，没有对齐/去闪/重定时，AI 再强也喂不进序列 |
| RawTherapee / DxO / ON1 / Luminar / Affinity | 各有单帧强项 | 同上，序列侧全空白 |

### 2.3 三条结构性空白（机会所在）

1. **「两跳中间文件」还没死绝。** Aevum 的 ffmpeg 直推已经消掉 LRTimelapse 那一跳；但星轨/夜景堆栈用户仍必须 LR 出 TIFF → StarStaX/Sequator → Photoshop 合成前景。谁把堆栈收进序列管线，谁就吃下这条完整链。
2. **AI 能力「按帧收费」。** LR 降噪不能批量、darktable 有批量但无序列一致性（无对齐去闪）。Aevum 的自训降噪网已在显影链里逐帧生效（`ai_denoise.rs`），这条反而已经是我们的优势——**不需要再做**，要做的是别让它倒退。
3. **长延时（建筑/工程）中文生态被整个忽略。** 数万帧、废片率 30–50%、跨天续拍、逐帧时间戳、无人值守交付——中文教程全部在教「LRTimelapse + AE + Premiere 三件套」；桌面端没有一个中文原生、以序列为一等公民的工具。工程延时控制器（云相册动辄 4 万帧）在中国的存量用户不小。

## 3. 功能候选池

> 核对过仓库：逐帧调色关键帧已有（`project.rs` 的 `keyframes: BTreeMap<usize, GradeParams>`）、AI 降噪已在显影链、HDR 合并/全景/局部对齐/重定时/运动模糊/水印（静态）/MCP/队列均已存在——以下候选**不与这些重叠**。

### F1 长延时筛选台（S）— P0

- **解决谁的什么问题**：建筑/工程/城市长延时作者，一次 3–50 万帧，废片率 30–50%（夜晚欠曝、正午过曝、连续阴雨、误入异物）。今天要靠 LRTimelapse 的亮度过滤器，或者肉眼拖缩略图。
- **现状怎么凑合**：LRT 亮度/时间过滤 → 在库里删文件 → 回来重载序列；中文用户则大量手删。
- **实现成本 S**：`metrics.rs` 已逐帧测光（亮度曲线就在那儿画着），`sequence.rs` 加「按指标区间选中 → 标废 → 剔除成子序列」，`library.rs` 评级体系复用。
- **契合度**：完全复用现有序列模型与指标管线；MCP 面顺势加一条 `aevum_sequence_cull`。
- **风险**：低。剔除与关键帧索引的联动要在 `project.rs` 里定义清楚（删帧后关键帧索引怎么变）。
- **成功判据**：对一个含已知坏帧的合成序列，按「亮度 < 阈值」一键剔除后，剩余帧亮度极差收敛到阈值内，且关键帧索引无悬空。

### F2 星空/夜景堆栈导出静帧（M）— P0

- **解决谁的什么问题**：星轨创作者（lighten 叠加 + gap fill + 彗星模式）和夜景降噪堆栈用户（平均/中值 + σ-clip 剔飞机卫星）。今天必须 LR 出 16bit TIFF → StarStaX/Sequator（仅 Win）→ Photoshop 合前景。
- **现状怎么凑合**：两跳中间文件 + 两个免费工具（其一五年没更新、其一只有 Windows）。
- **实现成本 M**：`hdr.rs` 的多帧合并基建 + `align.rs` 的亚像素平移对齐直接复用；新增 lighten/平均/中值/σ-clip 四种混合与 gap fill；落 `export.rs` 静帧路径。逐帧管线完全不用动。
- **契合度**：序列 → 静帧是现有「序列 → 视频」的对偶出口，管道概念一致；AVIF 10bit HDR 出口天然可用（星空是高动态场景）。
- **风险**：中。σ-clip 与星点判据有算法不确定度，但文献充分（σ-clip 是天文社区标准做法）；性能上 N 帧累加内存要分块。
- **成功判据**：对 120 帧、每帧含一条已知位置直线亮痕的合成序列，lighten 堆栈输出中亮痕连续无缺口，σ-clip 模式下外加的 5% 离群帧被剔除。

### F3 逐帧时间戳叠印（S）— P0

- **解决谁的什么问题**：建筑工程延时交付的硬要求——画面上要能核对「这是几月几号几点拍的」。每帧时间都不同，静态水印盖不住。
- **现状怎么凑合**：LRTimelapse 把 timestamp 放在 **Pro 付费墙**里；或者用 ffmpeg drawtext 脚本逐帧烧——又回到命令行。
- **实现成本 S**：`watermark.rs` 文字路径（自绘轮廓扫描线）已能渲染一行字，加「文本源 = EXIF 拍摄时间（`exif.rs` 已解析）+ 位置/格式模板」即可；同样只在导出尾部生效，预览不叠，与现有规矩一致。
- **契合度**：高。不动管线，只扩导出尾。
- **风险**：低。唯一注意点：格式模板的 i18n（日期格式中英习惯不同）走现有语言注册表。
- **成功判据**：导出序列任意两帧上叠印文本等于各自 EXIF 时间按模板格式化，预览帧不出现该层。

### F4 色彩闪烁修正（M）— P1

- **解决谁的什么问题**：混合光源、自动白平衡、路灯频闪导致的**色度**抖动。现有去闪只管亮度（`deflicker.rs`：测光 → 稳健平滑 → EV 偏移）；LR 社区 2026 年的答案仍是「手动给每个关键帧定白平衡」。
- **实现成本 M**：同一框架从「逐帧亮度 + EV」扩到「逐帧色温/色度 + 偏移」，金标同步加 `deflicker_chroma.json`。
- **契合度**：高。管线与参考实现机制照搬。
- **风险**：中。色度平滑不当会把日落时**该有的**色温漂移抹平——判据必须区分「自然渐变」与「帧间抖动」，这正是 A 组自证式测量的套路。
- **成功判据**：合成序列（色温叠加 ±200K 帧间抖动 + 缓慢真实漂移）修正后，帧间色差的标准差下降 ≥10 倍而漂移趋势保留。

### F5 圣杯自动过渡（M）— P1

- **解决谁的什么问题**：日转夜序列的曝光 ramp。LRT 的圣杯向导读 EXIF EV 差做初始补偿，但跨度大就失效（官方论坛承认），用户最后都靠多轮去闪兜底。
- **实现成本 M**：`exif.rs` 读 EV → 逐帧初始曝光补偿 → 现有去闪接管残差。**不做 LRT 式向导 UI**，做成去闪面板里的一个「按 EXIF 预对齐」开关。
- **契合度**：高，与现有关键帧 + 去闪叠加而不是替代。
- **风险**：中。EXIF 缺失/错写的容错；`MAX_EV=3` 的上限对日夜全程要放宽为可配。
- **成功判据**：合成日转夜序列（EXIF EV 从 +2 线性走到 −5）开启后，去闪前的亮度残差较关闭时下降一个量级。

### F6 MCP 无人值守批量编排（M）— P1

- **解决谁的什么问题**：多机位工程延时与批量出片的后期：夜里让 agent 把某个文件夹下全部序列跑「筛选 → 去闪 → 预设 → 渲染队列」。今天队列只吃单序列任务，跨序列编排靠人。
- **实现成本 M**：`aevum-mcp` 加 2–3 个编排工具（枚举序列、下发队列、回报进度），`queue.rs` 提升为可挂多序列。
- **契合度**：极高——MCP 控制面是这个产品的核心差异，别的竞品连接口都没有。
- **风险**：低-中。无人值守时的失败策略（坏帧、磁盘满）要在工具返回里可读。
- **成功判据**：一条 MCP 调用对一个含 3 个序列的目录完成端到端渲染，中途注入一个损坏序列，返回体里可读到「2 成功 1 失败 + 失败原因」。

### F7 Hyperlapse 大位移路径稳定（L）— P2

- **解决谁的什么问题**：大范围延时每 200 帧手补追踪点 20–40 分钟。现有 `align.rs` 的局部对齐是「小位移」口径，跨大基线要特征跟踪 + 路径平滑 + 自动裁剪。
- **风险**：高——算法不确定度大，AE Warp Stabilizer 是十几年迭代；做不好不如不做。观察项。

### F8 AI 蒙版（SAM 类交互分割）（L）— P2

- **解决谁的什么问题**：darktable 5.6 已把 SAM2.1 蒙版做成可选 AI 子系统，LR 有 Subject/Sky。现有蒙版是亮度/色彩范围，对「天空之外的楼」这类语义目标无能为力。
- **风险**：架构拍板题——引入 ONNX Runtime 与模型下载机制违背当前「exe 无外部推理依赖」的洁癖（darktable 的做法：默认关闭、可开、GPU 失败回 CPU）。这是方向决策，不是功能决策。观察项。

### F9 平台交付预设（S）— P1

- **解决谁的什么问题**：抖音/B 站/视频号各有一套尺寸-码率-帧率口径，中文教程全在教「4K 25fps 不低于 50 Mbps」这类口诀。导出面板加一组平台预设 + 文件命名模板。
- **成本 S**（`export.rs` 预设表 + UI）；**风险**：低（平台参数会漂移，预设要可编辑）。
- **成功判据**：选「竖屏短视频」预设后输出的文件尺寸/码率与预设表逐项一致。

### F10 X-Trans 传感器覆盖（L）— P2

- **解决谁的什么问题**：富士延时用户现在只能在 Capture One/LR 里出片。rawler 能解码 X-Trans，但现有去马赛克（方向判据 + 色差恒常）是 Bayer 口径，X-Trans 3×3 CFA 上 45° 上限分析全部要重做。
- **风险**：高（算法重做 + 台账 B4 的分析口径要重建）。观察项，等富士用户声音变大再立项。

## 4. 分级与推荐

| 级 | 条目 | 一句话理由 |
|---|---|---|
| **P0（下一版）** | F1 筛选台、F3 时间戳、F2 星空堆栈 | 两个 S 打穿「长延时中文生态」日用刚需，一个 M 用现有基建吃掉最后一处两跳 |
| **P1（再下一版）** | F4 色彩去闪、F5 圣杯预对齐、F6 MCP 批量编排、F9 平台预设 | 全部是现有管线的延伸，无新依赖 |
| **P2（观察）** | F7 Hyperlapse、F8 AI 蒙版、F10 X-Trans | 各有一个「架构/算法方向」待拍板 |

### 前 3 名推荐理由

1. **F1 筛选台**：成本最小、人群最痛、复用度最高（指标已在画、评级已在存）。它是长延时工作流的**第一步**，抢占入口。
2. **F2 星空堆栈**：唯一一条能讲出「删掉两个软件」的候选。StarStaX/Sequator 是停滞的免费件，这个人群对「一个窗口从 RAW 到成片」的感知会非常直接。
3. **F3 时间戳**：S 成本撬动 B 端（工程延时交付是能收钱的场景），且 LRT 把它锁在 Pro 付费墙里——我们免费给，就是差异点。

### 为什么不是另外那几个

- **F4/F5（去闪扩展）**：重要但属「质量深化」，用户现状能凑合（多轮去闪 + 手动关键帧）；P0 的三个是「现状完全没法凑合」的。
- **F6（MCP 批量）**：价值高但前提是 F1 的筛选语义先定下来（无人值守剔除的规则不该先于筛选台本身存在），顺序依赖。
- **F9（平台预设）**：太便宜，不需要占 P0 名额，跟谁顺路谁带上。
- **F7/F8/F10**：各自押一个 L 级赌注（跟踪算法 / AI 架构 / 去马赛克重做），在 S+M 已经排满的下一版里挤不进去，也不该挤。
- **不做**（台账已有结论，不翻案）：TIFF/PNG 16bit HDR；新增「LR 往返兼容」——那是把两跳workflow的病根接回来，与本产品定位相反。

## 5. 需要拍板的分歧点

1. **F2 排期**：P0 是 2×S + 1×M。若下一版容量只够两个 S，F2 与 F3 谁让位？（我主张保 F2——它承载「一个窗口」的叙事，F3 可以插队进任何一版。）
2. **F5 的产品口径**：只做「EXIF 预对齐」开关，还是也要 LRT 式圣杯向导 UI？我主张前者（向导 UI 是 LRT 的包袱，不是资产）。
3. **F8 的架构方向**：要不要为 AI 能力开「可选子系统」的口子（模型下载、GPU 运行时、默认关闭）？这决定的不只是蒙版一条功能，而是此后所有 AI 功能的落点。
