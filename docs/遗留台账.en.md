## A. Parameter fitting debt

One method throughout: `TODO(fit)` means "this number has no basis". There are exactly two ways out —

- **Literature value**: the original paper or spec states this number; cite the source and change the
  marker to `(literature value)`;
- **Self-proving measurement**: build a scene whose correct answer is known, measure the mapping from
  parameter to observable quantity, and turn a guess into a measured choice. The criterion must be
  **independent of the reference implementation** — the golden file only proves Rust == Python, and a
  guessed value written into both sides is green forever.

## 2026-11-05 (9) "Follow the system" now really follows the system on Windows

| Item | Record |
|---|---|
| Symptom | The settings panel defaults the UI language to "follow the system" (`LangPref::System` carries `#[default]`, stored as `settings.json`'s `lang`, resolved at startup), but `Lang::from_system()` **only read three Unix-style variables -- `LC_ALL` / `LC_MESSAGES` / `LANG` -- and never asked Windows**. Measured on this box: the OS UI language is `zh-CN`, while the terminal carries `LC_ALL=C.UTF-8` / `LANG=en_US.UTF-8`, so a terminal launch defaulted to **English** while a double-click launch (no variables) fell back to **Chinese**. Two languages on one machine, neither of them the system language; a Chinese box launched from a terminal inexplicably turned English, and an English box launched from Explorer stayed Chinese |
| Why no assertion caught it | The old implementation was only reasoned about in a "clean" environment: its comment says `LANG` is often absent on Windows so it also checks `LC_ALL` / `LC_MESSAGES`, but those are equally absent on native Windows. Conversely, a Git/MSYS terminal injects `LANG`, so **a Chinese dev machine can show both opposite results** -- yet nobody asserted against the OS language as an input. Same environment-coupling family as today's CI encoding and batch-file bugs |
| Fix | On Windows, `GetUserDefaultUILanguage()` yields a LANGID, `LCIDToLocaleName()` turns it into a BCP-47 name (`zh-CN` / `en-US`), and the existing `Lang::from_code` alias table resolves it; the three environment variables remain a fallback (other platforms, or when the API fails). **No new dependency** (both live in kernel32, linked by default; the inline FFI mirrors `export_bench.rs`'s `GetProcessTimes`) and **no hard-wired language** (adding one still means one line in `CATALOGS`, so the module-level promise holds). Extracted a pure `resolve_system(os_name, vars) -> Lang` so tests can inject inputs |
| Assertions | (1) `system_language_wins_over_shell_environment`: `en-US` -> EN, `zh-CN` -> ZH, Chinese OS plus English shell still ZH, unregistered `ja-JP` falls back to Chinese, variables still work without an OS answer, no information at all falls back to Chinese. (2) `from_system_really_reads_the_windows_ui_language`: `from_system()` must equal `resolve_system(real OS name, real variables)`. Nothing assumes a particular OS language, so it holds on an English CI runner too |
| Mutation check | Drop the Windows probe result inside `from_system` (equivalent to the old implementation) and assertion (2) goes red: `left: Lang("en") / right: Lang("zh")` -- exactly this machine's real combination; the other 11 i18n assertions stay green. Restoring turns them green again |
| Compile-time wrinkle | This is edition 2024, so `extern "system" { ... }` fails with "extern blocks must be unsafe"; it has to be `unsafe extern "system"` |
| Impact | First launch on English (or other) systems finally follows the OS; a Chinese system launched from a terminal no longer turns English for no reason. Users can still pin Chinese / English in settings, and `LangPref::System` still resolves once per launch |
