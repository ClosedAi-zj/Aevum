# Aevum Studio Algorithm Whitepaper

**English** · [中文](白皮书.md)

## 1. What this document solves, and who it is for

`docs/system_design.md` describes module structure and feature lists; the README describes
features and usage. This document covers exactly one thing: **the convention of every
algorithm** — formulas, constants, why each value is what it is, boundaries and known
limits. It is written for two audiences: a newcomer about to change an algorithm, and
myself a few months from now wondering "why is this 0.40 again?".

Conventions:

- Every number can be traced to a source: `crates/aevum-core/src/xxx.rs::symbol`, or a
  backlog ID (A1–A9, B2–B5) from the backlog ledger. Numbers without a traceable source
  are not written down at all.
- "Criterion" means a test name under `crates/aevum-core/tests/suite/` or inside a module's
  `#[cfg(test)]`. A criterion existing means the number is pinned; changing it requires
  changing the criterion too, with a stated reason.
- This document does not re-argue the golden mechanism. The golden (Python oracle) only
  proves Rust == Python; **it cannot prove a number is correct** — the same guess written
  into both ends stays green forever. Parameter correctness is owned by the self-verifying
  measurements in section 8; the two have different jobs.

## 2. Data flow and the single source of truth

### 2.1 The overall chain

```
sequence discovery (sequence) → per-frame metering (metrics / deflicker) → exposure
correction Ev → develop main chain (develop) → preview / still export / video export
(preview / export) → encoding (ffmpeg or built-in writers)
```

### 2.2 Two independent metering conventions

- `crates/aevum-core/src/metrics.rs::FrameMetrics`: gamma-domain mean brightness ("how
  bright it looks"), 512 long edge with area averaging, feeding the filmstrip curve,
  sequence QA, and the exposure ladder.
- `crates/aevum-core/src/deflicker.rs::FrameMeans`: **linear-light** 1%..99% trimmed mean
  (`deflicker.rs::trimmed_mean`), 320 long edge (`deflicker.rs::SCAN_LONG`). Deflicker must
  work in linear light: sRGB encoding flattens brightness jumps and cannot suppress color
  flicker.

The two never call each other. This redundancy is intentional: one serves "display", the
other serves "correction".

### 2.3 The develop main chain is the only pixel source of truth

GUI preview, still export and video export all go through
`crates/aevum-core/src/develop.rs::render`; the preview layer's
`crates/aevum-core/src/preview.rs::render` / `::render_sketch` / `::render_hdr` are pure
forwarders that swap the `Opts` of `develop::render`. Geometry (rotate / offset / framing)
lives in `crates/aevum-core/src/warp.rs`, and preview and export call the same function.
There is no second pixel implementation — that is the only way "what you preview is what
you export" can hold, and the condition for the golden to pin all three paths at once.

The four switches of `develop.rs::Opts` decide what gets skipped:

| Switch | Skips | Purpose |
|---|---|---|
| `sketch` | denoise, sharpening, clarity, texture, local spatial terms | responsiveness while dragging |
| `for_lut` | lens correction, all spatial ops, masks, grain, vignette | .cube generation (only pointwise terms can enter a LUT) |
| `local` | monochrome and global-only terms | the sub-chain inside a mask |
| `hdr` | one thing only: the exit does not clamp >1 to 1 | HDR export |

The difference between `sketch` and full render is **exactly** the skipped terms; with no
spatial parameters they are pointwise identical (`preview.rs::render_sketch` doc).

### 2.4 `STAGES_READY`: the honesty switch

`crates/aevum-core/src/develop.rs::STAGES_READY` lists the stages that have landed and are
pinned pixel-for-pixel by the golden (`tone` / `lut` / `spatial` / `vignette` / `mask` /
`mask_local` / `grain`). `tests/suite/develop_golden.rs` asserts pixel-for-pixel only for
cases whose stages are all in that list. Implementing a new stage means adding it there;
before that, do not claim consistency.

### 2.5 The shape of the deflicker correction

`crates/aevum-core/src/develop.rs::Ev`: a frame-wide EV offset `add` plus per-channel
residuals `chan`. For per-channel deflicker, the three-channel mean is merged into `add`
and only the color difference stays in `chan`; the two sum back to exactly that channel's
offset (`deflicker.rs::Analysis::chan_residual_per_frame`, criterion
`channel_residual_reconstructs_the_offset`). With `chan` all zero the result is
bit-identical to the older brightness-only convention.

## 3. The develop main chain, stage by stage

The order below copies the header comment of `crates/aevum-core/src/develop.rs` and
matches the Python oracle `acceptance/reference/grade.py::_core` / `apply` exactly. All
pixel buffers are sRGB-encoded, row-major, `[0,1]` f32; the luma coefficients are
`LUMA = [0.2126, 0.7152, 0.0722]` (`develop.rs::LUMA`). Per-pixel segments parallelize in
chunks of `MIN_PIXELS = 4096` (`develop.rs::MIN_PIXELS`); threading changes no values.

### 3.0 Lens correction (head of chain)

`crates/aevum-core/src/develop.rs::render`: the LCP profile (matched via EXIF,
`lcp.rs::Correction`) wins, then the camera/lens database (`lensdb.rs`), then the three
manual sliders (distortion / vignette / fringing, `develop/spatial.rs::lens`). The order
matters: fix the true geometry first, so the manual sliders remain creative quantities.
`for_lut` skips the whole stage.

### 3.1 External .cube look

A 3D lookup is applied before the main chain (`crates/aevum-core/src/cube.rs`). The
position matches the "a look modifies the input, not the output" usage. The Python oracle
has no such step; `look_cube` stays empty in golden cases, so comparison is unaffected.
LUT export runs the `for_lut` pointwise chain (`cube.rs::build`); the lattice varies red
fastest (`cube.rs::lattice`), default 65 cubed (`cube.rs::DEFAULT_SIZE`).

### 3.2 Denoise

AI denoise first, classical guided-filter denoise after (`develop.rs::core`): the AI net
learns the noise as-is, and the residual noise it leaves is then handed to the guided
filter. Both live inside `opts.detail()` (skipped for sketch/local), and a parameter of 0
skips the whole segment, so goldens are unaffected.

The network structure and measurements are in `crates/aevum-core/src/ai_denoise.rs`: two
separate paths, each a residual net of four 3x3 convolutions; the luminance net takes
Rec.601 luma, the chroma net takes (B−Y, R−Y) — a signed color difference is identically
zero on gray, so chroma denoise never drags colors off. Joint training failed (chroma PSNR
still 0.00 dB after 5000 epochs), hence the split. Inference is tiled at 256 squared,
keeping only tile centers, with a 4-pixel overlap (`ai_denoise.rs::TILE` / `::RADIUS`); on
x86_64 with AVX2+FMA a hand-written vector path runs, a 5984x3959 frame takes about 2.3 s
for both paths (a 1600x1067 preview about 0.2 s), the scalar path about 5.7 s per net.

The manual noise sigma mapping `sigma = 0.002 + (v/100)^1.6 * 0.030`
(`grade.rs::nr_sigma_manual` doc) is the product of A9; see section 8.

### 3.3 White balance / exposure (linear light, one pass)

`develop.rs::core`. Gains `g = [1+0.30t+0.08u, 1−0.22u, 1−0.30t+0.08u]`
(t = temperature/100, u = tint/100), normalized by the `LUMA` dot product, then multiplied
by `2^shift` (shift = parameter exposure + deflicker EV, including residuals when
per-channel). sRGB ↔ linear round trips use `develop.rs::srgb_to_lin` / `::lin_to_srgb`.

**Exposure highlight shoulder** (`hl_rolloff`, matching the LR rolloff convention):
`yy = y + krl*t/(1+t/len)` with `t = max(0, y−knee)`, scaled by the luminance ratio to
preserve hue. Two points are pinned by measurement (A7):

- `knee = 0.75` (linear) = encoded 0.881: everything below is bit-identical; measured,
  encoded 0.875 does not move and 0.885 does — a 0.01 window in encoded units;
- `len = 0.40`: the saturated lift is `krl*len`; maxed, encoded 1.0 rises into
  [1.03, 1.10].

**Note this function is not C1-continuous**: at the knee the slope jumps from 1 to
`1+krl`; it is a C0 corner, kept on purpose (lift only the brightest sliver). The
`develop.rs::core` comment records that it used to be wrongly described as C1 — do not
change it back.

### 3.4 Contrast

The gamma-domain delta and the linear-light S-curve delta are blended by `contrast_linear`
(`develop.rs::core`). The linear S-curve is `develop.rs::contrast_s_lin`: it pivots on
**mid-gray** (`u = xl^0.4496` → smoothstep → `u^2.2242` back), with `GAMMA=0.4496` /
`INV_GAMMA=2.2242` fixed in the function. A plain smoothstep on linear values would lift
the pivot to encoded 0.735; measured with contrast=50, mid-gray 0.5 was pushed to 0.4487
(14 levels eaten at 8 bit). The current implementation keeps mid-gray fixed across the
whole range (criterion `fit_sliders.rs::contrast_linear_keeps_mid_gray_fixed`, closed
entry in the backlog).

### 3.5 Dehaze (pointwise term + DCP spatial term)

The pointwise term in `develop.rs::core`: for positive `dz>0`, `x ↦ (x−v)/(1−v)` with
`v = dz*0.25`; for negative values, `x ↦ x(1−0.20v)+0.07v`.

The spatial term is dark-channel-prior dehaze (He DCP plus guided-filter refinement),
`develop/dehaze.rs::dehaze_dcp`, executed in linear light, layered after the pointwise
term. The seven internal constants live in `dehaze.rs::DehazeTune`, each with a source
(A1–A4, section 8): `t0=0.1` and `omega=0.95` are the DCP paper's own values, `eps=1e-4`
is the guided-filter convention for [0,1] data (0.01 squared), `r_div=200`,
`round_div=1` (effective radius = nominal radius, criterion
`min_filter_effective_radius_is_the_nominal_radius`), `t_radius_mul=4`,
`contrast_amp=0.15`. The contrast trim amplitude is contrast*0.15, criterion
`contrast_trim_is_linear_and_safe` (a maxed shift moves the black point 3.1%, inside the
10% line).

Known limit: DCP always darkens sky (sky has no dark channel) — that is the algorithm's
ceiling, not a parameter fault; the sweep uses both restoration PSNR and transmission RMSE
precisely to separate the two (`dehaze.rs` fit module `score` doc). The 48x64 golden
covers only the full-resolution guided-filter branch; the downsampled branch is covered by
`dehaze_downsample_matches_python` against Python-reference statistics (tolerance 2e-3),
not a per-pixel freeze.

### 3.6 Highlights / shadows / whites / blacks

One scan weighted by `LUMA` luminance (`develop.rs::core`):

- Highlights: `fac *= 1 + a*0.5*smooth(0.45, 1.0, lum)`
- Shadows: `k = sh*0.45*smooth(0.55, 0.0, lum)`, `fac *= 1−k`, `add` blends toward 1.2
- Whites: `k = wh*0.5*smooth(0.60, 1.0, lum)^2`
- Blacks: `add += bl*0.35*smooth(0.40, 0.0, lum)^2`

The segment ends with a hard clamp to [0,4] by default; `black_soft`/`white_soft` > 0
replace it with parabolic soft knees `develop.rs::soft_clip_high` / `::soft_clip_low`
(C1-continuous, bounded by 1, monotonically non-decreasing — provable, not approximate).
The width mapping `s = 0.08 + 0.17*(v/100)` (A6): the upper bound 0.25 keeps everything at
or below encoded 0.75 bit-identical; the lower bound 0.08 keeps the smallest setting
visible at about 0.7 of a level. Criterion
`fit_sliders.rs::soft_clip_is_c1_and_width_bounds_are_meaningful`.

### 3.7 Sharpening

USM + edge masking + halo limiting (`develop/spatial.rs::sharpen`, inside
`opts.detail()`). The always-on edge protection `sharp_protect` (aligned with LR
Sharpen3) is measured: at full sharpening, no protection amplifies noise 1.944x; 20 brings
it to 1.773 and 100 to 1.093, while the edge gain never moves (1.359)
(`fit_sharpen_protect.rs`, `grade.rs::sharp_protect` doc). The 0–50 dead zone of
`sharp_masking` is closed (noise gain 25 → 1.816, 50 → 1.385; criterion
`fit_sharpen_protect.rs::masking_responds_across_the_whole_slider`).

### 3.8 Clarity / texture

Shared `develop/spatial.rs::local_contrast`: the luminance field is guided-filtered into a
detail layer, weighted by `0.35 + 0.65*mid` for midtones, ratio clamped to [0,3]. Clarity
radius `max(2, min(w,h)/60)`, amount scaled by 1.6, eps 0.02 (`develop.rs::clarity_radius`
and the call site in `core`); texture radius `max(1, min(w,h)/300)`, eps 0.004
(`develop.rs::texture_radius`). Both radius formulas copy the Python reference. Sketch
skips them (among the most expensive terms in the chain).

### 3.9 Vibrance / saturation

`develop.rs::core`: `f = 1 + sat`; vibrance multiplies in `1 + vib*(1−range)*1.3` (range
is the per-pixel channel spread, so low-saturation pixels gain more). Scaling is computed
around luminance, and in HDR mode the region above white takes part (otherwise this stage
would flatten HDR highlights before they are ever encoded). HDR floors negatives, SDR
clamps to [0,1].

### 3.10 Color grading

`develop/lut.rs::color_grade` + `::grade_table`: an RGB offset table over 1024 luminance
steps (`GRADE_N`). The three band windows are steered by balance
`a = 0.46 − balance/100*0.12` (clamped to [0.18, 0.78]); tint strength is s/100*0.18 times
a zero-sum hue vector (`lut.rs::hue_vec`), luminance offset is l/100*0.15; blending
interpolates the weights toward pure luminance. Pointwise table lookup, no neighborhood
access, so `for_lut`/sketch run it unchanged.

### 3.11 HSL

`develop/lut.rs::hsl` + `::hsl_tables`: 8 hue bands centered at
`HSL_CENTERS = [0,30,60,120,180,240,285,330]`, with band weight `smooth(50, 18,
hue_dist)` over a 65536-entry hue table (`HUE_BINS`). Hue shift is h/100*40 degrees,
saturation factor is 1 + s/100*w, luminance factor is 1 + l/100*0.6*w. All three axes
share the bin index computed from the **original** hue (Python computes idx before
changing h). RGB ↔ HSV follows the OpenCV float convention (`lut.rs::rgb_to_hsv` /
`::hsv_to_rgb`; round-trip stability is asserted by `hsv_round_trip_is_stable`).

### 3.12 Monochrome

`develop/lut.rs::mono`: Rec.709 luminance blended with an 8-band luminance mix table (the
Lightroom B&W Mixer convention), interpolated toward the original color by `mono/100`.
Skipped inside a mask's local chain (`opts.local`) — monochrome is a global-only term.
Note: black and white must go through mono; lowering saturation alone leaves the 8 B&W
mixer sliders inert (`grade.rs::preset` comment for the black-and-white preset).

### 3.13 Levels + parametric curve + curve (one composed table)

`develop/lut.rs::curve_lut`: the five levels terms (`::levels_lut`, minimum span of
`+2/255` after normalization, gamma clamped to [0.1, 5.0]) and the four-band parametric
curve (`::par_lut`, amplitude `PAR_SCALE = 0.18`, `np.maximum.accumulate` for strict
monotonicity) compose a base index first, then the master curve and per-channel curves
(Fritsch–Carlson monotone cubic, `grade.rs::pchip_lut`) compose a 65536-entry uint16 table
(`CURVE_N`) that is quantized once and looked up once. The `np.rint` (round-half-to-even)
quantization is reproduced by `lut.rs::rint`.

**Curve HDR tail** (`lut.rs::tone_curve_keep_over`, HDR only): inputs above 1 extend as
`y1 + (x−1)*slope` instead of being truncated, with
`slope = pchip_end_slope/255 + k*0.6`. The 0.6 is the product of A5: four criteria
(carries the input / does not amplify / slope stays in [0.40, 0.85] / x=4 and x=2 remain
distinguishable), measured slope = 0.6033, x=1.5 → 1.0858, x=2 → 1.3873, x=4 → 2.5934
(s_curve(200), endpoint 0.7843). It feeds on the >1 created by the exposure stage
(`grade.rs::curve_hdr_tail` doc): the lens stage's clamp runs before exposure and never
sees it.

### 3.14 Local masks

`crates/aevum-core/src/mask.rs`: geometry is persisted in normalized coordinates, so one
set of parameters circles the same region at any preview resolution; parameters are
**deltas relative to the global grade**. Rendering (`develop.rs::render`): keep a copy of
the original → run the global chain → for each mask carrying deltas, re-run
`develop.rs::core` (`opts.local`) on the original plus the delta → blend back by weight
field → clamp per mode (SDR pins to white / HDR floors negatives) → finally re-apply
in-mask sharpening / denoise / clarity / texture (`develop/spatial.rs::mask_spatial`, same
convention as Python). A mask can carry 13 per-point parameters (`mask.rs::MASK_KEYS`),
one-to-one with the Python `MASK_KEYS`.

### 3.15 Grain

`develop/spatial.rs::grain` (skipped for `for_lut`). The luminance modulation `grain_lum`
is a design choice, not a fitted value: at full strength, shadows gain x2.5 and highlights
x0.3 (x1.75 / x0.65 at the half detent); cross-implementation agreement is guarded by the
`grain_stats_lum` golden — statistics only, tolerance ±25% (`grade.rs::grain_lum` doc).
The grain random sequence cannot match numpy (separate deterministic generators), so the
golden pins statistics and spatial structure only; the field is cached by (dimensions,
size, freq) and does not depend on the frame number.

### 3.16 Vignette

`grade.rs::vignette_mask`: a multiplicative mask; the elliptical/circular radius blends by
`roundness`, `start = midpoint*0.9`, `width = max(0.05, feather*1.2)`. Highlight
protection `vig_hl_contrast` returns the amount suppressed from bright pixels based on the
current pixel's luminance (only above 0.5). It runs after masks and grain: local
brightening must not pull the darkened corners back (`develop.rs::render` doc).

### 3.17 The final clamp

The last step of `develop.rs::render`: SDR clamps to [0,1] (it is written as 8 bit), HDR
only floors negatives — whatever is above white must reach the PQ encoder. This is the
only substantive difference between HDR and SDR, and all three clamps (mask blend exit
before vignette, the vibrance stage, the exit) branch on `opts.hdr`. Criterion
`fit_sliders.rs::hdr_render_keeps_brightness_above_white` (SDR tops at 1.0 / HDR > 1.2);
the SDR golden md5 is unchanged (closed entry in the backlog).

## 4. Sequence-level algorithms

### 4.1 Alignment

`crates/aevum-core/src/align.rs`. Two estimators: `Template` (bottom template + CLAHE
grayscale + normalized cross correlation + parabolic subpixel; most robust against
vertical drift from a sinking camera) and `Phase` (phase correlation over the same
hand-written 2D FFT). The convention is `dst(x,y) = src(x−off_x, y−off_y)`, matching the
Python `acceptance/reference/align.py`. Template start 0.7, search margin 150 px, CLAHE
grid 8 / clip 2.0 (`align.rs::SEARCH_MARGIN` / `::TEMPLATE_START` / `::CLAHE_*`); defaults
`max_shift=64`, `smooth_window=15`, `jump_px=24.0`, `min_score=0.35`
(`align.rs::AlignOptions::default`). The 4K template's cross correlation runs on the
hand-written FFT covering only the search window (4096x2048); no full-frame f32 copy is
kept. Residual verification takes the bottom ROI and warps per pixel with bilinear
sampling; no full warped image is materialized. Golden: `tests/suite/align_golden.rs`.

### 4.2 Deflicker

`crates/aevum-core/src/deflicker.rs`. Metering (linear-light trimmed mean, section 2.2) →
log2 → per column: a median filter (edge-replicated) suppresses single-frame jumps →
Gaussian smoothing (sigma = max(0.8, window/4), `deflicker.rs::analyze`) keeps the
correction from introducing steps → offset = target − current, applied by strength/100
and clamped to ±`MAX_EV` (3.0, `deflicker.rs::MAX_EV` — beyond that it is a bad frame, not
flicker). The multiscale mode passes window 3 first, then the full window
(`deflicker.rs::pass_windows`). The window is clamped to [3, 199]
(`deflicker.rs::WINDOW_MIN` / `::WINDOW_MAX`), even windows bump to odd, over-long windows
shrink to the frame count. Unreadable frames are filled by interpolation but their offset
is forced to 0 (criterion `missing_frames_are_interpolated_and_left_alone`). Statistics:
P95 of adjacent-frame differences (`deflicker.rs::jitter`). Golden
`acceptance/oracle/golden/deflicker.json`, tolerance 1e-4.

### 4.3 HDR merge

`crates/aevum-core/src/hdr.rs`: Mertens exposure fusion, no camera response calibration
and no radiance recovery. Each pixel is scored by the three published formulas
"well-exposed x saturated x contrast", then collapsed through a Laplacian pyramid. At most
9 frames per fusion (`hdr.rs::MAX_FRAMES`).

### 4.4 Retime (speed change + motion blur)

`crates/aevum-core/src/retime.rs`. Speed keys use **source progress** (0..1), not output
seconds — the render length is the integral of speed, not an input. Output frame count
`n_out = floor(n_src * integral of du/speed(u) over 0..1)`, exactly `n_src` at constant
speed. The shutter (0..1): within the exposure interval one output frame covers, crossed
source frames are averaged with weights given by their overlap time — the accumulate-
and-average the time-lapse world uses, no optical-flow interpolation; 0 means a linear
interpolation between two neighbours only. One run is capped at 200,000 output frames
(`retime.rs::MAX_OUTPUT_FRAMES`; beyond that the request is refused up front — a
slow-motion stretch that long means a wrong speed was entered). With `enabled=false`, or
constant speed with zero shutter, export takes the 1:1 fast path and not a single pixel is
touched (`retime.rs::Retime::is_identity`).

### 4.5 Music muxing

`crates/aevum-core/src/audio.rs`. A sequence carries no production sound, so music is
**replacement**, not a two-path mix. Delay pads with true silent samples via ffmpeg
`adelay`, looping uses `-stream_loop`, fades and volume go through filters (convention
aligned with the Python `acceptance/reference/audio.py`). The codecs a container can take
unchanged are aac / mp3 / alac only (`audio.rs::COPYABLE`); everything else re-encodes to
AAC; a volume deviation within 0.5% skips re-encoding
(`audio.rs::AudioOptions::needs_filter`).

## 5. RAW decoding: the capability boundary

`crates/aevum-core/src/raw/mod.rs` is the "generic fallback: CFA + embedded preview"
two-route design; both routes must report which one ran (`raw/mod.rs::RawPath`): `Sensor`
(16-bit sensor decode) or `Preview` (the camera's full JPEG). Fidelity is stated by
`RawPath`, never faked by bit depth — the preview itself is 8 bit and is scaled to 16 bit
by `v*257` on return; **this is width representation only, not added precision**.

### 5.1 The built-in CFA route (what it decodes, what it refuses)

Decode only when the IFD is explicit: single-channel CFA or linear raw data, uncompressed
(DNG additionally accepts Adobe Deflate, `dng.rs`), an 8- or 16-bit container, strip
length divisible by the row length. Caps: 512 MB per file, 40 MP
(`raw/mod.rs::MAX_FILE_BYTES` / `::MAX_PIXELS`); the DNG path caps at 24 MP
(`dng.rs::MAX_PIXELS`).

**Never guess pixels** is the route's principle. The following are soft errors — fall back
to the embedded preview rather than guess: 12/14-bit in-row packing ("per-row packing" and
"continuous whole-image packing" give exactly the same strip byte count at common widths;
a wrong guess shears the whole frame), lossless JPEG, CRX, tiled storage, private CFA
position markers. CFA uses only the standard tags `CFARepeatPatternDim`(33421) /
`CFAPattern`(33422); white balance uses only the three `AsShotNeutral`(50728) gains, and
without that tag no grading is applied.

The following are hard errors — named errors, no fallback, no guessing: BigTIFF/RRIF
containers, a CR3 with no embedded preview (CR3 is not TIFF; it is an ISO base media
container plus Canon's CRX, and the built-in route **does not decode CRX** — it does one
thing: find the camera-written full JPEG preview inside the container bytes), files or
pixel counts over the caps. Boundary criteria: `tests/suite/raw_reads.rs`,
`tests/suite/dng_reads.rs`.

Two built-in demosaic methods: `cell_average` (2x2 cell averaging, deliberately the same
coarse estimator as `dng.rs`) and `directional`, switchable at runtime
(`raw/mod.rs::demosaic_method` / `::set_demosaic_method`). The built-in route does **not**
apply ColorMatrix / camera gamut / preset baseline — C/M/Y patterns, four-color Bayer and
X-Trans, which are only correct with a color matrix, are rejected upstream and fall back
to the preview.

### 5.2 The rawler fallback

Under the default feature (`raw-rawler`), `read` tries the rawler sensor decode first:
CRX and the 12/14-bit packing layouts the built-in route rejects are covered there and
returned as `Sensor`; when rawler cannot decode, the built-in two routes take over. Built
with `--no-default-features`, behavior is identical to v0.3.0. rawler is LGPL-2.1 and
statically linked; a build that must be entirely copyleft-free uses
`--no-default-features` (README, "License").

### 5.3 Four bugs pinned by a real sample (B5)

Invisible to synthetic targets, exposed and fixed by the real sample
`samples/cc0/apple-iphone6s-plus/IMG_0853.DNG` (CC0, 4032x3024): (1) a real iPhone DNG
failed to open (the built-in parser did not fall back); (2) reading IFD0 only yielded an
852x640 thumbnail (the main image sits in SubIFDs, `dng.rs::TAG_SUB_IFDS`); (3) metadata
was coupled to pixel storage (with compression=7 even the size was unreportable); (4) the
**CFA value mapping was shifted by one** (the spec says `0=R,1=G,2=B`, the code read
2/3/4, so every compliant file was rejected while synthetic targets written under the
same wrong convention passed — a self-confirming false green). Criteria: the four in
`tests/suite/raw_real_sample.rs`; two mutations (mapping reverted to 2/3/4, `main_ifd`
degraded to IFD0) both turn red.

### 5.4 The demosaic limit imposed by sampling (B4)

The green error on 45-degree edges is bounded by "boundary fraction x one full step": the
green neighbours of an R/B site are only up/down/left/right, and on a 45-degree line those
are the **same-color** R/B, not G, so the boundary ring is necessarily wrong by a whole
step. 1/6 x 13000 = 2167; the measured R/B mean error is 2190 = 0.168 x step — they agree,
meaning not a single pixel outside the boundary is wrong. The directional method's +3 dB
comes from the R/B channels (constant color difference), not green; the soft decision was
rejected (on the same target 45-degree 24.55 → 23.85 dB, colored edges 19.81 → 17.23 dB;
blending candidates into middle values equals erasing the edge). Criterion
`raw::cfa::tests::diagonal_edges_are_bounded_by_the_sampling_pattern`.

## 6. Color

### 6.1 The working space

The grading pipeline computes end to end in **sRGB (D65 white point, sRGB transfer
function)**. Linear/encoded round trips use exactly one pair:
`develop.rs::srgb_to_lin` / `::lin_to_srgb`. Dehaze, white balance and exposure run in
expanded linear light; lookup-table operations run in the encoded domain. There is no
second working space.

### 6.2 Output tagging and conversion

`crates/aevum-core/src/colorspace.rs`; two tracks, each owning one job (**changing the tag
without moving the pixels is wrong**):

- `Srgb`: default, no ICC embedding, no pixel changes.
- `DisplayP3`: DCI-P3 primaries + D65 + the sRGB transfer function; pixels are genuinely
  converted to P3, and stills embed a self-generated ICC (Bradford adaptation to the D50
  PCS — the spec requires it; without it the system reads a color-shifted white).
- `Rec2020`: BT.2020 primaries + D65 + gamma 2.4, an **SDR tag, not HDR**.

Every ICC constant is a published colorimetry standard value plus matrices derived here;
no third-party color engine data is referenced. The final judge of the ICC bytes is not
the unit test: set `AEVUM_ICC_DUMP=<dir>` to persist the profiles, then run
`python acceptance/oracle/check_icc.py` to have littleCMS read them back (both curve-shape
revisions came out of that step).

### 6.3 DCP camera profiles

`crates/aevum-core/src/dcp.rs::decode`: white balance → color matrix → HueSatMap
(trilinear interpolation in the HSV space of ProPhoto linear RGB, per chapter 6 of DNG
1.6) → exposure offset → look table → tone curve. Dual-illuminant profiles interpolate
between the two calibrated white points by `AsShotNeutral`; a model mismatch is rejected
outright. DCP matrices are defined on camera linear RGB, so only DNG / vendor RAW is
accepted; embedded previews and ordinary images are rejected. The vendor RAW decode path
has already applied white-balance gains in sensor space and must not apply them twice —
RAW gets the matrices only.

**A deliberate deviation**: the spec places `ProfileToneCurve` in the ProPhoto pipeline;
this version applies it in linear sRGB — per-channel curves differ between the two linear
domains only in channel ratios for saturated colors, and the existing convention is kept
so already-exported colors do not change (recorded in the `dcp.rs` module header).

### 6.4 LCP lens profiles

`crates/aevum-core/src/lcp.rs`: geometry only (distortion / lateral CA / vignetting), no
color. The data shapes come from 3633 in-the-wild samples shipped with Adobe Camera Raw;
the piecewise vignetting table (present in 551/3633 files) tracks vendor measurements
better than the polynomial (median |diff| 0.0045, max 0.13), so a table covering the frame
corner is preferred; degenerate flat tables (85 files) and tables covering only a small
radius span (7 files) fall back to the polynomial. Frame selection interpolates on a
logarithmic focal scale.

### 6.5 HDR and PQ

`crates/aevum-core/src/hdr_output.rs`: render output (sRGB-encoded values, may exceed 1) →
`srgb_to_linear_ext` (the power segment extends continuously past 1) → multiply by the
reference white to get nits → inverse PQ → 10-bit full-range codes. Three things are
pinned:

1. **Reference white = 203 cd/m2** (`hdr_output.rs::REFERENCE_WHITE_NITS`, BT.2408).
   Mapping to 100 nits makes the HDR version look one stop darker than the SDR window
   beside it; at 203 the two match in brightness and only the highlights climb.
2. **No tone-mapping roll-off.** PQ reaches 10,000 nits
   (`hdr_output.rs::PQ_PEAK_NITS`); pushing values above 1 along the curve tail is the
   whole point of this path. A homemade roll-off would decide for the user how much
   highlight to crush and would partly cancel `curve_hdr_tail`. The peak belongs to the
   display.
3. **Full range** (`-color_range pc`), not the 64–940 limited video range. Measured on one
   10-bit source: limited round-trips with a max error of 178/65535, full with 128/65535.

The PQ forward/inverse formulas run in f64 internally
(`hdr_output.rs::nits_to_pq` / `::pq_to_nits`): f32 rounding in the `Y^m1` segment wobbles
one level near the 10-bit ends.

## 7. Export

### 7.1 One chain with the preview

Stills and video share the pixel convention of `preview::render` (`Opts::FULL`), spatial
terms and local masks included, none skipped; with default parameters the output matches
the Python oracle pixel for pixel (`export.rs` module header). Geometry (straighten /
align offset / crop / framing) lives in `warp.rs`; preview and export call the same
function. Output sharpening acts on the frame **after** resize.

### 7.2 Still containers and constraints

`export.rs::StillFormat`:

| Format | Bit depth | Lossy | Usable as video intermediates | EXIF |
|---|---|---|---|---|
| PNG 8bit (`Png8`) | 8 | no | yes | yes |
| TIFF 16bit (`Tiff16`) | 16 | no | yes | no (the IFD offsets point into the whole file; the block cannot be moved in) |
| JPEG | 8 | yes (quality 1..100) | no | yes |
| WebP | 8 | no (`image` only offers VP8L lossless; quality has no effect) | no | yes |
| AVIF | 8/10 by dynamic range | yes (libaom-av1, quality → crf) | no | no (the mov muxer writes no EXIF item) |

JPEG/WebP are for stills only: an intermediate frame keeps either 8bit lossless or 16bit,
and pushing it through a lossy container compresses the image twice
(`export.rs::StillFormat::frames_ok`). AVIF is the only still container that can hold HDR
(PQ): SDR 8bit `yuv444p`, HDR 10bit `yuv444p10le` at full range; color is marked by nclx
in the container, no ICC. Criterion
`tests/suite/export_hdr.rs::pq_codes_are_actually_written_into_the_file`.

### 7.3 Container refusal for HDR stills (B3)

TIFF/PNG can declare PQ only through the ICC `curveType` 4096-point sampled table, which
mainstream viewers do not parse — the result reads as flat gray; linear 16bit instead
collides with Photoshop's default gamma interpretation of 16bit TIFF. So HDR stills go
**AVIF + Rec.2020 only**; other containers are refused up front with an explanation:
`export_hdr::hdr_pq_is_refused_by_eight_bit_containers`,
`::hdr_pq_is_refused_by_narrow_gamuts`; the panel-side coercion criterion is
`crates/aevum-ui/src/state.rs::hdr_forces_rec2020_and_avif`.

### 7.4 Final render

Encoding runs through external ffmpeg: H.264 8bit / H.265 10bit (`export.rs::Codec`). HDR
video (B2) is H.265 only and must be Rec.2020: `pipe_command` switches `-pix_fmt` between
`rgb24`/`rgb48le` by dynamic range, and the x265 VUI carries
`bt2020`/`smpte2084`/`bt2020nc`; the PNG-sequence path is refused outright (PNG has no
place to declare PQ). Criteria:
`tests/suite/export_video.rs::hdr_video_is_really_ten_bit_pq_in_the_bitstream` (encode a
real segment and read the stream info back), `::hdr_video_refuses_h264_and_narrow_gamut`,
`export::tests::pipe_bytes_per_pixel_match_the_declared_pix_fmt` (3 vs 6 bytes per pixel).

### 7.5 The output sharpening ladder (A8)

`export.rs::OutputSharpen::profile`, acting on the post-resize frame; the purpose sets the
triple and the strength only scales amount (Low/Standard/High = x0.7/1.0/1.4,
`export.rs::SharpenStrength::scale`):

| Purpose | amount | radius | thr | MTF50x | halo |
|---|---|---|---|---|---|
| screen | 0.55 | 0.6 | 0.004 | 1.096 | 0.19% |
| glossy | 0.80 | 0.9 | 0.003 | 1.161 | 0.71% |
| matte | 1.00 | 1.4 | 0.002 | 1.209 | 2.09% |

The three fields must move together (amount up, radius up, threshold down); all nine real
combinations keep halo under 3%, the tightest being matte+high at 2.93% with 0.07 points
of margin — those two numbers must not be raised. Criterion
`fit_sharpen.rs::purpose_profiles_form_a_measured_ladder`.

## 8. Parameter fitting methodology

### 8.1 The two routes

`TODO(fit)` means "this number has no basis". There are exactly two ways to clear it
(the preamble of section A in the backlog ledger):

1. **Literature value**: the number is stated in the original paper or spec, cited;
2. **Self-verifying measurement**: construct a scene with a known correct answer and
   measure the "parameter → observable quantity" mapping.

Criteria must **not depend on the reference implementation** — the golden only proves
Rust == Python; a guess written into both ends stays green forever. Typical self-verifying
targets: dehaze builds a hazy image from a known clean scene through the atmospheric
scattering model `I = J*t + A*(1−t)` (`dehaze.rs` fit module `truth_pair`) and measures
restoration PSNR plus transmission RMSE; demosaic measures directional error on synthetic
targets with known answers. Pitfalls of the targets themselves are on record: a fully
smooth transmission field makes the sweep prefer ever-larger radii, measuring the target
rather than the algorithm — so block distances must jump, and a sky block is mandatory
(otherwise the estimated airlight comes out 21% low, swamping every difference between
parameter settings).

### 8.2 The A1–A9 summary table

| # | Constant | Value | Basis | Criterion |
|---|---|---|---|---|
| A1 | DCP transmission floor `t0` | 0.1 | Literature (the DCP paper) + corner measurement: 0.03 → RMSE 0.0964, 0.1 → 0.0955, 0.3 → 0.1488 | `dehaze.rs` fit `literature_t0_sits_on_the_corner` |
| A2 | Guided-filter eps | 1e-4 | Convention 0.01 squared; plateau 1e-6..1e-4 RMSE 0.0955–0.0956, 1e-2 → 0.0978 | fit `literature_epsilon_sits_on_the_plateau` |

| A5 | Curve HDR tail slope | k*0.6 (measured 0.6033) | Four criteria: carries the input / does not amplify / slope in [0.40, 0.85] / x=4 and x=2 distinguishable | `fit_sliders.rs::curve_hdr_tail_slope_stays_in_a_usable_window` |

### 8.3 Methodological lessons (already baked into the criteria)

- **A criterion must touch the thing it pins.** The first version of the dehaze fit had
  all five negative checks green — because they only asserted "0.95 beats 0.85", which
  stayed true after the default was changed to 0.85. The correct form measures
  `DehazeTune::default()` itself (`dehaze.rs` fit
  `default_tune_matches_the_documented_values` doc).
- **Tolerances must not swallow the difference.** On 480x360 the guided radius multiples 4
  and 8 differ by a few ten-thousandths; any relative tolerance lets "default changed to
  8" slip through. The criterion became "the default must sit on the optimal plateau",
  with a resolution chosen so the difference is measurable
  (`guided_radius_multiple_sits_on_a_plateau` doc).
- **"The default sits on the optimal plateau" is more honest than "equals the minimum".**
  0.09296 vs 0.09285 (0.1%) is the same plateau; demanding equality would only force
  constants to be changed.

## 9. Known limits and explicit non-goals

1. **HDR preview is not a display simulation (B1, criterion rewritten).** An SDR panel's
   peak is white; the difference between a 203-nit reference white and a 1000-nit peak
   belongs to display hardware and software cannot fix it. Forcing it would take a fake
   tone map, deciding for the user how much highlight to crush. What can be done and is
   useful: fold the region above white into the last 10% of code values to inspect whether
   highlight layers survive (`preview.rs::FOLD_KNEE = 0.90`, `::FOLD_SOFTNESS = 1.0` — 1.0
   is set by what the output can resolve: measured x=2 lands on 0.9667 and x=4 on 0.9955;
   at a softness of 0.25, x=2 is already 0.9988 and above white collapses into flat white
   again). Everything below the knee is bit-identical. Criteria
   `fold_leaves_everything_below_the_knee_alone` and friends (preview.rs).
2. **TIFF/PNG 16bit HDR: not done (B3)**; reasons in 7.3. HDR still delivery belongs to
   EXR/DNG; TIFF in a professional chain is a fully graded SDR negative.
3. **The 45-degree demosaic limit is imposed by sampling (B4)**, not a tuning problem; see
   5.4.
4. **The built-in RAW route does not decode CRX, applies no color matrix, and does not
   touch private markers** (5.1) — closing those gaps belongs to rawler, not to guesses
   inside the built-in route.
5. **DCP `ProfileToneCurve` runs in linear sRGB** (a documented deviation from the spec,
   6.3).
6. **The grain random sequence is not aligned with numpy**: statistics and spatial
   structure only (golden ±25%).
7. **AI denoise usability assumes AVX2+FMA**: the scalar path needs about 5.7 s per net
   (`ai_denoise.rs`).
8. **Retime does no optical-flow interpolation**: shutter-weighted averaging is the
   convention; optical flow would be a different algorithm tier.
9. **HDR output adds no tone-mapping roll-off** (6.5, item 2).
10. **Hard caps** (all explicit refusals, never silent cropping): RAW files 512 MB / 40 MP
    (DNG 24 MP), HDR merge 9 frames, retime 200,000 output frames, deflicker window
    3..199 frames, per-frame correction ±3.0 EV.
11. **Known coverage gaps of the golden**: the guided-filter downsampled branch has no
    per-pixel golden, only Python-reference statistics (`develop/spatial.rs::guided` doc);
    grain is pinned by statistics only. Both are declared gaps, not omissions.

## 10. How to verify

### 10.1 The five gates

`acceptance/check.sh` (the commit gate; any red stops everything):

0. Version and documentation consistency: Cargo.toml as the single source → lock /
   README / CHANGELOG; bilingual document twins cross-linked; module-level and pub-item
   code comments bilingual (`acceptance/check_version.py`, `check_docs.py`,
   `tools/doc_lint.py`).
1. `cargo fmt --check`.
2. `cargo clippy --workspace --all-targets -- -D warnings`.
3. Full test run (`cargo test --workspace`): without ffmpeg the export cases **turn red,
   they do not skip** (12 cases used to skip silently, which is how a broken AVIF export
   survived a whole round unnoticed).
4. UI layout self-check: `aevum.exe --selftest` (headless).

### 10.2 Goldens

- The Python reference implementation lives in `acceptance/reference/` (not part of the
  build, not shipped; the exe contains no Python); the frozen goldens live in
  `acceptance/oracle/golden/`; re-freeze with
  `./.venv/Scripts/python.exe acceptance/oracle/freeze_golden.py --develop-only`; two
  consecutive freezes must be byte-identical.
- Develop main chain: three 48x64 images (hue ramp / hard edges / noisy) x parameter
  combinations, **47 cases** (`acceptance/oracle/golden/develop.json::cases`), compared
  pixel for pixel with tolerance `tests/suite/develop_golden.rs::TOL = 2/255` (1e-3 for
  purely pointwise stages); which cases participate is decided by
  `develop.rs::STAGES_READY`.
- Other goldens: deflicker (1e-4), align, crop, cube (byte-identical .cube text) and more,
  under `tests/suite/*_golden.rs`.
- The per-channel deflicker `chan_ev` in the golden is fed split as "exposure carries the
  mean + residuals carry the color difference"; matching proves the split is lossless
  (`develop_golden.rs::run_case` doc).

### 10.3 Self-verifying criteria and mutation testing

- The fitting criteria live in `tests/suite/fit_sliders.rs`, `fit_denoise.rs`,
  `fit_sharpen.rs`, `fit_sharpen_protect.rs`, and the dehaze fit module; the sweep table
  prints via `cargo test -p aevum-core --lib dehaze_sweep -- --ignored --nocapture`.
- ICC is verified by a littleCMS read-back (`AEVUM_ICC_DUMP` +
  `acceptance/oracle/check_icc.py`).
- Real sample: `tests/suite/raw_real_sample.rs` (size cross-check between routes / CFA
  structure / capability-boundary fallback / real content and determinism).
- Mutation-testing practice: changing a constant or reverting a logic branch must be
  caught by a criterion — verified examples include B5's two mutations (CFA mapping, IFD
  selection), both red; every constant in A5–A9 has its own criterion, so changing any one
  of them trips a specific red.
- Scale: the integration tests of the three crates are merged into 3 executables with
  892 criteria, none dropped (backlog C1).
