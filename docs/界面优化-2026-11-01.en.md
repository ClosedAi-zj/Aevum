## How each item was settled

### #4 Trimming the panels (done)

**Approach**: "which groups are expanded on first screen" used to be an implicit default buried in
code (`collapsed` starts empty, i.e. everything expanded). It is now an explicit registry,
`state::GROUP_SPECS`:

```rust
in_module("basic", Module::Develop, true),    // touched on every photo → expanded
in_module("curve", Module::Develop, false),   // deep work, half a screen → collapsed
in_tab("info", "info-meta", true),            // dock-page groups are grouped by page
```

**The rule**: groups that every photo and every export touch stay open; groups set once and never
revisited (camera/lens profiles, watermark, HDR/panorama merge) are collapsed. Lightroom is the
reference — open an image there and only "Basic" is expanded.

**Effect (selftest shape counts, default / fully expanded)**: develop 1144/2193, render 653/675,
sequence 555/577. Develop's first screen paints about half as much, and an eighteen-section scroll
becomes six.

**Two things done along the way**:

1. **Collapse state persists.** `settings.json` gained `collapsed: Option<Vec<String>>` —
   `None` = never expressed a preference (use the default), `Some(vec![])` = the user expanded
   everything (respect it). Writing goes through a single end-of-frame exit (`settings_dirty` →
   one write in `tick`), not file pokes from scattered call sites.
2. **Right-click a group header**: show only this group / collapse all / expand all (Lightroom's
   Solo Mode). Kept in the context menu rather than as permanent buttons — an action used once a
   week should not cost pixels. The scope is "module + dock page", so one scope never collapses
   another.

**Regression coverage**: `--selftest` now paints every module twice (default state + fully
expanded), so the default layout and the expanded layout are both pinned; `tests/suite/i18n_coverage.rs`
does the same, otherwise the text inside collapsed groups would drop out of translation
acceptance entirely.

### #8 The automatic check mechanism (done)

`crates/aevum-ui/tests/suite/ui_tokens.rs`, nine tests in three kinds:

**Pinning "one implementation per concept"**

| Test | What it catches |
| --- | --- |
| `no_floating_window_is_anchored` | `.anchor(…)` → an immovable floating window (the cause of UI-2) |
| `floating_windows_share_one_title_frame` | a new floating window that forgets `title_frame()`, falling back to square corners |
| `one_radius_for_the_whole_window` | a second `corner_radius` in `windows.rs`, or two top corners that disagree, or bottom corners that are not zeroed |
| `floating_windows_use_soft_separators` | `ui.separator()` sneaking back inside a window (a full-width rule reads as "cut here") |
| `corner_radius_arguments_are_theme_tokens` | literals like `corner_radius(3.0)`; only `0`/`0.0` (explicit square corners) are allowed |

**Pinning "the scale itself still holds"**: `radius_scale_stays_ordered` (control < container <
window) and `type_scale_stays_ordered` (small < label < body < title).

**Pinning "the feature exists and can be found"**: `appearance_entry_point_stays_in_the_top_bar` —
the gear (the only visible entry to appearance/language) is there and actually opens the window.
The lesson of UI-7: the feature was never missing, the entry point was.

**Pinning "one registry must match its call sites"**: `panel_groups_match_the_registry` — every
`group_header(…)` key in the source must be registered in `GROUP_SPECS`, and the registry must not
carry orphan keys nobody uses. Keys are strings: a typo compiles fine and fails silently (the
default collapse does not apply, the persisted key is dropped on load). This turns that into a red
test.

How it was verified: four classes of defect (anchor / missing `title_frame` / mismatched top
corners / a `separator` sneaking back) were deliberately written back into the source one at a
time; the four tests each turned red, citing the line number and the fix, and then `git checkout`
restored the source. A green run is not evidence by itself — turning red for the right reason is.

**Why colours are out of scope**: `shell/` writes `Color32` directly in 60+ places, mostly canvas
overlays (crop-box shadows, mask handles, histogram gradients) and the macOS traffic-light colours
— those are pixel-level constants, and dragging them into tokens would turn `theme.rs` into a
dumping ground. Colour is covered by the WCAG AA contrast test in `theme.rs` and by `--selftest`.

### Release checklist (do not lose this)

1. All seven items belong in the next `CHANGELOG` section. Note that gate 0
   (`acceptance/check_version.py`) requires the CHANGELOG's top section version to equal
   `Cargo.toml`, so **the section must be added together with the version bump**, not ahead of it.
2. Every panel screenshot in `scripts/shots.sh` passes `--shot-group <group>`, and that flag
   expands only the target group while the rest keep their default collapse — documentation
   screenshots will look "cleaner" than before, and different from the old ones. If one image needs
   the whole panel expanded, add an "expand all" switch to `--shot` rather than changing the
   default state.

### What is left of #2 (not done, do not forget)

- **Drag-to-reorder the three sections** of the right-hand preset bar (built-in / snapshots /
  history): the user's words were "sub-windows must be draggable", and this round fixed dragging
  for the floating windows first. Whether section reordering is wanted, and with which interaction
  (drag headers to swap, or pin one to the top), waits until the user has tried window dragging.
- Floating-window positions are remembered for the session only, not persisted. If cross-launch
  memory is wanted, store each `Area`'s position in `settings.json`.
