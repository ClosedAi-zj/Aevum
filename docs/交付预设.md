# 平台交付预设

**中文** · [English](交付预设.en.md)

导出前要填的那四个数字——画幅、帧率、编码器、质量档——是**平台口径**，不是创作参数。
本页说明内置了哪些口径、面板与 agent 怎么用、以及怎么改表（不用改代码）。

## 1. 内置口径

| key | 名称 | 画幅 | 帧率 | 编码器 | 质量档 |
|---|---|---|---|---|---|
| `douyin-vertical` | 抖音竖屏 | 1080×1920 | 30 | H.264 | CRF 20 |
| `channels-vertical` | 视频号竖屏 | 1080×1920 | 30 | H.264 | CRF 20 |
| `xiaohongshu-vertical` | 小红书竖屏 | 1080×1440 | 30 | H.264 | CRF 20 |
| `bilibili-1080p` | B 站 1080p | 1920×1080 | 保持你的节奏 | H.264 | CRF 18 |
| `bilibili-4k` | B 站 4K | 3840×2160 | 保持你的节奏 | H.265 | CRF 20 |
| `master-1080p` | 母版 1080p | 1920×1080 | 保持你的节奏 | H.265 | CRF 16 |

三条短视频平台给 `30fps`：它们确实按 30 帧分发。两条长视频口径与母版**不给帧率**——
帧率对延时摄影是创作节奏（24 帧的云和 30 帧的云不是同一种时间感），平台没有硬要求时
就不该替你决定。

数值是起点不是圣旨：平台会改口径，改的时候请编辑预设表（见第 4 节），不要改代码。

## 2. 面板里怎么用

成片面板最上面一组「平台交付」：点一下平台，画幅、帧率、编码器、质量档**一次填好**；
下面「输出」与「编码」两组里的每一项仍可逐项改。

- **高亮按数值反推**：只有当前设置与某条口径完全一致时，那个平台才亮着。改掉任何一项
  （画幅、帧率、编码器、质量档）高亮立刻熄灭——不会出现「按钮亮着、设置其实已经
  不是它」。
- 编码速度档（极速/快/均衡/慢/很慢）不参与比较：那是性能偏好，不是平台口径。
- 点「预设表…」会写出一份模板并定位到文件（首次点击时创建）。

## 3. agent（MCP）里怎么用

- 先调 `aevum_sequence_info`，返回里的 `delivery` 数组就是可用清单（key、名称、画幅、
  帧率、编码器、质量档、一句话说明）。
- 再调 `aevum_export_video`，带上 `delivery: "<key>"`。
- **显式参数优先**：同时给 `fps` / `crf` / `codec` / `preset` / `width`+`height` /
  `long_side` 时，这些值会覆盖预设——预设是省掉逐项填，不是禁止改其中一项。
- key 拼错时错误信息里直接列出可用清单，并且**在查找 ffmpeg 之前**就报出来：参数写错
  不该等一个不相干的「找不到 ffmpeg」先撞上来。

静帧导出（`aevum_export_stills`）暂不接预设：这套口径是给成片分发的。

## 4. 改表（不改代码）

位置：

```
%APPDATA%/aevum-studio/delivery-presets.toml
```

面板上点「预设表…」会写一份完整模板。格式：

```toml
# 同 key 覆盖内置项（整条替换），新 key 追加在末尾。
[[presets]]
key = "douyin-vertical"
name_cn = "抖音竖屏（我的）"
name_en = "Douyin vertical (mine)"
width = 1080
height = 1920
fps = 60.0            # 省略或删掉 = 不碰用户的帧率
codec = "h265"        # h264 / h265（也认 h.265、hevc、x265）
crf = 17
encoder_preset = "slow"   # 省略 = medium
hint_cn = "我自己的口径"
hint_en = "my own convention"

[[presets]]
key = "my-platform"
name_cn = "自用平台"
name_en = "My platform"
width = 1440
height = 1080
codec = "h264"
crf = 19
```

规则与边界：

- **改完重启生效**：预设在启动时读一次（面板每帧都画，不能每帧读盘）。
- 表读不懂时**整张退回内置**并在 stderr 喊一声，不会带半张错表跑。
- 校验：`key` 不能空、不能重复；宽高不能是 0；CRF 必须在 1~51；帧率必须为正。
- 选 H.264 的口径会**可见地**把动态范围退回 SDR——H.264 是 8bit，装不下 PQ；留一个
  按下导出才报错的组合是最坏的失败方式。

## 5. 为什么是 CRF 不是固定码率

延时摄影的画面内容变化极大（云在走、光在变），固定码率对「静止三秒 + 一道闪电」这种
镜头要么浪费要么糊。CRF 保的是质量下限，码率随内容走。

平台真正的硬约束是**体积上限**，那是另一回事。这里不把它伪装成一个码率旋钮——那会
造出一个「设了也不保证」的开关，比没有更糟。

## 6. 判据

- `delivery::tests::*`（core 单测）：内置表合法且 key 唯一；竖屏口径五个字段逐项正确
  且不动无关字段；`fps: None` 不碰节奏；文件覆盖 + 新 key 追加 + 内置项保留；坏表退回
  内置；模板能读回。
- `export_video::every_number_of_the_vertical_delivery_preset_reaches_the_render`
  （core 端到端）：命令层验 `-framerate 30` / `-c:v libx264` / `-crf 20` / `-preset medium`，
  像素层验中间帧与成片首帧都是 1080×1920。
- `tools::a_delivery_preset_is_discoverable_and_a_typo_is_reported_before_ffmpeg`
  （MCP）：清单可发现、数值对得上内置表、拼错 key 立刻报错且早于 ffmpeg 检查。
- `delivery_panel::*`（界面）：套用写对五个字段、改任意一项高亮熄灭、`fps: None` 不动
  节奏、H.264 把动态范围退回 SDR。

以上均做过定向变异（改回旧行为必红）。
