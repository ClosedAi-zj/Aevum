# 1.0.0 Acceptance checklist (Definition of Done)

[中文](1.0.0-验收清单.md) · **English**

> Frozen on 2026-10-31. Applies to `v1.0.0` (starting from `v0.5.0-beta.2`).
> This file is the **single acceptance standard** for 1.0.0. Each phase is judged solely against
> it when deciding whether to move on; the technical choices inside a phase belong to whoever
> executes it, but the criteria are never loosened to suit the implementation.

## 0. Stance

1.0 does not mean "more features" — it means **three things holding at once**:

1. **User work is not lost** — any path that could silently drop an edit, write it to the wrong
   place, or fail to save must produce a readable notice and a definite destination;
2. **Promises can be made** — the compatibility policy for the project format, presets,
   command-line arguments and the MCP tool set is written out for each, and the words "stable
   release" no longer contradict the documentation's "no promise during beta";
3. **Delivery is reproducible** — anyone who takes the tag can produce, with one command, a package
   that can be verified byte-for-byte against the published artefact, an artefact that is itself
   compliant (licences included), and version numbers that do not depend on manual syncing.

If any of those three fails, 1.0.0 does not ship.

## 3. Phases and exits

Every phase **must** satisfy: (1) its own commit (one feature, one commit — never squashed);
(2) all five steps of `acceptance/check.sh` green; (3) the evidence required above for every
blocking item in that phase; (4) team review passed. Miss any one and the next phase does not
start.

| Phase | Content | Exit |
|---|---|---|
| S1 | Freeze this checklist and make `docs/` selectively committable | This file is committed; `.gitignore` uses `docs/*` plus negation rules |
| S2 | Data safety: B2 (read-only notice), B3 (portable override diagnostics) | Both have tests; the read-only scenario is demonstrable |
| S3 | Algorithms: B1 (denoise `eps`) plus re-freezing `acceptance/oracle` in step | `fit_denoise` passes; all 47 `develop_golden` cases pass; two consecutive freezes are byte-identical |
| S4 | Delivery chain: B4 (scripted packaging + LICENSE + checksum), B5 (version consistency check), B8 (ffmpeg probe), B9 (toolchain) | One command produces the package; `sha256sum -c` passes; the gate catches version drift |
| S5 | Public documentation and promises: B6, B7, disclosure of N1-N9 | Release notes complete; Chinese and English README agree; `grep 'beta 期不承诺'` = 0 |
| S6 | Ship 1.0.0: bump, freeze, package, tag, release, fill in | The artefact downloads and its sha256 matches the local one; CI green; rollback path written in the release notes |

## 4. Per-phase gate (fixed actions)

1. `bash acceptance/check.sh` → EXIT=0 (version consistency / format / clippy `-D warnings` /
   full tests / UI self-check).
2. Any change touching numerics: record a baseline first, then change, then compare; **the
   acceptance criteria are frozen before implementation** — weakening an assertion to fit the
   implementation is not allowed.
3. Any change touching goldens: the Rust implementation, the Python reference, the golden data and
   the acceptance thresholds move **together** — all four, no exceptions; after re-freezing, run it
   a second time to confirm byte-identical output.
4. Any change touching an on-disk format (project JSON / presets): `project_roundtrip` and the old
   project regression must pass; new fields always carry `serde(default)`.
5. UI changes: any change in `--selftest` shape counts must be explained in the commit message as
   either an expected change or a regression.

## 5. Release procedure (executed in S6)

1. Green gate → `cargo build --release` → `scripts/package.sh` produces the zip plus `SHA256SUMS`.
2. **On the unzipped artefact**, run `--selftest` and one real export (`package.sh` already does
   both); the shape counts must match the build tree.
3. Bump `Cargo.toml` to `1.0.0`, syncing `Cargo.lock`, the four README positions, the new CHANGELOG
   section and the release notes.
4. Create the annotated tag `v1.0.0`, push the commits and the tag (this machine cannot reach
   `github.com:443`, so the push replays through the Git Data API; the acceptance criterion is that
   the remote sha is byte-identical to the local one).
5. Create the GitHub Release (`prerelease: false`) and upload the zip plus `SHA256SUMS`, aligning the
   API-returned `digest` with the local sha256.
6. Download the artefact and re-verify the sha256; write the result into the "acceptance data"
   section of the release notes.

## 6. Rollback

- Program: switch back to the `v0.5.0-beta.2` package; 1.0.0 changes no project directory, config
  directory or tool name.
- Project: if 1.0.0 introduces new fields they all carry `serde(default)`, so an older build loses
  only the **delta** of new fields, with no error.
- Promise: if a blocking defect is found after 1.0.0, ship `1.0.1`. Never delete a tag and never
  modify a published artefact (the artefact and the tag must correspond — beta.1 learned this the
  hard way).

## 7. Change control

- **One feature, one commit**: each blocking item gets at least one standalone commit, and the
  message states what changed, why, and how it was verified.
- The team lead reviews between phases: the diff, the evidence, and whether unrelated changes were
  smuggled in. Fail and the phase is sent back; the next one does not start.
- Stuck detection: **two attempts on the same problem in the same phase without new evidence** means
  change the approach; if the new approach also fails, reduce scope and record the unfinished item
  under §2 — labelled "not finished", never "known limitation".
