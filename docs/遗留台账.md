## A. 参数拟合债

清账方式统一：`TODO(fit)` 的意思是「这个数字没有依据」。消掉它只有两条路——

- **文献值**：原论文 / 规范里就写着这个数，标注出处，标记改成 `（文献值）`；
- **自证式测量**：构造一个已知正确答案的场景，测出「参数 → 可观测物理量」的映射，
  把「猜」变成「测过的选择」。判据必须是**不依赖参考实现**的（金标只证明 Rust ==
  Python，猜值写进两端就永远绿）。

## 2026-11-05（三）构建链：回收站每次构建后清空 · 门槛卡死归因

这一节记的是**机器事实**，不是产品行为。用户 2026-11-05 明确要求「每次构建后清理回收站」，
要求本身就说明前几轮「删了 target」是假清理。

| 项 | 记录 |
|---|---|
| 物理事实 | 这台机器上的删除在文件系统层被拦：连 `[System.IO.Directory]::Delete`（RemoveDirectoryW，文档写明永不使用回收站）都只把文件搬进 `<盘>:\$Recycle.Bin`。于是「删掉 `target`」只是换地方——2026-11-01 删 46.7 GB 后 `df` 零回升、bin 涨到 85.58 GB；2026-11-05 又攒到 **402,058 项 / 114.34 GB**，E 盘只剩 5 GB，链接器随即 `LNK1180` / `LNK1201`（「虚拟内存不足」，本质是磁盘满），门槛跑到一半卡死 |
| 接法 | 新增 `tools/purge-bin.sh`（探测盘符 → 调 `tools/empty-bin.ps1` 直删各 SID 下的 `$R`/`$I`，跳过 `S-1-5-18`；退出码恒 0，`AEVUM_SKIP_BIN_PURGE=1` 可跳过）。`acceptance/check.sh` 与 `scripts/package.sh` 都挂在 `EXIT` 上，盘符默认取仓库所在盘，`AEVUM_BIN_DRIVE` 可改。**红的那次照清**——正是跑不下去的那次 |
| 判据 | 只有一个：**`df` 见到回升**。脚本说「已删除 XX 项」不算数（2026-11-01 就信过一次，日志写回收 85 GB 而 `df` 没动）。本次实测：`empty-bin: 409,799 items deleted, 114.3 GB of payload, 0 failure(s), 193.3s`，可用空间 **5.0 → 66.9 GB（+61.9 GB）** |
| 门槛卡死的归因 | 卡在 `export_hdr::pq_codes_are_actually_written_into_the_file`：`cargo` 与 `ffmpeg` 的 CPU 累计都停在 0.0x 秒，进程在、20 分钟零输出。清完 bin 之后同一条用例 **0.11s 通过**，说明**不是代码**，是磁盘满 + 前几次被 kill 留下的进程/锁态。同时顺手堵掉一个真实隐患：`decode_rgb48` 用 `status()` 会把测试进程的 stdin 继承给子进程，ffmpeg 在非交互管道上仍会去读它 —— 补 `-nostdin` + `.stdin(Stdio::null())`（生产代码走 `Command::output()`，stdin 本来就是关的，只有测试侧这条路中招）。验证：6 条 `export_hdr` 全绿 0.09s，**没有「跳过」行**＝真的经过 ffmpeg 编码→解码→PQ 断言 |
| 教训 | 「删了」与「空间回来了」是两件事，本机尤甚。任何「腾空间」的结论都必须以 `df` 的前后差为准，脚本自报的数字只当线索 |

## 2026-11-05（九）「跟随系统」在 Windows 上真的跟随系统了

| 项 | 记录 |
|---|---|
| 现象 | 设置面板里界面语言默认是「跟随系统」（`LangPref::System` 带 `#[default]`，落盘 `settings.json` 的 `lang`，启动时 `saved.lang.resolve()`），但 `Lang::from_system()` **只读 `LC_ALL` / `LC_MESSAGES` / `LANG` 三个 Unix 风格环境变量，从不问 Windows API**。本机实测：系统 UI 语言 `zh-CN`（`Get-UICulture`、`Get-WinUserLanguageList` 均为 zh-Hans-CN），而终端里是 `LC_ALL=C.UTF-8` / `LANG=en_US.UTF-8` ⇒ 从终端启动默认**英文**；从资源管理器双击（变量不存在）回退**中文**。同一台机器两种语言，且都不等于系统语言；中文系统从终端起程序莫名变英文，英文系统双击起程序却还是中文 |
| 为什么判据没抓到 | 旧实现只在「干净环境」下被想过：注释写「Windows 上 `LANG` 常常不存在，所以再看 `LC_ALL` / `LC_MESSAGES`」，但这两个在原生 Windows 上同样基本不存在；反过来，装了 Git/MSYS 的终端会注入 `LANG`，于是在**中文开发机上恰好能测出两种相反结果**，却没人把「系统语言」当输入去断言。与今天 CI 编码、替换脚本同属「环境耦合」类 |
| 修法 | Windows 上 `GetUserDefaultUILanguage()` 拿 LANGID → `LCIDToLocaleName()` 转 BCP-47（`zh-CN` / `en-US`）→ 复用 `Lang::from_code` 的别名表；三个环境变量降为回退（非 Windows 平台与 API 失败时仍有效）。**零新依赖**（两个函数都在系统默认链接的 kernel32，内联 FFI 与 `export_bench.rs` 的 `GetProcessTimes` 同一手法）、**零硬编码语言**（加一种语言仍只改 `CATALOGS` 一行，模块头那条承诺没破）。抽 `resolve_system(系统名, 环境变量) -> Lang` 纯函数以便注入测试 |
| 判据 | ① `system_language_wins_over_shell_environment`：系统 `en-US`→EN、`zh-CN`→ZH、中文系统 + 英文 shell 变量仍 ZH、未注册的 `ja-JP` 回退中文、无系统答案时环境变量仍生效、全无信息回退中文。② `from_system_really_reads_the_windows_ui_language`：`from_system()` 的结果必须等于 `resolve_system(真实系统名, 真实环境变量)`；判据不断言系统具体是哪种语言，所以在英文 CI runner 上同样成立 |
| 变异验证 | 把 `from_system` 里 Windows 探测的结果丢掉（等价旧实现），判据 ② 当场红：`left: Lang("en") / right: Lang("zh")`——正是本机的真实组合；其余 11 条 i18n 判据保持绿。还原后全绿 |
| 编译期小坑 | 项目是 2024 edition，`extern "system" { … }` 直接报 `extern blocks must be unsafe`，要写 `unsafe extern "system"` |
| 影响面 | 英文 / 日文等系统首次启动终于按系统语言走；中文系统从终端启动不再莫名变英文。用户仍可在设置里钉死「中文 / English」，语义不变；`LangPref::System` 仍是「每次启动解析一次」 |
