# 分发与更新

**中文** · [English](分发与更新.en.md)

程序怎么发到用户手上、用户怎么升到下一版、这一路上有哪几道检查。一页纸，写完现状、
三条路、信任链、签名的成本，最后是明确还没做的部分。

## 1. 现状：一条路

`scripts/package.sh` 跑完，`dist/` 下只有两样东西：

```
dist/aevum/                                       绿色包解压出来的树
dist/Aevum-Studio-vX.Y.Z-windows-x64.zip          用户下载的就是它
dist/SHA256SUMS                                   <64 位十六进制>  <zip 文件名>
```

`SHA256SUMS` 只有一行，就是那个 zip。格式与 `sha256sum -c` 一致，用户拿到后自己就能验：

```bash
sha256sum -c SHA256SUMS
```

这条路的优点是不需要任何服务端：没有安装器、没有注册表、没有管理员权限。缺点同样明显
——用户得自己知道「有新版本了」，而且升级 = 手动解压覆盖。

**v1.9.6 起，这个包不再只由一台机器产出**：推 `vX.Y.Z` tag 会触发
`.github/workflows/release.yml`，在干净的 `windows-latest` 上跑**同一个**
`scripts/package.sh`（六关 + release 构建 + 自检 + 真实导出 + zip + 解压回验），把 zip 与
`SHA256SUMS` 直接发成 GitHub Release，再回读 API 核对 `draft=false`、资产 `state=uploaded`
与 `digest` 是否等于本地 sha256。`workflow_dispatch` 可在打 tag 之前手动跑同一条链，只传
artifact、不发 Release。`acceptance/check_release.py`（第 0 关 R1–R9）盯住的是「CI 没有
偷偷变成另一条链」。随包 ffmpeg 不进版本库：CI 从固定 tag 的 7.1 essentials 构建下载，
对**真正进包的那个 exe** 做 sha256 校验——上游没发布 zip 的 checksum，GitHub 的 asset
digest 也是空的，所以校验的是被分发的字节本身。

**下一版发版注意**：v1.9.6 的 tag run 用的是改严之前的 `--verify`（API 未返回 digest 时只打印
跳过、仍返回 0）；现在的版本要求 digest 必须存在且等于本地 sha256，并额外断言 `tag_name`，
至今还没在真实 tag 发布流程里跑过。模拟 `v1.9.7` 的 API JSON（含 `tag_name` 与两资产 `digest`）
已验证不会被新断言误卡，但 `release.yml` 是 `gh release create` 之后立即 `gh api` 回读，
GitHub 是否在那一个瞬间就算好 asset digest，本机无法复现。下一次打真 tag 时留意 `--verify` 的
首次回读；若即时响应偶发不带 digest，正确做法是在 workflow 里对 `gh api` 加一次带退避的重读，
**不要放宽 `verify()`**——跳过未验过的字节对账，正是这一轮修掉的弱失败。

## 2. 三条路，各管一段

| | 绿色包（zip） | 安装器（`scripts/install/aevum.iss`） | 内置更新器（`crates/aevum-core/src/update.rs`） |
|---|---|---|---|
| 解决什么 | 单机、免安装、可放 U 盘 | 开始菜单能找到、`/SILENT` 批量部署、卸载知道该删什么 | 用户不用自己去发布页看 |
| 谁需要 | 工作站、临时机器、审查用 | 机房、培训班、公司统一部署 | 长期使用的个人用户 |
| 需要管理员 | 否 | 默认是（可 `/CURRENTUSER`） | 否（装在用户目录时） |
| 状态 | **已在用** | 脚本已就绪，**未在真机出过包** | **已接线**（v1.9.2：菜单「检查更新…」+ 启动静默检查 + 更新/回滚窗口；v1.9.3 真机八场景联调，见 §6.2） |

三条路装出来的**是同一个程序**：同一个 `aevum.exe` 与同一个 `tools/ffmpeg.exe`。
安装器不写「只有安装版才有的功能」，更新器也不假设自己跑在安装版上（它只关心
「新 exe 从哪来、目标 exe 在哪」）。

内置更新器的形状值得单独说一句：它**没有引入任何 HTTP 客户端**。下载走系统自带的
`curl.exe`（Windows 10 1803+），找不到就退到 `powershell -NoProfile -Command
Invoke-WebRequest`，两条都没有时明确报「本机没有可用的下载通道」并给出手动下载地址——
不静默失败。这样离线构建、依赖审计都不用为一个「检查更新」多背一个 TLS 栈。

## 3. 信任链

一条更新请求要过五道，任何一道不过就停下：

1. **HTTPS**：`curl -fsSL` 与 `Invoke-WebRequest` 都走系统证书库；`-f` 让 404 变成非零
   退出码，否则一份 404 的 HTML 会被当成「下载成功」写进 exe。
2. **标签必须是三段版本号**：`v1.8` / `v1.8.0-beta` 一律不认。比较是**数值**比较
   （`1.10.0 > 1.9.0`），不是字符串比较——按字节比 `"1.10.0" < "1.9.0"`，用户会永远
   收不到 1.10 之后的更新。
3. **资产按后缀挑**：`windows-x64.zip`。挑不到就报「没有匹配当前平台的资产」，不猜。
4. **SHA256SUMS 比对**：清单里**没有这一行也算失败**。把「找不到」当成「不用校验」是
   这类代码最常见的漏洞。
5. **签名（已拍板不做）**：见下一节；这一道在当前发布链里不存在，前四道就是全部。

要诚实说清第 4 道的边界：清单和 zip 来自**同一个地址**，所以它证明的是「传输没坏、
镜像没偷偷改」，**不能**证明「发布者没被冒名」。真正的身份保证只能靠代码签名——那是
唯一一条「你不需要信任下载地址，只需要信任证书」的链路。本项目是 MIT 开源、给摄影
爱好者的免费工具、仅供学习与个人使用、零预算，因此这个缺口是**明确的取舍，不是待办**。

## 4. 签名：成本与三个选项

`scripts/sign.ps1` 是接入点，**默认不阻断打包**：没有证书时打印一行说明并 `exit 0`，
产物照出；只有「配了证书但签失败」才返回非零。签名一律 SHA256 + RFC3161 时间戳——
没有时间戳，证书一过期，**所有已经发出去的旧版本**都会变成「签名已过期」，而二进制一个
字节没变。

| 选项 | 成本 | SmartScreen | 适用 |
|---|---|---|---|
| **不签** | 0 | 前几百次下载会被提示「未知发布者」，累积声誉后缓解 | 现在就属于这一档 |
| **自签**（自建根证书） | 0（自己生成） | 对公网用户**几乎无改善**；只有把根证书装进信任存储的机器才认 | 内网批量部署 |
| **Azure Trusted Signing** | 约 $9.99/月 | 需要可验证的组织身份；通过后提示消失 | 面向公众发布的正经选择 |

结论（2026-11-05 拍板）：**不买证书、不做签名**。本项目是 MIT 开源、给摄影爱好者的免费
工具，仅供学习与个人使用，零预算；上表保留三个选项只是把成本写清楚，不是待办清单。
开源免费路径（SignPath Foundation）要求二进制来自仓库自动构建且每版人工批准——自动构建
这一半已由 `release.yml` 满足，但每版人工批准对学习用途仍不划算，搁置。签名之前能做的
两件免费事已经做完：`SHA256SUMS` 随 Release 上传（CI 发布时强制对账），发布页固定在
仓库的 Releases 页。

## 5. 怎么跑

```bash
# 绿色包（含 zip 与 SHA256SUMS，最后会解压回验一遍）
scripts/package.sh

# CI 发布：推 tag 即构建并发布；发布说明由 scripts/release_body.py 从 CHANGELOG.md 生成
git tag vX.Y.Z && git push origin vX.Y.Z
# 打 tag 之前可先在 Actions 手动跑 workflow_dispatch 验整条链（只出 artifact，不发 Release）

# 安装器（需 Inno Setup 6 的 iscc；版本号从 Cargo.toml 之外显式传）
iscc /DMyAppVersion=X.Y.Z scripts/install/aevum.iss
# → dist/installer/Aevum-Studio-X.Y.Z-setup.exe

# 签名（可选；没证书就跳过一次说明）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sign.ps1 -Path dist/aevum
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sign.ps1 -Path dist/installer
```

安装器的静默参数：`Aevum-Studio-X.Y.Z-setup.exe /SILENT /NORESTART`，彻底无界面用
`/VERYSILENT`。静默卸载时**一律保留** `%APPDATA%\aevum-studio`（没人能回答那个对话框，
而误删配置不可恢复）；交互卸载时会问一次。

## 6. 还差什么

### 6.1 已接线（v1.9.2）

`update.rs` 的纯逻辑以前没有任何调用方，现在界面上有一整条路：

- **帮助 → 检查更新…**：打开更新窗口并立即检查一次；查到可装的版本时，菜单项本身
  变成「有新版本 vX.Y.Z…」。
- **启动静默检查**：每个进程一次，距上次检查超过 24 小时才会真的联网；失败不弹窗、
  不打断，只在更新窗口里留一行原因。
- **更新窗口**：当前版本 / 远端版本 / 发布说明 / 真实字节进度 / 「立即重启并安装」。
  下载、校验、解包、写替换脚本全在后台线程，界面线程一秒都不阻塞；「备好」之后才让
  用户点重启——中途失败（断网、校验不过、杀软锁文件）都能看见并留在原地。
- **回滚**：安装脚本不再删 `*.old`；程序旁边有它时，帮助菜单出现「回滚到上一版…」，
  二次确认后把当前版本挪成 `*.failed`（留证据）、把 `*.old` 搬回来并重启。

### 6.2 真机联调：已经真跑过一遍（2026-11-05）

`crates/aevum-core/examples/update_e2e.rs` 是这条链的联调工具。它对着一个**本地假发布**
（`python -m http.server` + `tar.exe` 打的 zip + 真实 `SHA256SUMS` + 一份 GitHub 形状的
`latest` JSON）把 检查 → 下载 → 校验 → 解包 → 替换 → 回滚 走完，安装目录特意放在带空格
与中文的路径下（`E:\tmp\upd-e2e\install\恒晷 程序\`）。

```bash
# 四个模式：install（默认）/ prepare / rollback / locked
E2E_API=http://127.0.0.1:8788/latest \
E2E_TARGET='E:\tmp\upd-e2e\install\恒晷 程序\aevum.exe' \
E2E_WORK='E:\tmp\upd-e2e\work' \
cargo run -p aevum-core --example update_e2e
```

跑出来的结果（每一行都是字节级核对过的）：

| 场景 | 结果 |
|---|---|
| 启动静默检查（真实 exe + 本地服务） | `settings.json` 落下 `last_update_check`，服务端收到 `GET /latest 200` |
| 下载进度 | 真实字节回调（0 → 23,740,830），落盘大小与发布声明相等 |
| 校验 | 清单从 HTTP 取，`verify` 通过；清单与包不匹配时停住 |
| 解包挑文件 | 包里同时有 `aevum.exe` 与 `tools/ffmpeg.exe`，挑到**同名**那个 |
| 替换 | 目标变成新版（sha256 逐字节相等），`.old` 留旧版，脚本自删 |
| 等待 | 程序还开着时不动手：4 秒后目标仍是旧版、无 `.old`；程序退出后 1 秒内完成替换 |
| 回滚 | 目标回到旧版，`.failed` 留新版，脚本自删 |
| 被占用 | `share_mode(0)` 锁住新 exe → 十五次重试 → 把 `.old` 搬回去（用户仍有可用版本） |

**这一步抓到两个真 bug**（都不是判据能发现的，判据当时全绿）：

1. **批处理正文里的中文路径会变成乱码。** `cmd` 按 OEM 代码页（中文系统 936）解码
   `.cmd`，而 Rust 写文件是 UTF-8：安装路径里只要有一个汉字（`D:\软件\...`、
   `C:\Users\张三\...`），`if exist` 与 `move` 全部落空，错误又被 `>NUL` 吞掉——用户看到
   的是「点了更新，什么都没发生」，十五次重试后静默回滚。隔离实验：同一份脚本存 UTF-8
   时输出 `MISSING`，用 `iconv` 转成 GBK 后同一份内容输出 `FOUND`。
   修法：**路径一个都不写进正文**，全部当命令行参数传（`%~1`/`%~2`/`%~3`，命令行是
   UTF-16，不受代码页影响），正文保持纯 ASCII。
2. **`tasklist | find` 依赖 PATH。** PATH 上有一个 Unix 版 `find`（开发者装了 Git/MSYS，
   或者从 Git Bash 里启动本程序）时，`find /I` 直接报 `No such file or directory`，等待
   循环立刻失效——程序还开着就开始替换。修法：系统工具一律写
   `%SystemRoot%\System32\...` 的绝对路径（`tasklist` / `find` / `ping` 三个都换）。

**还没覆盖**：`C:\Program Files` 的 UAC 提权（本机测试目录不在受保护位置）、真实杀软
（用 `share_mode(0)` 模拟了「被占用」）、Authenticode 签名（已拍板不做）。真 GitHub 发布
自 v1.9.6 起由 `release.yml` 覆盖（见 §1）；该项已于 2026-11-05 在 `docs/遗留台账.md` 末节记为关闭。签名的成本与三个选项见 §4。

### 6.3 还没做（都需要外部条件，不是写代码能关的）

- **真实签名：已拍板不做**（不是待办）。项目是 MIT 开源、摄影爱好者用的免费工具、
  仅供学习与个人使用、零预算；不买证书、不做 Authenticode。首次下载被 SmartScreen
  标成「未知发布者」属已知且接受的后果，`sign.ps1` 保留为「若将来有人自愿承担成本」
  的接入点，默认仍是打印一行说明并 `exit 0`。
- **真 GitHub 发布的 CI 路径**：v1.9.6 起已由 `release.yml` 覆盖（tag → 构建 → 发布 →
  回读对账）；§6.2 那次本地假发布联调仍是不可替代的真机行为验证，两者不互相替代。
- **更新范围**：更新器只换 `aevum.exe`，不换 `tools/ffmpeg.exe`、`licenses/`、
  `third-party-src/`。ffmpeg 升级要走整包或安装器——这是有意的：替换一整个目录树在
  文件被占用时的失败模式远比换一个 exe 复杂，收益不足以在这一版承担。
- **`.aevum` 后缀关联**：没有做，因为工程文件不是「一个带扩展名的文件」，而是每个序列
  目录里的 `<序列根>/.aevum/project.json`。`.aevum` 是目录名，Windows 没有「双击目录用
  某程序打开」的机制；要做关联得先有单文件工程格式。
