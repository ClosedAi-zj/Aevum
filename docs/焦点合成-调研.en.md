# Focus Stacking: Research and Selection

> 中文版：[焦点合成-调研.md](焦点合成-调研.md) · Date: 2026-11-02 · Status: **confirmed and implemented** (implementation record in section 5)

This document answers three questions: how Helicon Focus 8 works (reverse-engineering
evidence), how the open-source tools work (ideas only, clean-room), and what Aevum should
do (a selection proposal). **It records facts and plans only; no implementation code has
been written. Implementation starts after confirmation.**

---

## 1. Helicon Focus 8 reverse-engineering conclusions

Target: `D:\app\Helicon Focus 8\_HeliconFocus.exe` (22.7 MB, PE x86_64, Qt application,
sha256 `b7e4d68f...f58eca`). Evidence grades follow the ps-lr clean-room rules:
E1 = decompilation, E2 = struct/parameter metadata, E3 = names/docs.

RE chain: REA 6.8.0 + Ghidra 12.1.4 (installed to `E:/code/ps-lr/.tools/` for this
research; 12.2 is rejected by REA's version gate). The exe has no retained symbols, so
deep decompilation pays poorly; string evidence, embedded OpenCL metadata and the official
help file were enough to pin the algorithm taxonomy.

### 1.1 Method taxonomy (E2/E3, solid)

| Official name | Internal settings key | Algorithm family |
|---|---|---|
| Method A (weighted average) | `FocusParameters.Method_A` | weighted average |
| Method B (depth map) | `FocusParameters.Method_B` (plus `Method_B_(legacy)`) | depth map |
| Method C (pyramid) | `FocusParameters.Method_C` | pyramid |

### 1.2 GPU pipeline (E2, embedded OpenCL metadata)

The exe embeds **pre-compiled AMD GFX8 kernels** (Code Object V3, built with clang 3.9);
the kernel symbol names (`__OpenCL_*_kernel`) expose the pipeline structure directly:

- **Weighted average**: `convert_rgb_to_gray16` (16-bit grayscale measure) ->
  `stack_first_pass` / `stack_second_pass` / `stack_weighted_average` /
  `get_results_weighted_average` (two passes + weighted average) ->
  `calc_difference` / `calculate_difference_batch`
- **Pyramid**: `fast_downsize_by2` (halving per level) -> `horizontal_blur` /
  `vertical_blur` (separable blur, weighted variants too) ->
  `collapse_pyramid_{1x16,3x16,4x32}` (three block widths) ->
  `pyramid_stacking_combine` -> `apply_feathering` (feather table)
- **Depth map**: `calc_differencial_layers` / `draw_differencial_image` / `ApplyDeformations`
- **Common**: `get_histogram`, `calculate_total_brightness`, `extract_channel`,
  `FillMarginsWithPureBlack`

### 1.3 Alignment subsystem (E2, kernel argument reflection metadata)

The alignment kernel argument tables leaked as a continuous field-name string:

- **Grid deformation alignment**: `canvas/canvas_info`, `detectrect`,
  `npoints_x/npoints_y` (grid points), `stepx/stepy` (grid step), `varations`
  (candidate deformations per point), `deform_number`, `results/sum_cache` (score cache)
- **Measure**: `histogram_size`, `global_histogram`, `local_histogram` (alignment scoring
  uses **histograms**, global + local), `brightness_factor_1024`
- **Pyramid parameters**: `number_of_layers`, `feather_table`
- **Deformation kernel**: `curve/curve_size`, `border_width`, `radius`, `f`, `k1`,
  `k1weights` (f/k1 are probably lens distortion parameters — unverified)

Settings serialization keys (E2): `Radius`, `Smoothing`, `smoothing_gamma`,
`smoothing_gamma_size`, `opacity_filter`, `best_plane_info`, `pixel_sum(_info)`.

### 1.4 Official documentation wording (E3, `Help/english/HeliconFocus.html`)

- Method A: weighted average with a **Radius** parameter (analysis area around each
  pixel); preferred for smooth, low-noise scenes
- Method B: depth map with **Radius** + **Hardness** + smoothing
- Method C: pyramid, strongest contrast wins; best detail, highest noise/colour-shift risk
- Alignment interpolation setting: "Interpolation is used to preserve details during
  alignment process. The slower, the better"

### 1.5 Unverified items (honest boundaries)

- The exact weight formula shapes (A's Gaussian window, B's hardness mapping) — needs E1
  decompilation, not done (stripped exe, poor payoff; implementation may not copy anyway)
- Whether `f/k1` is distortion correction — unverified
- The exact depth-map smoothing kernel size — the docs only say "smoothing of the depth map"

## 2. Open-source comparison

| Tool | License | Algorithm | Alignment | Quality | Performance |
|---|---|---|---|---|---|
| **focus-stack** (PetteriAimonen) | **MIT** | Forster complex-wavelet DWT fusion (the extended-DOF classic); optional depth-map PNG output | OpenCV `findTransformECC` (neighbour chaining, <=2048 px pre-alignment) | batch consistency filter (consistency 0-2); depth map threshold/smooth-xy/smooth-z/halo-radius tunable | optional OpenCL; batched merge (batchsize 8), ~100 MB RAM per megapixel |
| **enfuse** (Enblend family) | **GPL-2.0+** | Mertens-Kautz-Van Reeth exposure fusion + Burt-Adelson Laplacian pyramid blending; contrast measure is a **local standard deviation** (docs explicitly say it beats the paper's Laplacian for defocused images) | **none** (needs external align_image_stack) | flexible weighting criteria but not focus-stacking-specific; `--hard-mask` exists for focus stacks | tunable pyramid levels, memory hungry |
| **Zerene Stacker** | closed source | PMax (pyramid max contrast) / DMap (depth map + contrast threshold slider + Estimation/Smoothing Radius) | built in (with parallax correction) | industry benchmark; PMax strong on complex geometry but prone to inversion halos/noise/colour shift; DMap preserves colour and smoothness but struggles with complex geometry | proprietary |
| ppsp and similar pipelines | various | align + enfuse wrappers | align_image_stack | compositional | — |

**Community consensus** (long threads on photomacrography, with Rik Littlefield
participating personally):

1. Pyramid methods (PMax / Helicon C) are strongest on **complex overlapping geometry**
   (hairs, crossing bristles) but prone to "inversion halos", noise gain and colour shift —
   an inherent information-leak property of pyramid decompositions;
2. Depth-map methods (DMap / Helicon B) **preserve colour and smoothness** best, but
   featureless flat areas need a contrast threshold to be judged as noise, or they blotch;
   weak on complex overlapping geometry;
3. Top-quality workflow: render with both methods and retouch by hand to take the best of each;
4. Featureless regions (watch faces, sky) are the shared blind spot of every
   measure-driven method — a focus measure only means something where texture exists.

## 3. Selection proposal (confirmed)

### 3.1 Algorithms: **depth map as primary, weighted average as fast path, pyramid deferred**

| Priority | Method | Benchmarked against | Rationale |
|---|---|---|---|
| **P0 depth map** | per-pixel focus measure -> argmax depth map -> threshold featureless areas -> xy/z smoothing -> pick source frame per pixel with feathered transitions | Helicon B / Zerene DMap | the quality ceiling closest to the commercial benchmark; preserves colour (no pyramid reconstruction, no colour/contrast drift); **best testability** (the depth map is a directly assertable intermediate); same shape as Aevum's existing "owner fallback" idea |
| **P1 weighted average** | 16-bit grayscale measure -> cross-frame normalized weights -> direct blend | Helicon A | simplest to build; good quality on low-noise stacks; cross-checks the depth map |
| P2 pyramid | Laplacian pyramid picking max contrast per level | Helicon C / PMax | strongest on complex geometry but inversion halos and colour drift make golden tests hard; add after P0/P1 stabilize |

Key algorithm decisions (designed independently, informed by the Helicon evidence):

- **Measure**: modified Laplacian (`|2I-I(x-1)-I(x+1)|+|2I-I(y-1)-I(y+1)|`) or Tenengrad
  (Sobel squared), computed on 16-bit grayscale with a tunable radius (Helicon's Radius);
  Gaussian pre-smoothing of the measure map suppresses noise
- **Featureless fallback**: below a measure peak threshold the region takes the
  **reference frame** (sequence median frame by default, or user-specified), which
  eliminates DMap blotching — the same idea as Aevum's deghost owner fallback
- **Depth-map smoothing**: xy Gaussian (tunable radius, Helicon's smoothing) + z (frame
  index) median filtering against jumps; transition bands feathered by depth difference
  (Hardness inverted: feather width inversely proportional to adjacent depth difference)
- **Halo suppression**: morphological opening on the depth map to remove isolated depth
  points (Helicon's halo-radius)

### 3.2 Alignment: **reuse Aevum's existing alignment, grid deformation as an upgrade path**

- Focus stacks need the same alignment as time blending (frame shifts, focus breathing);
  Aevum already has a frame alignment pipeline (`warp::transform_into`) — reuse it first;
- Helicon uses **grid deformation** (an npoints grid, per-point candidate deformations,
  histogram scoring), far more accurate than a global affine for focus breathing —
  a P1 upgrade: add a mesh warp on top of the existing warp, scored by block histogram
  differences.

### 3.3 Processing flow (wired into the existing pipeline)

```
MergeKind::Focus (new) -> run_merge_job decode loop (reused, full resolution + RAW)
  -> alignment (reuse warp pipeline; grid deformation at P1)
  -> focus measure (16-bit grayscale, per frame)
  -> depth map (argmax + threshold + smoothing + feathering) <- assertable intermediate
  -> blend by map (P0 per-pixel source selection with feathering / P1 weighted)
  -> write (same encoding as write_single_still: no transfer change)
Preview: reuse the B8 half-resolution cache pattern (unchanged frames only redo the blend)
```

Parameters (benchmarked against Helicon's knobs, serde defaults for zero breakage):
`focus_radius` (measure radius), `focus_threshold` (featureless threshold, 0 = off),
`focus_smooth_xy`, `focus_smooth_z`, `focus_feather` (inverse of Hardness),
`focus_method` (depthmap|weighted). The `focus.merge` MCP command joins the catalog
(no. 77, four-way sync as usual).

### 3.4 Performance considerations

- Measure and blending are per-pixel independent and naturally tileable/streamable;
  alignment is the only full-frame-resident stage — same shape as timeblend, memory is
  controllable
- The depth map is a small single-channel product; preview can run the measure at 1/4
  resolution and upsample
- No GPU (OpenCL) for now: Helicon needs it for second-level responsiveness in a product;
  Aevum first guarantees a numerically correct CPU path with golden regression, GPU stays
  a later accelerator
- Deep stacks (>100 frames) merge in batches: per-batch depth maps fused afterwards,
  following focus-stack's batchsize idea

### 3.5 Licences and clean-room constraints

- focus-stack is **MIT** (ideas may be referenced; no code is copied — this project never
  copies external code anyway)
- enfuse is **GPL-2.0+**: only the publicly documented ideas are referenced, **its source
  is not read**, avoiding GPL contamination
- All Helicon evidence follows the ps-lr rules: facts only (structures/fields/order/
  constants); the implementation is an independent rewrite

## 4. Acceptance outline (draft, confirm before implementation)

1. Depth-map test: a three-frame composite (foreground/midground/background textures)
   asserts the depth map assigns each region to the frame holding the sharp texture;
   **negative check**: with a flat measure the depth map must degenerate to the reference frame
2. Featureless-area test: a flat gradient background shows no blotching (fallback in effect)
3. Feathering test: transition luminance is monotonic with no steps ("no step at the seam
   for a 5% depth error")
4. Weighted-average test: two frames differing in exactly one textured region — the weight
   concentrates on the sharp frame and the output matches that region point by point
5. End-to-end: same shape as the existing merge tests (real small sequence export +
   pixel-level assertions)

## 5. Implementation record (landed 2026-11-02)

Built as the P0 plan in section 3, in three commits: `21a3924` (core algorithm), `8bc61dc`
(merge pipeline and command no. 77), `cfb3488` (panel and end-to-end evidence).

**Where the implementation pinned down what the survey left open**:

- `smooth_z` landed as the **depth-map mode-filter radius** (despeckle) and `feather` as the
  **Gaussian feather radius on the selection masks**. The survey's "xy/z smoothing" is
  conceptually these two things: one removes speckle, the other handles transitions.
- `threshold` is expressed as a **percentile of the per-image best measure** (0-100), not an
  absolute value -- it transfers across sequences, exactly the convention of DMap's contrast
  slider; 0 = fallback off.
- The reference frame is the **sequence's middle frame** (`count / 2`), matching time blending.
- The measure runs on gamma-2.0 luma (the square root of linear): defocus is a spatial
  property of the lens, but the measure should track perceived contrast, and linear luma
  crushes dark textures out of proportion.
- The pyramid (P2) is deferred as recommended; no GPU (OpenCL) either -- the CPU path is kept
  numerically correct with golden regression first.

**Evidence list** (5 core + 1 end-to-end, all with negative checks):

| Evidence | What it proves | Negative check |
|---|---|---|
| `the_depth_map_assigns_each_region_to_the_frame_holding_the_sharp_texture` | region ownership across three thirds | with everything defocused the output must stay blurry (no inventing sharpness) |
| `a_featureless_field_falls_back_to_the_reference_frame` | flat areas fall back to the reference | with the fallback off, flat areas must follow the noisy argmax |
| `feathering_blends_across_depth_jumps_without_a_step` | cross-seam samples sit between the frames | away from the seam, feathering must not change values (point-wise equal to the hard cut) |
| `weighted_average_concentrates_weight_on_the_sharp_frame` | textured region ~ the sharp frame; flat region falls back | the textured region must not be the mushy two-frame average |
| `degenerate_inputs_are_handled` | empty / zero size / size mismatch / single frame / parameter bounds | -- |
| `focus_merge_takes_each_band_from_the_frame_that_holds_the_texture` (UI end to end) | a real exported sequence takes each band from the right frame | a 100th-percentile fallback returns the whole image to the reference; unknown method and missing confirm are refused before a job starts |

**Known boundaries**: ownership of the one or two rows straddling a seam is affected by the
measure window reaching into the neighbour (`radius + smooth_z`) -- a property of the method,
not a defect; the 32-frame cap assumes every frame is resident, so deeper stacks fuse in passes.

### Corrections from the pre-1.4.0 audit (2026-11-02)

The survey's conclusions hold; three things needed correcting once the code existed:

1. **`focus.merge` frames on `start`, not `center`.** The contract table said `center?+around?`
   ("current frame +/- 7") while the implementation always meant "eight frames from a start
   index" -- passing `center` per the schema never did anything. 1.4.0 renames the contract to
   `start?+around?` and leaves the implementation alone. Section 3's "take N either side of the
   current frame" reads as `start` for the same reason.
2. **The memory figure is measured, not estimated.** The survey guessed about 2.3 GB for 32
   frames at 24MP; the measurement is about **9.6 GB** (`frames x pixels x 12 B + three output
   planes`). Computing the ownership map on the fly brought the peak down by an order of
   magnitude, but the 32-frame cap still assumes every frame is resident -- it was not raised.
3. **The headless control plane now has it.** `aevum_focus_merge` is direct tool no. 35 and
   calls straight into `focus.merge`. A headless session has no "current frame", so omitting
   `start` takes eight frames from the sequence's middle frame.

**Not implemented in this round** (still open): pyramid fusion (P2 in section 3) and the GPU
(OpenCL) path; the panel has no depth-map preview either -- the `depth_map` entry point exists
and the tests assert on it, but the UI shows no per-pixel ownership.


### T10 measurement: pyramid vs weighted (2026-11-03)

The first landing carried "2-3x" and "about 1.0 GB" as order-of-magnitude notes in
`pyramid.rs`'s module header, flagged "T10 replaces these with measured numbers". T10 is this
section: **both figures were estimates, and both were wrong**, so here are measurements.

**How it was measured** (reproducible by anyone):

- Material: the four real PANA 6000x4000 samples in `samples/cameras/` (`PANA0001.RW2` /
  `PANA0450.RW2` / `PANA1631.RW2` / `PANA0198.JPG`), cycled up to **eight frames**. Frame
  count drives memory and time; **content does not** -- fusion is per-pixel work, so once the
  pixel count is fixed the cost is fixed.
- Build: `cargo build --release`, `opt-level = 3`.
- Machine: i5-12600KF (16 logical cores) / 31.8 GB RAM / Windows 10.0.26200 / rustc 1.98.0.
- Peak memory: the process's own `PeakWorkingSetSize` (`GetProcessMemoryInfo`). **One process
  per method** -- the peak is a monotonic per-process high-water mark, so running both methods
  in one process would charge the second one with the first one's peak.
- Wall clock: brackets only the fusion call itself (`focus::focus_stack` /
  `pyramid::fuse_pyramid`), decoding excluded.
- **Median of three runs** per method; the spread across all six runs was under 1%.
- The eight input frames alone stay resident at **2.32 GB** (8 x 288 MB plus decoder slack),
  so besides "process peak" there is a "fusion delta" column = peak minus what was resident
  before fusion started. That delta is the method's own cost.

| Method | Wall clock | Process peak | Fusion delta | Levels |
|---|---|---|---|---|
| Weighted | **1.95 s** | 2.88 GB | 732 MB | -- |
| Pyramid (before) | **29.7 s** | 4.43 GB | **2.10 GB** | 6 (`levels = auto`) |
| Pyramid (after) | **24.4 s** | 4.43 GB | **2.10 GB** | 6 (`levels = auto`) |
| Ratio (after / Weighted) | **12.5x** | 1.54x | **2.9x** | -- |

The Weighted baseline jitters between sessions (the pre-optimisation round measured
1.97 s / 3.19 GB / 864 MB; the same-protocol re-run after optimisation measured
1.95 s / 2.88 GB / 732 MB). Ratios are always computed against the **same-session** baseline.

`levels = auto` at 24 MP is `clamp(floor(log2(4000/32)), 3, 8)` = **6**.

**Where the estimates went wrong**:

1. **Memory was off by more than 2x.** The old arithmetic only counted "output tower 384 MB +
   weight tower 128 MB, about 1.0 GB". It forgot Pass A's two full-resolution single-channel
   `best` / `gate` planes (96 MB each), the mask tower (128 MB), the per-frame measure plane
   (96 MB) and the current frame's Laplacian (288 MB). Add those back and 2.1 GB falls out.
2. **The wall clock is 12-15x, not 2-3x.** At first this was attributed to
   `focus::measure_plane` running **twice** per frame -- that attribution was **half refuted**
   by the optimisation round below.

**One optimisation round (2026-11-03, done under assertion cover)**:

1. `focus::measure_peak`: the modified Laplacian is computed **once** per frame per level,
   taking the per-pixel max across frames before one box average; Pass A's percentile cut is
   estimated from the subsampled peaks. At `t = 0` this is pixel-for-pixel identical to the old
   path (regression round 4 measured 49152/49152 pixels, max|Δ| = 0 on the 128x128 fixture);
   at `t > 0` it is **no longer equivalent** -- `box(max ml)` and `max(box ml)` do not commute
   and the percentile cut is drawn from a different distribution: when the texture scale is
   comparable to the box window (radius = 2) the difference is material (block-texture fixture,
   threshold = 25: 65% of pixels differ, max|Δ| = 0.23); for textures finer than the window it
   tends to zero. The pyramid assertions P-C1..P-C6 pin the new path's own behaviour;
   `measure_peak`'s box-average window semantics currently have **no assertion anchor**
   (mutating the radius to 0 keeps all six green) and are recorded as open in the ledger.
2. `reduce` rewritten as a separable streaming row pass with a ring buffer, removing two
   `collect()` heap allocations per output pixel.
3. Pass B's weight planes switched from `.clone()` to `Cow::Borrowed`, saving one 128 MB
   pure copy per frame per level.

Result: **29.7 s -> 24.4 s (−18%), peak memory and fusion delta untouched**. Two lessons.
First, collapsing the measure from two passes to one only saved 18% -- the bulk of the 15x was
never the measure computation but the tower's own per-level reduce / expand / collapse and
per-pixel blending, i.e. memory-bandwidth work. Second, `Cow` removes transient copy-time
allocations but never touches the resident baseline of the `best` / `gate` planes and the mask
tower, which is why the peak did not move. Going further means changing the algorithm's
structure (fewer levels, blocked processing, threading) and is out of scope for this round.

**What this means for users**: at 24 MP x 8 frames, pyramid is an order of magnitude slower
and takes more than twice the memory of weighted, in exchange for suppressing low-frequency
halos. The default therefore stays depth-map / weighted; pyramid is the choice for "there are
halos and I can wait twenty-odd seconds", and the panel's hover text says exactly that.
