# Rename & Version Reset Handbook

[中文](改名与版本重置.md) · **English**

When the app gets renamed (new name TBD), [`tools/rename_brand.py`](../tools/rename_brand.py)
does it in one command: brand constants, repo-wide text, directory structure and the version
number, all in one pass. brand.rs's nine constants remain the single source of truth; the script
just moves them -- and every reference across the repo -- onto the new name. This page records
the parameter semantics, the script's boundaries, the post-rename checklist, and the five bugs a
real worktree run caught (all fixed).

## One command

```bash
python tools/rename_brand.py --en "New Name" --cn "中文名" [--bin newbin] \
    [--reset-version 0.1.0] [--apply]
```

- **Dry-run by default**: without `--apply` the script only prints the plan (which files, how
  many replacements, the git mv list) and writes nothing.
- `--bin` defaults to the lower-cased first word of `--en`; it must match `[a-z][a-z0-9]*`
  (it becomes the executable name and the crate prefix).
- `--reset-version` triggers the version reset (start from `0.1.0` when migrating to a new
  repo); without it the version stays put.
- Prerequisite: a clean working tree. The script uses `git mv` for structural renames; a dirty
  tree would mix in unrelated changes.

## What the script changes

1. **brand.rs's nine constants** (`NAME_EN` / `NAME_CN` / `TITLE` / `BIN` / `CRATE_PREFIX` /
   `APP_DIR` / `GUARD_DIR` / `ENV_PREFIX` / `TOOL_PREFIX`) get the new values; the old
   `APP_DIR` / `GUARD_DIR` are pushed into the `LEGACY_APP_DIRS` / `LEGACY_GUARD_DIRS` arrays
   (deduplicated, length follows content), and the old `ENV_PREFIX` / `TOOL_PREFIX` go into
   `LEGACY_ENV_PREFIX` / `LEGACY_TOOL_PREFIX` -- existing users' data directories and environment
   variables stay recognisable at runtime, so there is no "read from the old, write to the new"
   split.
2. **Repo-wide text replacement**: a table ordered longest-syntax-first (`Aevum Studio` → first
   word → `AEVUM` → `aevum_` → `aevum-` → `aevum` → `恒晷`) over every tracked text file.
3. **Structural renames**: five `git mv`s (three crates, the app directory, the migration script).
4. **Version reset** (only with `--reset-version`): root `Cargo.toml` → the four `Cargo.lock`
   members (matched under the **renamed** package names) → the two README spots in both
   languages (the header and the "Versioning" section; the English one wraps the version after
   "is", the regex handles it) → a `## v0.1.0 — unreleased` section inserted atop both
   CHANGELOGs (the **`v` prefix is mandatory** or check_version rejects it).
5. **Built-in reconciliation**: the run ends with a residue report (where the old name still
   appears) plus one pass of
   [`acceptance/check_version.py`](../acceptance/check_version.py).

## Post-rename checklist

```bash
cargo check --workspace          # a full rebuild the first time, expected
bash acceptance/check.sh         # six gates (check_docs / check_version included)
```

- Residue grep: `aevum` (the old name) should remain only in brand.rs's LEGACY archive.
- Commit and push only after the six gates are green and `git status` is clean; to migrate to a
  new repo, point the remote at the new address and push.

## Recommended flow: run for real in an isolated worktree first

```bash
git worktree add /e/tmp/rename-test --detach
cd /e/tmp/rename-test
python tools/rename_brand.py --en "New Name" --cn "中文名" --reset-version 0.1.0 --apply
# run the checklist above; once satisfied, run the same command in the main repo
cd /e/code/aevum-studio && git worktree remove /e/tmp/rename-test --force
```

The isolated worktree's target is empty, so a full rebuild takes a few minutes -- expected.
Lesson from history: on 2026-11-04 the real worktree run caught five bugs a dry-run cannot show
(next section) -- **the acceptance bar for this script is a real run**; a green dry-run is not a
deliverable.

## Known pitfalls (handled in the script; do not regress them)

1. `git ls-files` octal-escapes non-ASCII paths by default, silently skipping documents with
   Chinese filenames -- the script uses `git -c core.quotepath=off ls-files -z`.
2. The `Cargo.lock` version reset must match the **renamed** package names (order: rename first,
   reset second).
3. The new CHANGELOG section title must be `## v0.1.0 — …` with the `v` prefix.
4. The second version spot in the README's "Versioning" section, and the English README's
   version number that wraps after "is", must both be covered.
5. Never hardcode the length of a LEGACY re-export -- the source now uses
   `[&str; crate::brand::LEGACY_GUARD_DIRS.len()]`; the script additionally normalises any
   leftover hardcoded lengths against brand.rs (`fix_legacy_reexports`), so there are two
   layers of protection.

## Boundaries (what the script does not do)

- It does not touch the git remote, create a new repo, or cut a release. Releasing
  (tag / Release / asset upload) is a separate flow.
- It only processes tracked text: binary assets (images, zips) and untracked paths
  (`samples/`, `target/`) are out of scope.
- If a `.github/` workflow references the old executable name, the replacement table rewrites
  the text; whether the workflow still parses is a human eyeball check.
