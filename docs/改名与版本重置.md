# 改名与版本重置手册

**中文** · [English](改名与版本重置.en.md)

软件改名（名称待定）时用 [`tools/rename_brand.py`](../tools/rename_brand.py) 一条命令完成：
品牌常量、全仓文本、目录结构、版本号四件事一次做完。brand.rs 的九个常量仍是唯一真源，
脚本只是把它们和整仓引用一起搬到新名字上。本页记参数口径、脚本边界、改名后的核对清单，
以及 worktree 真跑验证抓到并已修掉的五个坑。

## 一条命令

```bash
python tools/rename_brand.py --en "New Name" --cn "中文名" [--bin newbin] \
    [--reset-version 0.1.0] [--apply]
```

- **dry-run 缺省**：不带 `--apply` 只打印计划（会改哪些文件、各多少处、git mv 清单），不写任何文件。
- `--bin` 缺省取 `--en` 首词小写；必须是 `[a-z][a-z0-9]*`（可执行名与 crate 前缀都用它）。
- `--reset-version` 触发版本重置（迁移新仓库时从 `0.1.0` 重开）；不传则版本号原地不动。
- 前提：工作树干净。脚本用 `git mv` 做结构改名，脏树会混入无关改动。

## 脚本改什么

1. **brand.rs 九常量**（`NAME_EN` / `NAME_CN` / `TITLE` / `BIN` / `CRATE_PREFIX` / `APP_DIR` /
   `GUARD_DIR` / `ENV_PREFIX` / `TOOL_PREFIX`）全部换新值；旧 `APP_DIR` / `GUARD_DIR` 自动
   推进 `LEGACY_APP_DIRS` / `LEGACY_GUARD_DIRS` 数组（去重、长度随内容），旧 `ENV_PREFIX` /
   `TOOL_PREFIX` 写进 `LEGACY_ENV_PREFIX` / `LEGACY_TOOL_PREFIX`——老用户的数据目录与环境变量
   在运行时仍能被识别，不会出现「读旧的、写新的」劈成两半。
2. **全仓文本替换**：按「长短语法优先」排序的替换表（`Aevum Studio` → 首词 → `AEVUM` →
   `aevum_` → `aevum-` → `aevum` → `恒晷`）扫全部入库文本文件。
3. **结构改名**：五个 `git mv`（三个 crate、应用目录、迁移脚本）。
4. **版本重置**（传了 `--reset-version` 才做）：根 `Cargo.toml` → `Cargo.lock` 四个成员
   （用**改名后**的新包名匹配）→ README 中英页首与「版本方案」段两处（英文处版本号跨行在
   "is" 之后，正则已处理）→ CHANGELOG 中英顶部插入 `## v0.1.0 — 未发布` 节（**必须带 `v`
   前缀**，否则 check_version 不认）。
5. **收尾自带对账**：打印残留报告（旧名还出现在哪），并跑一遍
   [`acceptance/check_version.py`](../acceptance/check_version.py)。

## 改名后的核对清单

```bash
cargo check --workspace          # 首次全量重编，属预期
bash acceptance/check.sh         # 六关（含 check_docs / check_version）
```

- 残留 grep：`aevum`（旧名）应只剩 brand.rs 的 LEGACY 留档。
- 六关绿、`git status` 干净后再提交推送；要迁新仓库时把 remote 换成新址再推。

## 建议流程：先在隔离 worktree 真跑

```bash
git worktree add /e/tmp/rename-test --detach
cd /e/tmp/rename-test
python tools/rename_brand.py --en "New Name" --cn "中文名" --reset-version 0.1.0 --apply
# 跑上面的核对清单，满意后回主仓库执行同一命令
cd /e/code/aevum-studio && git worktree remove /e/tmp/rename-test --force
```

隔离 worktree 的 target 是空的，全量重编要几分钟，属预期。历史教训：2026-11-04 的
worktree 真跑抓到五个 dry-run 看不出的 bug（见下节）——**改名脚本的验证口径就是真跑**，
dry-run 绿不等于能交付。

## 已知的坑（脚本已处理，改脚本时别回退）

1. `git ls-files` 默认把非 ASCII 路径转义成八进制，中文文件名的文档会被**静默跳过**——
   脚本用 `git -c core.quotepath=off ls-files -z`。
2. `Cargo.lock` 的版本重置必须用**改名后**的新包名匹配（执行顺序：先改名后重置）。
3. CHANGELOG 新节标题必须 `## v0.1.0 — …` 带 `v` 前缀。
4. README「版本方案」段的第二处版本号，与英文 README 里 "is" 后跨行的版本号，都要覆盖。
5. LEGACY 数组的再导出不要硬编码长度——源码里已改成
   `[&str; crate::brand::LEGACY_GUARD_DIRS.len()]` 的写法；脚本里另有按 brand.rs 实际长度
   归一化的兜底（`fix_legacy_reexports`），两层保险都在。

## 边界（脚本不做的）

- 不动 git remote、不建新仓库、不发版。发版（tag / Release / 资产上传）是另一条流程。
- 只处理入库文本：图片、zip 等二进制资产与未入库路径（`samples/`、`target/`）不在范围。
- `.github/` 工作流若引用了旧可执行名，替换表会一并改文本；但 workflow 语法是否仍成立
  要人工过一眼。
