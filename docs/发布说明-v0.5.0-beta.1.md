# 恒晷 · Aevum Studio 0.5.0-beta.1 发布说明

**中文** · [English](发布说明-v0.5.0-beta.1.en.md)

发布日期：2026-10-31
上一版：`0.4.0-beta.1`（发布名「光时 / Lumen Studio」）

---

## 一句话

**产品改名为「恒晷 / Aevum Studio」。** 这是本版唯一的破坏性变更，其余是配套的兼容层、
文档与打包调整。**算法一行未改**：全部数值金标（`oracle/golden/` 10 个文件）sha256
逐字节不变，`--selftest` 的八个界面形状数与 0.4 完全一致。

---

## 升级须知（三句话）

1. **旧工程的 `.lumen/` 会在你第一次打开那个序列时自动搬成 `.aevum/`。** 搬失败（只读盘、
   杀软正占用文件）时**继续在旧目录里工作**——不会丢数据，也不会变成只读。手动整盘搬迁见
   `scripts/migrate-to-aevum.sh`。
2. **环境变量 `LUMEN_*` 仍然可用**，但每个进程第一次用到时会在 stderr 打一行弃用提示。
   建议改成 `AEVUM_*`；两个都设时以 `AEVUM_` 为准。
3. **MCP 客户端升级后请重新拉取一次 `tools/list`。** 旧工具名 `lumen_*` 服务端仍然认
   （静默别名，返回结果逐字节相同），但**列表里只列 `aevum_*`**；有客户端会在调用前校验
   「这个名字必须出现在 list 里」，那种情况下旧名会被**客户端自己**拦掉，重拉即可恢复。

## 二、兼容策略（**旧数据不会丢，旧调用不会断**）

这一版按「三级向后兼容」实现，`.lapse → .lumen → .aevum`。所有迁移都是**搬不是删**。

### 1. 旧工程能直接开

- 打开序列时，`<序列>/.lumen/` 会自动搬成 `<序列>/.aevum/`；更早的 `<序列>/.lapse/` 同样能搬。
- 参数、评级、标记、关键词、堆叠、关键帧、对齐结果、去闪曲线、取景框、运镜、水印设置
  **全部原样恢复**（工程文件格式没变）。
- 两个旧目录同时存在时：**只用 `.lumen`**（更新的那个），`.lapse` 原样留着不删——
  分不清哪份是用户现在在用的，猜错了就是覆盖数据。
- **搬不动时不会降级成只读**（只读盘、杀软正占用插件文件等）：继续用旧目录读写，
  只在 stderr 打一行告警。让「保存」静默失败比迁移失败严重得多。
- **`.aevum` 万一是同名文件不是目录**（用户手滑、别的工具写出来的）：不搬，继续用旧目录并提示
  一句。这条看着多余，但 Windows 上往一个已存在的文件上 `rename` 会**把它直接抹掉**——
  F8 的回归测试就是拿这个场景写的，第一版实现真踩了。

一次搬完整个素材盘可以用：

```bash
scripts/migrate-to-aevum.sh 'F:/2025'           # 预演，只看会动哪些
scripts/migrate-to-aevum.sh 'F:/2025' --apply   # 真搬
```

### 2. 旧环境变量仍然生效

**12 个运行时变量支持旧名回退**，**新名优先**（外加 1 个打包变量，见下方说明）：

```
AEVUM_LENSFUN      AEVUM_FFMPEG      AEVUM_LIBRARY     AEVUM_SETTINGS
AEVUM_PLUGINS      AEVUM_DCP         AEVUM_LCP         AEVUM_RENDER_QUEUE
AEVUM_FRAMES       AEVUM_DEV_CASES   AEVUM_REAL_RAW    AEVUM_ICC_DUMP
```

例：`LUMEN_FFMPEG=D:/tools/ffmpeg.exe` 仍然会用那个 ffmpeg；若同时设了 `AEVUM_FFMPEG`，
以 `AEVUM_` 为准。**每个进程首次用到旧名时会在 stderr 打一行弃用提示**，提示里带新名。

**第 13 个变量是例外：`AEVUM_FFMPEG_SRC`。** 它只给 `scripts/package.sh` 打包时用，
没有旧名回退——本版起打包脚本**不再读** `LUMEN_FFMPEG_SRC`，设了也不生效。
所以上面的「旧名仍然可用」这句话不覆盖它。

便携盘用法不变：设任一 override（`AEVUM_SETTINGS` / `AEVUM_PLUGINS` / `AEVUM_LIBRARY` /
`AEVUM_RENDER_QUEUE`）即视为便携模式，**完全不碰 `%APPDATA%`**。

### 3. 旧配置目录首次启动自动并过来

- `%APPDATA%/lumen-studio`（或更早的 `lapse-studio`）在首次启动时搬成 `%APPDATA%/aevum-studio`。
- 新目录还不存在时走**整目录改名**：旧路径不再存在，但一个文件都没删，内容整体挪到了新路径。
- 新目录已存在时走**逐项补缺**：目标缺什么补什么，**同名文件以新目录为准**（老覆盖新会把
  用户在新版本里的设置打回去），旧目录这次**原样留着**，随时能回去翻。
- 任何情况下都不删文件，最坏也只是原地不动。
- 迁移只做一次，靠 `aevum-studio/adopt-sentinel` 标记。这条不能省：否则你在新目录里删掉的插件，
  下次启动又会被旧目录搬回来。

> 上一代 `scripts/migrate-to-lumen.sh` 只搬了 `render_queue.json` 一个文件，导致从 Python 版
> 升上来的用户丢过 `settings.json` / `galleries.json` / `plugins/`。本版改成**整目录级**迁移，
> 并补上了 Rust 侧一直缺失的 `lapse-studio` 回退。

### 4. 旧 MCP 工具名仍然可调（静默别名）

`lumen_open_sequence`、`lumen_grade_set`… 34 个旧工具名全部仍可调用，返回结果与对应的
`aevum_*` **逐字节相同**（有测试钉着）。写操作日志也照常记录——`is_write_op` 内部会先把
旧名规范化，所以旧名不会被漏记进 `op_journal.jsonl`。

**但 `tools/list` 只列新名。** 旧名是「接受调用但不宣传」。

> ## ⚠️ 升级后请在客户端重新拉取一次 `tools/list`
>
> 有些客户端在调用前会校验「这个名字必须出现在 list 里」。这类客户端拿到旧的
> `tools/list` 缓存后，用 `lumen_*` 调用会被**客户端自己**拦掉（服务端其实接得住）。
> 重新拉一次即恢复。
>
> 另外 `serverInfo.name` 由 `lumen-studio` 变成 `aevum-studio`，按 server 名做权限记忆的
> 客户端会重新询问一次授权——这是应有的行为，不是缺陷。

### 5. 启动器兼容

`恒晷.bat` 的查找顺序：`dist\aevum\aevum.exe` → `dist\lumen\lumen.exe` →
`target\release\aevum.exe` → `target\debug\aevum.exe`。

已经解压过 0.4 绿包的人不改任何东西，双击新脚本也能起来（会用到旧的 `dist/lumen/lumen.exe`）。
不保留 `光时.bat` 的副本：文件名本身就是品牌，留两份只会让人不知道点哪个。

### 6. 插件不受影响

插件清单的 `id` 前缀**不被解析**（只校验「含点 + 小写字母/数字/点/连字符」），
已装的第三方插件照常加载。唯一变化是仓库内的**示例插件**改名为 `aevum.example-invert`。
若你既装过 `lumen.example-invert` 又装过 `aevum.example-invert`，插件菜单里会出现两个
（id 不同）——删掉旧的即可，我们不会自动改写用户的 `plugin.toml`。

## 五、已知问题

1. **`scripts/package.sh` 的默认 ffmpeg 路径已失效**：`$ROOT/../pythonProject4/.venv/...`
   在多数机器上不存在（**改名之前就是这样，不是本版引入的**）。本版只改进了失败提示——
   找不到时会把探测顺序和下一步命令打出来，然后 `exit 1`，不再只报一句「未找到」。
   **修法待定**，三个候选：找 venv 路径 / 找 PATH / 优先找 exe 同目录，属于依赖解析的独立决策，
   不混进改名轮。当前请显式传 `AEVUM_FFMPEG_SRC=<ffmpeg.exe 绝对路径>`。
2. **clippy / rustfmt 在本机工具链上本来就是红的**（rustc 1.98，4 条 lint + 197 个 fmt hunk，
   其中一条落在冻结文件 `layout.rs` 内）。本版按设计**只保证差异为零**，不做「强行全绿」。
   建议下一轮单独加 `rust-toolchain.toml` 钉版本后再统一修。
3. 从 0.3 及更早（Python 版）升上来的用户，若当年已被旧迁移脚本弄丢
   `settings.json` / `galleries.json`，本版**无法凭空找回**——只能从备份恢复。
   本版做的是「以后不再丢」。
4. **`tools/split_step1.json` / `split_step2.json` 里指向已不存在的目录**（`F6`）：
   那是历史重构脚本的输入记录，改了等于篡改记录，本轮不动。
5. **附着模式下 9/34 个工具解析不到，且 `xmp_read`/`xmp_write` 与 `xmp_import`/`xmp_export`
   跨模式命名不一致**（`F10`）：**pre-existing，非本轮引入**。下一轮补「工具名穷举双向覆盖」
   测试并统一命名，本轮不在改名里顺手改工具集。
6. **只读盘回退状态只在 stderr 里，GUI 下用户看不到**（`R3`）：工程落在只读盘、护带目录搬不动时，
   界面没有任何提示，用户仍以为参数会存下来。修它需要界面告警，属产品改动，另开单。
7. **便携模式路径失效时静默回默认值**（`R4`）：`AEVUM_SETTINGS` 指到一个写不进去的位置时，
   程序不报错、直接退回默认配置。需要一段诊断输出，另开单。
8. **双实例同时首启的跨进程竞态**（`R6`）：两个进程同时判断「`aevum-studio` 不存在」并各自迁移，
   理论上可能互相覆盖。概率极低，本轮不加跨进程锁。
9. **工程目录下若存在名为 `.aevum` 的普通文件，保存失败并只报 `os error 183`**（`F8` 子情形 b）：
   罕见（通常是用户误建，或别的工具写的同名文件）。打开与读参数正常，**保存时报
   「当文件已存在时，无法创建该文件」**，提示里看不出该怎么办。
   本版**已保证不会删掉那个文件**——`adopt_guard_dir` 发现目标被同名文件占用就跳过迁移、
   继续用旧目录并打一行提示。这是 QA Round 1 抓到的真 bug：第一版实现会 `rename` 到那个
   文件上，而 Windows 的 `MoveFileEx(REPLACE_EXISTING)` 把它连内容一起抹掉，且 stderr 还打印
   「已迁移」。但「没有旧目录、只有那个文件」的情况下仍然保存不了。
   处理办法：改掉/删掉该文件后重试。**这是 0.4 就存在的存量缺口，不是本版引入**。
   下一轮补 `ensure_guard_dir_usable()` 之类的前置检查与可读错误文案，并明确告诉用户
   「数据在 `.lumen/` 里，没丢」——本轮裁定不做，因为那会把 diff 从「改名」扩成
   「改名 + 容错改造」，review 成本不值。

## 六、回滚

- 绿色包：直接换回 0.4 的 `lumen.exe` / `dist/lumen/` 即可，旧目录与新目录都在。
- 工程：`.aevum/` 与 `.lumen/` 的 `project.json` 格式**完全相同**，把 `.aevum/` 改回 `.lumen/`
  就能被 0.4 打开。
- 配置：`%APPDATA%/aevum-studio` 改回 `%APPDATA%/lumen-studio`；旧目录若还在，直接删掉新目录即可。

### ⚠️ 不要在新旧版本之间来回打开同一个序列

0.5 已经把 `.lumen/` 搬成 `.aevum/` 之后，用户若再用 0.4 的快捷方式打开**同一个序列**：

1. 0.4 找不到 `.lumen/` → **新建一个空的** `.lumen/` → 界面显示默认参数。
   用户看到的是「参数全丢了」，其实都还在 `.aevum/` 里。
2. 用户以为要重调，于是在 0.4 里做的改动全部写进那个**空目录**。
3. 再切回 0.5 → 0.5 优先读 `.aevum/`（它存在）→ 0.4 里的改动被**静默忽略**，
   两边从此对不上，且没有任何提示。

**回退必须一次性完成**：先按上面把目录/配置改回去，确认 0.4 正常后再继续用 0.4。
中间不要交叉打开。这条是「数据没丢但用户以为丢了」的典型，比真正的数据丢失更难排查。
