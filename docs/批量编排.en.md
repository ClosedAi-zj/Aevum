# Cross-sequence batch orchestration (F6, v1.7.0)

**English** · [中文](批量编排.md)

## Why this page exists

One call is enough for one sequence, but "a dozen timelapses under one directory" is the real
workload. The old answer was to let the agent loop: `aevum_open_sequence` → tweak → export,
and after a dozen rounds nobody could tell which sequence it was on. Now a single call returns
"how many succeeded, how many failed, and why for each".

Two tools: `aevum_sequences_scan` (read-only) and `aevum_batch_run` (scan → enqueue → run).

## Scan rules

| Rule | Why |
|---|---|
| The root itself plus subdirectories down to `depth` (default 1, max 4) | A sequence is usually a child of the parent; a library root or a year/month layout uses `depth: 2` |
| Once a directory opens as a sequence, stop descending | A sequence directory holds frames; descending further only offers cache directories as candidates |
| Directories starting with `.` are skipped | A sequence's own `.aevum/` (project, metering ledger, thumbnail cache) is not source material |
| `skipped` records only "has images but will not read" | An empty folder is not a defect; "there are images but some format we cannot open" is the sentence worth saying |

There is exactly one criterion: **what `Sequence::open` says is the verdict** (`sequence.rs` is
the single source of truth), and the scanner does not keep its own suffix logic -- otherwise
"the scan says this is a sequence, opening says it is not" would drift apart sooner or later.

## Batch semantics

| Behaviour | Default | Why |
|---|---|---|
| `confirm` | Required | It writes to disk in bulk, the same gate as `aevum_queue_run` |
| Queue | **Cleared first**, `append: true` appends | "Render every sequence under this directory" mixed with the previous batch makes the result unreadable |
| `out` | `<sequence dir>/<name>_成片.mp4` per item | One `out` across a batch would overwrite itself, so it is refused when more than one sequence is found |
| Spec validation | The whole batch is validated before the queue is touched | Half a batch enqueued is harder to clean up than none |
| Rendering | The same `queue::render_item` the queue uses | Parameters, progress, cancellation and bit-exactness get no second implementation |

Single add and batch share `queue_item_from_args` for validation: one argument, one verdict
(the R4 lesson applied to arguments).

## Result shape

```json
{
  "root": "D:/timelapse/2026-11-04", "depth": 1,
  "scanned": 3, "queued": 3, "cleared": 0,
  "ok": 2, "failed": 1, "cancelled": false,
  "items": [
    {"index": 1, "root": ".../a_first", "out": ".../a_first_成片.mp4", "status": "完成", "note": ""},
    {"index": 3, "root": ".../c_broken", "out": ".../c_broken_成片.mp4", "status": "失败",
     "note": "打开序列失败：这些文件里有我们解不开的格式"}
  ],
  "skipped": [{"root": ".../d_bad", "reason": "这些文件里有我们解不开的格式"}]
}
```

`items` shares its source with the GUI queue panel (`render_queue.json`), so opening the GUI
afterwards shows exactly the same state.

## Unattended use

`background: true` returns immediately; poll `aevum_queue_status`, cancel with
`aevum_queue_cancel` / `aevum_cancel`. The criterion
`tools::batch_run_covers_a_directory_and_names_the_broken_sequence` pins three things: two
segments really leave a finished file on disk (not "it said it succeeded"), the broken one comes
back failed with a note a human can read, and the previous batch is cleared by default
(`cleared` equals the previous count).

## Boundaries

- Never delete or modify a source image (the same bottom line as every other tool); intermediate
  frames from a failed segment are kept per the queue rules.
- A directory with no sequences is an error, not an empty list -- an empty list would let the
  caller believe "done, zero segments".
- It orchestrates directories that are already sequences: culling (rating / flag) still goes
  through `aevum_cull_*`, and neither side crosses into the other.
