# Dependency licence notes (M2 increment)

**English** · [中文](依赖许可说明.md)

This document records the licensing and distribution terms of the third-party decoding dependency
introduced in M2, for packaging (`scripts/package.sh` / direct zip distribution) and for compliance
records. The licences of dependencies already in the repository follow each crate's own declaration
and are not repeated here; the complete user-facing list is `THIRD-PARTY-NOTICES.txt` in the
repository root.

> **Correction, 2026-10-31**: this document used to state rawler's licence as "MIT OR Apache-2.0
> (dual-licensed)" and, on that basis, concluded "zero additional obligations for binary
> distribution". **That was wrong.** rawler is **LGPL-2.1, a single licence**, and it is linked
> statically into the shipped binary. Every judgement that was made on the old wording needs
> re-evaluating; what follows is rewritten from measurement, and the end of the document explains
> why the error was made at the time (so the same class of mistake is not repeated).

### Compliance points (LGPL-2.1 §6, static-linking scenario)

Because aevum.exe contains the library statically, it is what §6 calls "a work that uses the
Library", not a "mere aggregation of separate processes", so it **cannot** be shipped as-is with
zero obligations the way a permissive licence allows. The four obligations and what this repository
does about them:

| Obligation | What we do | Where it lives |
|---|---|---|
| State that the library is used and is covered by the LGPL | Written into the bundled notice and the release notes | `THIRD-PARTY-NOTICES.txt`, section 2 |
| Include the full licence text | The licence text ships with the package | `licenses/LGPL-2.1-rawler.txt` |
| Provide the corresponding source | The Cargo source package ships with the bundle (730 KB, unpacking it gives the complete source) plus the official download address and checksum | `third-party-src/rawler-0.8.0.crate` inside the zip |
| Allow modification and relinking | The document gives two concrete routes, `[patch.crates-io]` and `cargo vendor`, neither of which requires changing project code; if the object-file form is wanted, ask the publisher for it | `THIRD-PARTY-NOTICES.txt`, section 2 |

**One shortcoming remains, recorded honestly**: Rust static linking has no ready-made equivalent of
"the user swaps the DLL", so genuine replacement means rebuilding the whole exe yourself. In LGPL
practice that counts as an acceptable "means of rebuilding", but it is weaker than a dynamic-link
arrangement. If an explicit demand arrives in future, the upgrade path is to package rawler as a
`cdylib` and ship a DLL alongside (work involved: a C ABI boundary + the Windows load path + graceful
degradation on failure); this release does not do it.

### How to build with no copyleft at all

```bash
cargo build --release --no-default-features
```

`raw-rawler` is the only feature affected; with it off, all RAW decoding goes through the built-in
backend (behaviour identical to v0.3.0) and the binary contains no LGPL/GPL code at all. The price is
that CR3-CRX, the 12/14-bit packed-in-line formats and the like cannot be decoded (they report
"unsupported" explicitly rather than failing silently). **This path must stay available long-term** —
it is the exit left for downstream users who are "not allowed to link LGPL", and any change that
turns rawler into a non-optional dependency is dismantling that exit.

### One piece of old wording, clarified in passing

The earlier text said "a pure-Rust implementation, so it does not bring libraw's (LGPL-2.1/CDDL)
packaging burden" — that comparison is wrong: rawler's own licence is LGPL-2.1 as well. The real
difference is not the licence but the **form of implementation**: rawler is pure Rust (no C toolchain,
no dynamic library, no vendored C sources), so building and distribution are simpler; the copyleft
obligations, however, are on a par with libraw's. Writing MIT/Apache back then was most likely a copy
of an older version's metadata on the crates.io page, or a confusion with a transitive dependency such
as `kamadak-exif`. **Lesson: a licence field must be cross-checked against both the crate's own
LICENSE file and `cargo metadata` — never just the crate page summary or from memory.**

### Offline builds and vendoring

- On by default; for offline builds, or when the v0.3.0 behaviour has to be restored, use
  `cargo build --no-default-features` (behaviour is bit-identical to the built-in backend).
- Before distribution, run `cargo vendor vendor/` on the CI side and commit `.cargo/config.toml`,
  then have CI/packaging verify once with `cargo build --offline`. If the machine already has a warm
  cache (the registry `CARGO_HOME` points at), one vendor run pins every transitive dependency.
- rawler's transitive dependencies (kamadak-exif, num_enum, rayon, thiserror, backtrace and others)
  are all pinned along with the vendor tree, and their licence is whatever each crate's `LICENSE`
  file in the vendor directory says. Measured, these transitive dependencies are all permissive
  licences (MIT / Apache-2.0 class) and **introduce no new copyleft**; even so, re-run the audit on
  every rawler major-version bump — do not assume it is unchanged.

## vendor plan (still not executed)

1. On a machine with network access, `cargo vendor vendor/`, and commit `vendor/` + `.cargo/config.toml`;
2. Run `cargo build --workspace --offline` and `cargo test --workspace --offline` once each;
3. Have the packaging script aggregate the third-party list from the vendor directory and reconcile it
   against `THIRD-PARTY-NOTICES.txt`.

One note in passing: even with vendoring done, **rawler's LGPL obligations are not waived by it** —
vendoring merely turns "the source is obtainable" from "downloadable from outside" into "carried in
the repository", which strengthens the position rather than replacing it.
