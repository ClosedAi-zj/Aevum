# Platform delivery presets

**English** · [中文](交付预设.md)

The four numbers you fill in before an export — frame size, frame rate, encoder, quality
target — are **platform conventions**, not creative parameters. This page covers the built-in
conventions, how the panel and agents use them, and how to edit the table (without touching
code).

## 1. Built-in conventions

| key | Name | Frame | Rate | Encoder | Quality |
|---|---|---|---|---|---|
| `douyin-vertical` | Douyin vertical | 1080x1920 | 30 | H.264 | CRF 20 |
| `channels-vertical` | WeChat Channels vertical | 1080x1920 | 30 | H.264 | CRF 20 |
| `xiaohongshu-vertical` | Xiaohongshu vertical | 1080x1440 | 30 | H.264 | CRF 20 |
| `bilibili-1080p` | Bilibili 1080p | 1920x1080 | keeps your pacing | H.264 | CRF 18 |
| `bilibili-4k` | Bilibili 4K | 3840x2160 | keeps your pacing | H.265 | CRF 20 |
| `master-1080p` | Master 1080p | 1920x1080 | keeps your pacing | H.265 | CRF 16 |

The three short-video conventions carry `30fps`: those platforms really do distribute at 30.
The two long-form ones and the master carry **no rate** — frame rate is creative pacing for
timelapse (24 fps clouds and 30 fps clouds are not the same sense of time), and nothing should
decide that for you when the platform does not require it.

The numbers are a starting point, not gospel: platforms change, and when they do, edit the
table (section 4) rather than the code.

## 2. In the panel

The "Platform delivery" group at the top of the render panel: one click fills frame size, rate,
encoder and quality target at once. Everything in "Output" and "Codec" below stays editable.

- **The highlight is inferred from the numbers.** A platform chip is lit only when the current
  settings match that convention exactly. Change any one of the four and the highlight goes
  out — no chip left lit for settings that no longer match it.
- Encoder speed (ultrafast … veryslow) is excluded from the comparison: a performance
  preference, not part of the convention.
- "Preset table..." writes a template (on first click) and reveals the file.

## 3. From an agent (MCP)

- Call `aevum_sequence_info` first; its `delivery` array is the list of available keys with
  their frame, rate, encoder, quality target and a one-line note.
- Then call `aevum_export_video` with `delivery: "<key>"`.
- **Explicit arguments win.** Passing `fps` / `crf` / `codec` / `preset` / `width`+`height` /
  `long_side` overrides the preset — a preset saves typing, it does not forbid changing one
  number.
- A misspelled key returns the available list, and does so **before** ffmpeg is located: a typo
  should not wait behind an unrelated "ffmpeg not found".

Still export (`aevum_export_stills`) does not take presets yet; this table is for distributed
video.

## 4. Editing the table (no code change)

```
%APPDATA%/aevum-studio/delivery-presets.toml
```

The "Preset table..." button writes a complete template. Format:

```toml
# A matching key replaces the built-in entry wholesale; a new key is appended.
[[presets]]
key = "douyin-vertical"
name_cn = "抖音竖屏（我的）"
name_en = "Douyin vertical (mine)"
width = 1080
height = 1920
fps = 60.0            # omit it (or delete the line) to leave the user's rate alone
codec = "h265"        # h264 / h265 (also accepts h.265, hevc, x265)
crf = 17
encoder_preset = "slow"   # omitted = medium
hint_cn = "我自己的口径"
hint_en = "my own convention"

[[presets]]
key = "my-platform"
name_cn = "自用平台"
name_en = "My platform"
width = 1440
height = 1080
codec = "h264"
crf = 19
```

Rules and edges:

- **Restart to apply:** the table is read once at startup (the panel redraws every frame and
  must not read a file each time).
- An unreadable table **falls back to built-ins as a whole**, with one line on stderr; it never
  runs half a broken table.
- Validation: `key` non-empty and unique; width and height non-zero; CRF within 1-51; frame
  rate positive.
- Choosing an H.264 convention **visibly** drops the dynamic range to SDR — H.264 is 8bit and
  cannot carry PQ, and leaving a combination that only fails when export is pressed is the
  worst failure mode.

## 5. Why CRF and not a fixed bitrate

Timelapse content varies wildly (clouds move, light changes); a fixed bitrate either wastes
bits or smears the "three still seconds then a lightning bolt" shot. CRF guarantees a quality
floor and lets the bitrate follow the content.

The real platform constraint is a **size cap**, which is a different thing. Dressing it up as a
bitrate knob here would create a switch that cannot promise anything — worse than no switch.

## 6. Assertions

- `delivery::tests::*` (core unit tests): built-in table valid and keys unique; the vertical
  convention writes all five fields exactly and touches nothing else; `fps: None` leaves the
  pacing alone; a file overrides numbers, appends new keys and keeps built-ins; a broken table
  falls back; the template round-trips.
- `export_video::every_number_of_the_vertical_delivery_preset_reaches_the_render` (core
  end-to-end): the command layer checks `-framerate 30`, `-c:v libx264`, `-crf 20`,
  `-preset medium`; the pixel layer checks that both the intermediate frames and the first
  frame of the render are 1080x1920.
- `tools::a_delivery_preset_is_discoverable_and_a_typo_is_reported_before_ffmpeg` (MCP): the
  list is discoverable, numbers match the built-in table, and a typo is rejected before the
  ffmpeg check.
- `delivery_panel::*` (UI): applying writes the five fields, changing any one clears the
  highlight, `fps: None` keeps the pacing, H.264 drops the dynamic range to SDR.

All of the above were mutation-tested (reverting the behaviour turns them red).
