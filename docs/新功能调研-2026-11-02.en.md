# New Feature Research (2026-11-02)

**English** · [Chinese](新功能调研-2026-11-02.md)

> Verdict: the next release ships **F1 long-timelapse culling bench + F3 per-frame timestamp overlay + F2 astro/night stacking**. The first two are S-cost, daily-driver needs of the core audience; the third reuses existing alignment and merge infrastructure to eliminate the last "two-hop intermediate file" detour in the astro workflow.

---

## 1. Scope and Method

- Grounded in the v1.2.1 feature set (README, Feature Overview) and bounded by Group B plus the "won't do" entries of the legacy ledger in `docs/` (Chinese-only document, see the Chinese edition for the link).
- Competitive research based on public 2026 sources: LRTimelapse official tutorials and forum (from 2026-04), the darktable 5.6.0 release notes (2026-06), the Lightroom user community (2026-01), and Chinese-creator tutorials (CSDN / Toutiao / WeChat official accounts, 2026).
- Not a feature checklist. The goal is three classes of structural gaps: switching-software rework, parameters that cannot be reused, and preview-to-deliverable mismatch.

## 2. Competitive Landscape (as of 2026-11)

### 2.1 Timelapse / Sequence-Specific Tools

| Tool | Status | Structural problem |
|---|---|---|
| LRTimelapse 7.x | De facto standard. Keyframes must be edited in Lightroom, via XMP metadata round-trip plus a dedicated sync script | The round-trip is fragile: forget to save XMP or leave auto-write off and the chain breaks; the Holy Grail wizard fails on sequences with extreme exposure spans (official forum, 2026-04: "skip the wizard, rely on multiple deflicker passes") |
| LRTimelapse internal export | Can render without Lightroom | Constrained develop pipeline, and it still writes a JPEG/TIFF **intermediate sequence** before rendering - double disk usage, one extra quality hop |
| StarStaX / Sequator | Free standard tools for star-trail and nightscape stacking | Sequator is Windows-only and effectively dormant; neither reads RAW - both require a pre-developed 16-bit TIFF batch out of Lightroom, another two-hop detour |
| After Effects / Premiere | Hyperlapse stabilization, frame blending for object flicker | Manually patching tracking points takes 20-40 minutes per 200 frames (quoted from a Chinese tutorial); stabilize, then deflicker, then back to Lightroom for export, then into the NLE - the most fragmented chain of all |
| Time-Lapse Tool / Flicker Free | Single-purpose deflicker / stabilization | Operate on finished sequences only: no RAW, no grading |
| qDslrDashboard / Sequence (iOS) | Capture-side tools | No handoff into post |

### 2.2 General RAW Developers

| Tool | Status | Structural problem |
|---|---|---|
| Lightroom / ACR | AI Denoise, AI masks (re-detected per frame on sync), Super Resolution | **AI Denoise still cannot be batched** (community-confirmed 2026-01: batch applies to the first selected image only), and it is mutually exclusive with Super Resolution; one parameter set times N frames is exactly the shape of timelapse |
| Capture One | Best-in-class tethering, strong X-Trans reputation | No sequence concept |
| darktable 5.6 (2026-06) | New optional AI subsystem (ONNX: SAM2.1 masking, RAW denoise / upscale, batch tiled inference, CPU fallback), HEIF export | A single-frame tool with no alignment / deflicker / retiming; however good the AI, it cannot feed a sequence |
| RawTherapee / DxO / ON1 / Luminar / Affinity | Various single-frame strengths | Same: the sequence side is entirely empty |

### 2.3 Three Structural Gaps (the opportunities)

1. **The "two-hop intermediate file" is not dead yet.** Aevum's direct-to-ffmpeg pipeline already removes the hop LRTimelapse still has; but star-trail / nightscape stackers must still go Lightroom TIFF export, then StarStaX / Sequator, then Photoshop to composite a foreground. Whoever absorbs stacking into the sequence pipeline takes the whole chain.
2. **AI is priced per frame.** Lightroom cannot batch denoise; darktable can batch but has no sequence-consistency model (no alignment, no deflicker). Aevum's self-trained denoising network already runs per frame inside the develop chain (`ai_denoise.rs`) - this is already our advantage. **Nothing to build here**; the job is not to regress it.
3. **The long-timelapse (construction / engineering) ecosystem in China is ignored wholesale.** Tens of thousands of frames, 30-50% discard rates, multi-day resumed shoots, per-frame timestamps, unattended delivery - Chinese tutorials all teach the "LRTimelapse + AE + Premiere" trio. No desktop tool is natively Chinese and treats the sequence as a first-class citizen. Engineering timelapse controllers (cloud galleries with 40k+ frames) have a substantial installed base in China.

## 3. Feature Candidate Pool

> Verified against the repository: per-frame grading keyframes already exist (`keyframes: BTreeMap<usize, GradeParams>` in `project.rs`), AI denoise is already in the develop chain, HDR merge / panorama / local alignment / retiming / motion blur / static watermark / MCP / render queue all exist. None of the candidates below overlaps those.

### F1 Long-timelapse culling bench (S) - P0

- **Whose problem**: construction / engineering / city long-timelapse authors; 30k-500k frames per project with 30-50% discard rates (underexposed nights, blown midday, days of overcast, intruding objects). Today they depend on LRTimelapse's brightness filter, or eyeball thumbnails.
- **Workaround today**: LRT brightness / time filter, delete files in the library, reload the sequence; Chinese users largely delete by hand.
- **Cost S**: `metrics.rs` already meters every frame (the brightness curve is already plotted); add "select by metric range, mark as bad, cull into a sub-sequence" in `sequence.rs`, reusing the `library.rs` rating system.
- **Fit**: fully reuses the existing sequence model and metrics pipeline; the MCP surface gains an `aevum_sequence_cull` tool in passing.
- **Risk**: low. The interaction between culling and keyframe indices must be defined in `project.rs` (what happens to keyframe indices after frames are removed).
- **Success criterion**: on a synthetic sequence with known bad frames, one-click culling by "brightness below threshold" leaves a residual brightness spread within the threshold, with no dangling keyframe indices.

### F2 Astro / nightscape stacking to a still frame (M) - P0

- **Whose problem**: star-trail creators (lighten blend + gap filling + comet mode) and nightscape noise-stackers (average / median with sigma-clipping to reject satellite and plane streaks). Today: Lightroom 16-bit TIFF export, then StarStaX / Sequator (Windows-only), then Photoshop for the foreground composite.
- **Workaround today**: a two-hop intermediate pipeline plus two free tools (one unmaintained for years, one Windows-only).
- **Cost M**: the multi-frame merge infrastructure in `hdr.rs` plus the sub-pixel translation alignment in `align.rs` carry over directly; new work is the four blend modes (lighten / average / median / sigma-clip) and gap filling, landed on the still-frame path in `export.rs`. The per-frame pipeline is untouched.
- **Fit**: "sequence to still" is the dual of the existing "sequence to video" exit, conceptually identical piping; the AVIF 10-bit HDR still-frame exit is naturally available (astro scenes are high dynamic range).
- **Risk**: medium. Sigma-clipping and star-pixel criteria carry algorithmic uncertainty, but the literature is solid (sigma-clipping is standard practice in the astro community); memory for N-frame accumulation needs tiling.
- **Success criterion**: on a 120-frame synthetic sequence where each frame contains a straight bright streak at a known position, the lighten stack output shows a continuous unbroken streak, and in sigma-clip mode the injected 5% outlier frames are rejected.

### F3 Per-frame timestamp overlay (S) - P0

- **Whose problem**: construction-timelapse delivery hard requirements - the frame must show which date and time it was taken. Every frame differs; a static watermark cannot cover it.
- **Workaround today**: LRTimelapse gates timestamps behind the **Pro license**; or burn them with per-frame ffmpeg drawtext scripts - back to the command line.
- **Cost S**: the `watermark.rs` text path (self-drawn outlines and scanline fill) already renders a line of text; add "text source = EXIF capture time (already parsed in `exif.rs`) + position and format template". Like everything else in that layer, it applies only at the export tail and never in previews, matching the existing rule.
- **Fit**: high. No pipeline changes, export tail only.
- **Risk**: low. One caveat: the format template is locale-sensitive (date conventions differ between Chinese and English) and goes through the existing language registry.
- **Success criterion**: on any two exported frames the overlaid text equals each frame's EXIF time formatted by the template, and the layer never appears on preview frames.

### F4 Chroma (color) deflicker (M) - P1

- **Whose problem**: chromatic jitter from mixed lighting, auto white balance, and street-lamp flicker. Current deflicker is luminance-only (`deflicker.rs`: metering, robust smoothing, EV offset); the Lightroom community's 2026 answer is still "set white balance manually on every keyframe".
- **Cost M**: extend the same framework from "per-frame luma + EV" to "per-frame color temperature / chroma + offset"; add a frozen `deflicker_chroma.json` golden alongside.
- **Fit**: high; the pipeline and the reference-implementation mechanism carry over unchanged.
- **Risk**: medium. Careless chroma smoothing erases the *intended* color drift of a sunset; the criteria must separate natural gradients from frame-to-frame jitter - exactly the self-validating measurement playbook of Group A.
- **Success criterion**: on a synthetic sequence (color temperature with plus/minus 200K frame-to-frame jitter over a slow real drift), correction reduces the standard deviation of frame-to-frame color difference by at least 10x while preserving the drift trend.

### F5 Holy Grail pre-alignment (M) - P1

- **Whose problem**: day-to-night exposure ramps. LRT's Holy Grail wizard reads EXIF EV differences for an initial compensation but fails on wide spans (the official forum concedes it); users fall back to repeated deflicker passes.
- **Cost M**: read EV from `exif.rs`, apply a per-frame initial exposure compensation, let the existing deflicker absorb the residual. **No LRT-style wizard UI** - a single "align to EXIF first" switch inside the deflicker panel.
- **Fit**: high; stacks with the existing keyframes and deflicker rather than replacing them.
- **Risk**: medium. Tolerance for missing or wrong EXIF; the `MAX_EV = 3` cap must become configurable for full day-night spans.
- **Success criterion**: on a synthetic day-to-night sequence (EXIF EV ramping linearly from +2 to -5), the pre-deflicker luminance residual drops by an order of magnitude with the switch on.

### F6 Unattended batch orchestration over MCP (M) - P1

- **Whose problem**: post for multi-camera engineering timelapse and batch delivery: overnight, an agent walks a folder of sequences through "cull, deflicker, preset, render queue". Today the queue consumes single-sequence tasks; cross-sequence orchestration is manual.
- **Cost M**: 2-3 orchestration tools in `aevum-mcp` (enumerate sequences, dispatch to the queue, report progress), with `queue.rs` promoted to hold multiple sequences.
- **Fit**: very high - the MCP control plane is this product's core differentiator; no competitor has any programmatic interface at all.
- **Risk**: low-medium. Failure policy under unattended runs (bad frames, disk full) must be readable from the tool's return payload.
- **Success criterion**: one MCP call renders a directory containing 3 sequences end to end; with one corrupted sequence injected, the response reports "2 succeeded, 1 failed" plus the failure reason.

### F7 Hyperlapse large-baseline path stabilization (L) - P2

- **Whose problem**: hyperlapse authors spend 20-40 minutes per 200 frames patching tracking points. The local alignment in `align.rs` is a "small displacement" design; large baselines need feature tracking, path smoothing, and auto-crop.
- **Risk**: high - deep algorithmic uncertainty; Warp Stabilizer represents a decade of iteration. A botched version is worse than none. Watchlist.

### F8 AI masking (SAM-class interactive segmentation) (L) - P2

- **Whose problem**: darktable 5.6 already ships SAM2.1 masking as an optional AI subsystem; Lightroom has Subject / Sky masks. Current masks (luminance / color range) cannot target semantic objects like "buildings against the sky".
- **Risk**: an architecture decision, not a feature decision - bringing in ONNX Runtime and model downloads breaks the current "no external inference dependency in the executable" discipline (darktable's pattern: off by default, opt-in, CPU fallback on GPU failure). Watchlist.

### F9 Platform delivery presets (S) - P1

- **Whose problem**: Douyin / Bilibili / Channels each carry their own resolution-bitrate-frame-rate conventions; Chinese tutorials recite "4K 25fps at 50 Mbps minimum" style rules. Add a preset group plus a filename template to the export panel.
- **Cost S** (preset table in `export.rs` + UI); **risk**: low (platform specs drift, so presets must stay editable).
- **Success criterion**: choosing the "vertical short-video" preset produces a file whose size and bitrate match the preset table item by item.

### F10 X-Trans sensor coverage (L) - P2

- **Whose problem**: Fujifilm timelapse shooters currently finish in Capture One or Lightroom. rawler can decode X-Trans, but the current demosaic (orientation criterion plus chroma constancy) is Bayer-specific; the 45-degree bound analysis behind ledger item B4 would have to be redone for the 3x3 CFA.
- **Risk**: high (algorithm rework, and the B4 analysis framework rebuilt). Watchlist; revisit if Fujifilm demand grows.

## 4. Tiering and Recommendation

| Tier | Items | One-line rationale |
|---|---|---|
| **P0 (next release)** | F1 culling bench, F3 timestamps, F2 astro stacking | Two S items cut through the daily needs of the Chinese long-timelapse niche; one M item uses existing infrastructure to take the last two-hop detour |
| **P1 (release after)** | F4 chroma deflicker, F5 Holy Grail pre-alignment, F6 MCP batch orchestration, F9 platform presets | All extensions of existing pipelines, no new dependencies |
| **P2 (watchlist)** | F7 hyperlapse, F8 AI masking, F10 X-Trans | Each carries an unresolved "architecture / algorithm direction" decision |

### Why the Top 3

1. **F1 culling bench**: smallest cost, sharpest pain, highest reuse (metrics already plotted, ratings already stored). It is the **first step** of the long-timelapse workflow - own the entry point.
2. **F2 astro stacking**: the only candidate with a "we deleted two pieces of software" story. StarStaX and Sequator are stalled freebies; this audience will feel "one window from RAW to finished film" immediately.
3. **F3 timestamps**: S cost that unlocks B-end money (engineering timelapse delivery is a paid scenario), while LRTimelapse keeps it behind the Pro paywall - we give it away free, and that is the differentiator.

### Why Not the Others

- **F4 / F5 (deflicker extensions)**: important but "quality deepening"; users can muddle through today (repeated passes, manual keyframes). The P0 three are "cannot muddle through at all" items.
- **F6 (MCP batch)**: high value, but it depends on F1's culling semantics being settled first (unattended culling rules should not exist before the culling bench itself) - a sequencing dependency.
- **F9 (platform presets)**: too cheap to spend a P0 slot on; it hitches onto whichever release has room.
- **F7 / F8 / F10**: each bets on an L-level gamble (tracking algorithms / AI architecture / demosaic rework). With two S items and one M already filling the next release, they neither fit nor should they.
- **Not doing** (settled in the ledger, not reopening): 16-bit HDR TIFF/PNG; adding "Lightroom round-trip compatibility" - that would reintroduce the root cause of the two-hop workflow, opposite to this product's positioning.

## 5. Decisions Needed

1. **F2 scheduling**: P0 is 2x S + 1x M. If the next release only fits two S items, which of F2 and F3 gives way? (My call: keep F2 - it carries the "one window" narrative; F3 can slip into any release.)
2. **F5 product scope**: only the "align to EXIF first" switch, or also an LRT-style Holy Grail wizard UI? My call: the switch only (the wizard UI is LRT's baggage, not an asset).
3. **F8 architecture direction**: do we open an "optional AI subsystem" door for AI features (model downloads, GPU runtimes, off by default)? This decides the landing spot not only for masking but for every future AI feature.
