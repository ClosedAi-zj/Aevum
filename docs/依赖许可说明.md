# 依赖许可说明（M2 增量）

**中文** · [English](依赖许可说明.en.md)

本文档记录 M2 引入的第三方解码依赖的许可与分发口径，供打包（`scripts/package.sh` / zip 直发）
与合规留档使用。仓库既有依赖的许可沿用各 crate 声明，不在本文重复；
面向用户的完整清单在仓库根目录 `THIRD-PARTY-NOTICES.txt`。

> **2026-10-31 订正**：本文原先把 rawler 的许可写成「MIT OR Apache-2.0（双许可）」，
> 并据此得出「二进制分发零附加义务」。**这是错的。** rawler 是 **LGPL-2.1 单一许可**，
> 且以静态方式链接进发货二进制。凡依据旧表述做过的判断都需要重新评估；
> 下面按实测重写，并在末尾说明当时为什么会写错（避免同类错误再犯）。

## rawler

| 项 | 内容 |
|---|---|
| 引入版本 | 0.8.0（锁定于 `Cargo.lock`；要求 rustc 1.89，本仓 MSRV 随之上抬到 1.89）。**0.7.2 有已知缺陷**：iPhone 的 LinearRaw DNG 上读越界 panic，且 panic 在它自己的 rayon 工作线程里被吞掉，主流程仍返回 Ok → 静默脏数据。见 `docs/RAW兼容性-根因与防线.md` |
| 用途 | RAW 传感器直解后端：补齐 CR3-CRX、CR2、NEF、ARW 及 12/14 位行内打包 formats |
| **许可** | **LGPL-2.1**（GNU Lesser General Public License 2.1，**单一许可**，非双许可） |
| 许可依据 | crate 内 `LICENSE` 文件即 LGPL-2.1 全文（503 行）；`cargo metadata` 的 `license` 字段为 `LGPL-2.1` |
| 代码来源 | <https://github.com/dnglab/dnglab>（crates.io 发布名 `rawler`），作者 Daniel Vogelbacher、Pedro Côrte-Real |
| 是否修改 | **否**，使用 crates.io 原样源码，未打补丁。`Cargo.lock` 校验和：`sha256:04f4cc35c23969a4a834e0b117c7da41ace812eb9053b5effc3fc5c77d114677` |
| 接入方式 | `crates/aevum-core` 的 optional 依赖，feature 名 `raw-rawler`（`default = ["raw-rawler"]`，**默认开启**） |
| 链接形态 | **静态链接**进 `aevum.exe`（可用 `strings -a aevum.exe \| grep rawler-0.8.0` 自证） |

### 合规要点（LGPL-2.1 §6，静态链接场景）

因为 aevum.exe 静态包含该库，它属于 §6 所称 "a work that uses the Library"，
不是"独立进程聚合"，因此**不能**按宽松许可那样零义务直发。四项义务与本仓的做法：

| 义务 | 做法 | 落点 |
|---|---|---|
| 声明使用了该库、且该库受 LGPL 保护 | 写入随包通知与发布说明 | `THIRD-PARTY-NOTICES.txt` 第 2 节 |
| 附许可全文 | 随包分发许可原文 | `licenses/LGPL-2.1-rawler.txt` |
| 提供对应源码 | 随包附 Cargo 源码包（730 KB，解压即全部源码）+ 官方下载地址与校验和 | zip 内 `third-party-src/rawler-0.8.0.crate` |
| 允许修改并重新链接 | 文档给出 `[patch.crates-io]` / `cargo vendor` 两条具体做法，均不需改动项目代码；如需 object 文件形式则向发布者索取 | `THIRD-PARTY-NOTICES.txt` 第 2 节 |

**仍然存在的一处不足，如实记录**：Rust 静态链接没有"用户替换 DLL"这种现成手段，
要真正替换必须自行重建整个 exe。这在 LGPL 实务上属于可接受的"提供重建手段"，
但比动态链接方案弱。若将来收到明确要求，升级路径是把 rawler 包成 `cdylib`
随包放 DLL（工程量：C ABI 边界 + Windows 加载路径 + 失败降级），本版不做。

### 想彻底不含 copyleft 的构建方式

```bash
cargo build --release --no-default-features
```

`raw-rawler` 是唯一受影响的 feature，关掉后 RAW 解码全部走内置后端
（行为与 v0.3.0 一致），二进制不再含任何 LGPL/GPL 代码。代价是 CR3-CRX、
12/14 位行内打包等格式解不动（会明确报不支持，不静默出错）。
**这条路径必须长期可用**——它是给"不允许链接 LGPL"的下游留的出口，
任何把 rawler 变成非可选依赖的改动都是在拆这条出口。

### 顺带澄清一处旧表述

原文写「纯 Rust 实现，不引入 libraw（LGPL-2.1/CDDL）的打包负担」——这句的对比是错的：
rawler 自己的许可也是 LGPL-2.1。真正的区别不在许可，而在**实现形态**：
rawler 是纯 Rust（无 C 工具链、无动态库、无 vendored C 源），构建与分发更简单；
但 copyleft 义务与 libraw 同级。当初写成 MIT/Apache，多半是照抄了 crates.io 页面
上更早版本的元数据、或与 `kamadak-exif` 一类的传递依赖混淆了。
**教训：许可字段必须从 crate 内的 LICENSE 文件与 `cargo metadata` 双向核对，
不能只看 crate 页面摘要或凭印象。**

### 离线构建与 vendoring

- 默认 feature 开启；离线或需要回退 v0.3.0 行为时用
  `cargo build --no-default-features`（行为与内置后端逐位一致）。
- 分发前在 CI 侧执行 `cargo vendor vendor/` 并提交 `.cargo/config.toml`，
  之后 CI/打包用 `cargo build --offline` 验证一次。本机若已有热缓存
  （`CARGO_HOME` 指向的 registry），vendor 一次即可锁定全部传递依赖。
- rawler 的传递依赖（kamadak-exif、num_enum、rayon、thiserror、backtrace 等）
  均随 vendor 一并锁定，许可以 vendor 目录内各 crate 的 `LICENSE` 为准。
  实测这些传递依赖均为宽松许可（MIT / Apache-2.0 类），**不引入新的 copyleft**；
  但每次升级 rawler 大版本都应重跑一次核对，别假设不变。
