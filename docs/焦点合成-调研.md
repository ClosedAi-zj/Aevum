## 1. Helicon Focus 8 逆向结论

目标：`D:\app\Helicon Focus 8\_HeliconFocus.exe`（22.7 MB，PE x86_64，Qt 程序，
sha256 `b7e4d68f…f58eca`）。证据分级按 ps-lr clean-room 规约：E1 = 反编译，
E2 = 结构体/参数元数据，E3 = 名称/文档。

RE 链路：REA 6.8.0 + Ghidra 12.1.4（为本次调研新装到 `E:/code/ps-lr/.tools/`，
12.2 被 REA 版本门槛拒绝）。exe 无保留符号，深层反编译性价比低；
本次以字符串证据 + 内嵌 OpenCL 元数据 + 官方帮助文档为主，已足够定算法口径。

### 1.1 方法分类（E2/E3，铁证）

| 官方名 | 内部设置键 | 算法族 |
|---|---|---|
| Method A (weighted average) | `FocusParameters.Method_A` | 加权平均 |
| Method B (depth map) | `FocusParameters.Method_B`（另有 `Method_B_(legacy)`） | 深度图 |
| Method C (pyramid) | `FocusParameters.Method_C` | 金字塔 |

### 1.2 GPU 管线（E2，内嵌 OpenCL 元数据）

exe 内嵌 **AMD GFX8 预编译内核**（Code Object V3，clang 3.9 构建），内核符号名全集
（`__OpenCL_*_kernel`）直接暴露管线结构：

- **加权平均**：`convert_rgb_to_gray16`（灰度 16bit 测度）→ `stack_first_pass` /
  `stack_second_pass` / `stack_weighted_average` / `get_results_weighted_average`
  （两趟 + 权重平均）→ `calc_difference` / `calculate_difference_batch`
- **金字塔**：`fast_downsize_by2`（逐级减半）→ `horizontal_blur` / `vertical_blur`
  （可分离模糊，另有 weighted 变体）→ `collapse_pyramid_{1x16,3x16,4x32}`（三种块宽的塌缩）→
  `pyramid_stacking_combine` → `apply_feathering`（羽化表）
- **深度图**：`calc_differencial_layers` / `draw_differencial_image` / `ApplyDeformations`
- **公共**：`get_histogram`、`calculate_total_brightness`、`extract_channel`、`FillMarginsWithPureBlack`

### 1.3 对齐子系统（E2，内核参数反射元数据）

对齐内核参数表漏出（连续字段名串）：

- **网格形变对齐**：`canvas/canvas_info`、`detectrect`、`npoints_x/npoints_y`（网格点数）、
  `stepx/stepy`（网格步长）、`varations`（每点候选形变数）、`deform_number`、
  `results/sum_cache`（评分缓存）
- **测度**：`histogram_size`、`global_histogram`、`local_histogram`（对齐评分用**直方图**，
  全局+局部）、`brightness_factor_1024`
- **金字塔参数**：`number_of_layers`、`feather_table`（羽化查表）
- **形变内核**：`curve/curve_size`、`border_width`、`radius`、`f`、`k1`、`k1weights`
  （f/k1 疑为镜头畸变参数，未证实）

设置序列化键（E2）：`Radius`、`Smoothing`、`smoothing_gamma`、`smoothing_gamma_size`、
`opacity_filter`、`best_plane_info`、`pixel_sum(_info)`。

### 1.4 官方文档口径（E3，`Help/english/HeliconFocus.html`）

- Method A：加权平均，参数 **Radius**（围绕每像素的分析半径）；平滑、低噪声场景优先
- Method B：深度图，参数 **Radius** + **Hardness**（过渡硬度）+ smoothing；
  「the analysed area around each pixel」判定焦点归属
- Method C：金字塔，对比度最强处胜出，细节最好、噪声/色彩偏移风险最高
- 对齐插值设置：「Interpolation is used to preserve details during alignment process.
  The slower, the better」

### 1.5 未证实项（诚实边界）

- 权重公式的精确形状（A 的高斯窗参数、B 的 hardness 映射）——需 E1 反编译才能定，
  本次未做（exe 剥符号，投入产出比低；实现时也不许抄，只许独立重写）
- `f/k1` 是否为畸变校正——未证实
- 深度图平滑核的精确尺寸——文档只有「smoothing of the depth map」

## 2. 开源方案对比

| 方案 | 许可证 | 算法 | 对齐 | 效果 | 性能 |
|---|---|---|---|---|---|
| **focus-stack**（PetteriAimonen） | **MIT** | Forster 复小波 DWT 融合（扩展景深经典论文）；输出可选深度图 PNG | OpenCV `findTransformECC`（邻居链式对齐，≤2048px 预对齐） | 批处理一致性滤波（consistency 0–2）；深度图 threshold/smooth-xy/smooth-z/halo-radius 可调 | OpenCL 可选；批式合成（batchsize 8），~100 MB RAM/百万像素 |
| **enfuse**（Enblend 家族） | **GPL-2.0+** | Mertens-Kautz-Van Reeth 曝光融合 + Burt-Adelson 拉普拉斯金字塔多带混合；对比度测度用**局部标准差**（文档明确说比论文建议的 Laplacian 对散焦图更好） | **无**（依赖外部 align_image_stack） | 加权准则（曝光/饱和/对比/熵）灵活但对焦点合成不专精；`--hard-mask` 专为焦点栈 | 金字塔层数可调，内存大 |
| **Zerene Stacker** | 闭源（商业） | PMax（金字塔最大对比度）/ DMap（深度图 + 对比度阈值滑杆 + Estimation/Smoothing Radius） | 内建（含视差校正） | 业界标杆；PMax 毛发类复杂几何强但易反转光晕/提噪/偏色，DMap 保色彩平滑但复杂几何弱 | 专有 |
| ppsp 等管线 | 各异 | align + enfuse 封装 | align_image_stack | 组合式 | — |

**社区共识（photomacrography 等长帖，Rik Littlefield 本人参与）**：

1. 金字塔类（PMax/Helicon C）对**复杂重叠几何**（毛发、刚毛交叉）最强，
   但有「反转光晕」（亮主体周围暗圈）与提噪、偏色倾向——这是金字塔分解的信息泄漏固有属性；
2. 深度图类（DMap/Helicon B）**保色彩保平滑**最好，但对无细节平坦区需要对比度阈值
   把「垃圾」判黑，否则平坦区出斑块；复杂重叠几何偏弱；
3. 顶级成片流程是「两种方法各渲一遍 + 人工润色取长」；
4. 无细节区域（表盘、天空）是所有测度驱动方法的共同死穴——测度只在有纹理处有意义。

## 3. 选型建议（已确认）

### 3.1 算法选型：**深度图法为主，加权平均为快档，金字塔暂缓**

| 优先级 | 方法 | 对标 | 理由 |
|---|---|---|---|
| **P0 深度图** | 每像素焦点测度 → argmax 得深度图 → 阈值剔除无细节区 → xy/z 双向平滑 → 按图选源帧 + 羽化过渡 | Helicon B / Zerene DMap | 质量上限最接近商业标杆；保色彩（不做金字塔重构，无色彩/对比度漂移）；**可测试性最好**（深度图是中间产物，可直接断言）；与恒晷现有「素材帧兜底」的思路同构 |
| **P1 加权平均** | 灰度 16bit 测度 → 跨帧归一化权重 → 直接加权 | Helicon A | 实现最简单；低噪栈质量好；作为快档与深度图互验 |
| P2 金字塔 | 拉普拉斯金字塔逐级选最大对比度 | Helicon C / PMax | 复杂几何最强但有反转光晕与色彩漂移，测试金标难定；等 P0/P1 稳了再加 |

关键算法决策（对标 Helicon 证据独立设计）：

- **测度**：modified Laplacian（|2I−I(x−1)−I(x+1)|+|2I−I(y−1)−I(y+1)|）或 Tenengrad（Sobel²），
  在 16bit 灰度上算，半径可调（对应 Helicon Radius）；测度图做高斯预平滑抑制噪点
- **无细节区兜底**：测度峰值低于阈值 → 该像素区域整体取「基准帧」（默认序列中位帧或用户指定），
  直接消灭 DMap 的斑块问题——这与恒晷去鬼影的「素材帧兜底」是同一个思想
- **深度图平滑**：xy 向高斯（半径可调，对应 smoothing）+ z 向（帧号向）中值滤波去跳变；
  过渡带按深度差羽化（对应 Hardness：羽化带宽度与相邻深度差成反比）
- **光晕抑制**：深度图形态学开运算去掉孤立深度点（对应 halo-radius）

### 3.2 对齐选型：**复用恒晷现有对齐 + 网格形变升级路径**

- 焦点栈的对齐需求与时间合成同源（帧间平移/呼吸），恒晷已有帧对齐管线（`warp::transform_into`），
  先直接复用；
- Helicon 用的是**网格形变**（npoints 网格 + 每点候选形变 + 直方图评分），
  对焦移导致的放大率变化（focus breathing）远比全局仿射准——列为 P1 升级项：
  在现有 warp 基础上加网格 mesh warp，评分用块直方图差。

### 3.3 处理流程（对接现有管线）

```
MergeKind::Focus（新）→ run_merge_job 解码循环（复用，全分辨率 + RAW）
  → 对齐（复用 warp 管线，网格形变 P1）
  → 焦点测度（16bit 灰度，逐帧）
  → 深度图（argmax + 阈值 + 平滑 + 羽化）← 中间产物可存盘/可测试
  → 按图混合（P0 选源帧羽化 / P1 加权）
  → 写盘（与现有 write_single_still 同编码：不做传输变换）
预览：复用 B8 半分辨率缓存模式（帧选择不变只重算混合），面板即时刷新
```

参数（对照 Helicon 开口，走 serde default 零破坏）：`focus_radius`（测度半径）、
`focus_threshold`（无细节阈值，0=关）、`focus_smooth_xy`、`focus_smooth_z`、
`focus_feather`（过渡硬度反向）、`focus_method`（depthmap|weighted）。
MCP 命令 `focus.merge` 入目录（第 77 条，四处同步照旧）。

### 3.4 性能考量

- 测度与混合都是逐像素独立运算，天然可分块流式（对齐才是全帧驻留的瓶颈）——
  与 timeblend 同构，内存可控
- 深度图是 8bit/16bit 单通道小产物，预览可在 1/4 分辨率测度上做，再上采样成图
- GPU（OpenCL）暂不做：Helicon 用它是因为商业产品要秒级出图；恒晷先保证 CPU 路径
  数值正确 + 可金标回归，GPU 列为后续加速项
- 深栈（>100 帧）分批合成：相邻批各出深度图再融合，参考 focus-stack batchsize 思路

### 3.5 许可证与 clean-room 约束

- focus-stack 是 **MIT**（思想可参考，代码不拷——本项目铁律本就不拷任何外部代码）
- enfuse 是 **GPL-2.0+**：只参考公开文档描述的思想，**不读其源码**，避免 GPL 传染
- Helicon 证据全部按 ps-lr 规约只记事实（结构/字段/顺序/常量），实现独立重写

## 4. 验收口径（草案，实现前确认）

1. 深度图判据：三帧合成（前/中/后景各一测试纹理），断言深度图把每个区域正确归给持有
   清晰纹理的帧；**负向验证**：测度全平时深度图必须退化为基准帧
2. 无细节区判据：平坦渐变背景不出斑块（测度兜底生效）
3. 羽化判据：过渡带亮度单调、无台阶（对应「±5% 深度误差接缝无台阶」）
4. 加权平均判据：两帧只有一处纹理差异，权重应集中于清晰帧，输出与清晰帧该区域逐点一致
5. 端到端：与现有 merge 判据同构（真实小序列导出 + 像素级断言）

## 5. 实现记录（2026-11-02 落地）

按 §3 的 P0 方案实现，提交三个：`21a3924`（core 算法）、`8bc61dc`（merge 管线与第 77 条命令）、
`cfb3488`（面板与端到端判据）。

**与调研稿的差异（实现时定的口径）**：

- `smooth_z` 落地为**深度图模值滤波半径**（去孤立深度点），`feather` 落地为**选中掩膜的高斯羽化半径**。
  调研稿里写的「xy/z 双向平滑」概念上就是这两件事：一个去斑、一个过渡。
- `threshold` 用**全图最佳测度的分位数**（0–100）表达，不用绝对阈值——跨序列可迁移，
  这正是 DMap 那根对比度滑杆的口径；0 = 关闭兜底。
- 参考帧取**序列中位帧**（`count / 2`），与时间合成的参考帧口径一致。
- 测度在 γ2.0 亮度（linear 的平方根）上算：散焦是镜头的空间属性，但测度该反映感知对比，
  线性亮度会把暗部纹理压得不成比例。
- 金字塔法（P2）按建议暂缓；GPU（OpenCL）也没做，先保 CPU 数值正确 + 金标回归。

**判据清单**（核心 5 条 + 端到端 1 条，全部含负向验证）：

| 判据 | 验的是什么 | 负向验证 |
|---|---|---|
| `the_depth_map_assigns_each_region_to_the_frame_holding_the_sharp_texture` | 三帧各管 1/3 的分区归属 | 全失焦后输出必须仍是糊的（变不出清晰度） |
| `a_featureless_field_falls_back_to_the_reference_frame` | 平坦区兜底到参考帧 | 关掉兜底时平坦区必须跟随噪声 argmax |
| `feathering_blends_across_depth_jumps_without_a_step` | 跨界样本落在两帧之间 | 远离边界处羽化不该改变取值（逐点等于硬切） |
| `weighted_average_concentrates_weight_on_the_sharp_frame` | 纹理区≈清晰帧；全平区退回参考帧 | 纹理区不许是两帧的糊平均值 |
| `degenerate_inputs_are_handled` | 空/零尺寸/尺寸不齐/单帧/参数边界 | —— |
| `focus_merge_takes_each_band_from_the_frame_that_holds_the_texture`（UI 端到端） | 真实序列导出后逐带取对帧 | 兜底开 100 分位 → 整幅退回参考帧；未知方法与缺 confirm 起任务前被拒 |

**已知边界**：分区边界那一两行归属受测度窗口串扰（`radius + smooth_z` 内），
这是方法的属性不是缺陷；32 帧上限按全部帧驻留内存算，更深的栈要分段合成。

### 1.4.0 发版前的一轮修正（2026-11-02 审计）

调研稿的口径整体成立，落地之后有三处需要就地更正：

1. **`focus.merge` 的取帧参数是 `start` 不是 `center`**。契约表当初写的是 `center?+around?`
   「当前帧±7」，实现从头就是「起始帧起 8 帧」——按 schema 传 `center` 从来没生效过。
   1.4.0 把契约改成 `start?+around?`，实现不动。调研稿 §3 里那句「当前帧前后各取」同样
   按 `start` 读。
2. **内存口径按实测改正**：原文按「32 帧 24MP ≈ 2.3 GB」估，实测约 **9.6 GB**（估算式
   `帧数 × 像素数 × 12 B + 输出三个面`）。M1 那轮把归属图改成边算边比之后，峰值降下来
   一个量级，但「32 帧」这条上限是按**全部帧驻留**算的，没有放宽。
3. **无头控制面补齐**：`aevum_focus_merge` 是第 35 个直连工具，接的就是 `focus.merge`。
   无头会话没有「当前帧」，省略 `start` 时从序列中位帧起取 8 帧。

**本轮未实现**（照旧挂着）：金字塔融合法（§3 的 P2）与 GPU（OpenCL）加速；面板也还
没有深度图预览——`depth_map` 这个入口已经在，判据在用它，界面上看不到逐像素归属。


### T10 实测：金字塔 vs 加权（2026-11-03）

底座那一版把「2–3×」「≈1.0 GB」当量级说明写在 `pyramid.rs` 的模块头里，并标明「权威数字
由 T10 实测替换」。T10 就是这一节：**两个数都是推算，且都错了**，如实写实测。

**测量方法**（别人照着能做出来）：

- 素材：`samples/cameras/` 的四张真实 PANA 6000×4000 样张（`PANA0001.RW2` /
  `PANA0450.RW2` / `PANA1631.RW2` / `PANA0198.JPG`），循环取满 **8 帧**。帧数影响内存与
  耗时，**内容不影响这两个数**——合成是逐像素运算，像素数定了，开销就定了。
- 构建：`cargo build --release`，`opt-level = 3`。
- 机器：i5-12600KF（16 逻辑核）/ 31.8 GB RAM / Windows 10.0.26200 / rustc 1.98.0。
- 峰值内存：进程自己的 `PeakWorkingSetSize`（`GetProcessMemoryInfo`）。
  **一个方法一个进程**——峰值是进程级单调量，同一个进程跑两个方法，第二个会背着第一个的
  高水位，测出来的数没有意义。
- 墙钟：只包住融合调用本身（`focus::focus_stack` / `pyramid::fuse_pyramid`），不含解码。
- 每个方法 **3 次取中位数**，6 次跑完两列的离散都在 1% 以内。
- 输入 8 帧本身驻留 **2.32 GB**（8 × 288 MB + 解码器余量），所以除了「进程峰值」还给一列
  「融合增量」= 峰值 − 融合开始前的常驻，那才是方法自己的开销。

| 方法 | 墙钟 | 进程峰值 | 融合增量 | 层数 |
|---|---|---|---|---|
| Weighted | **1.95 s** | 2.88 GB | 732 MB | — |
| Pyramid（优化前） | **29.7 s** | 4.43 GB | **2.10 GB** | 6（`levels = auto`） |
| Pyramid（优化后） | **24.4 s** | 4.43 GB | **2.10 GB** | 6（`levels = auto`） |
| 倍数（优化后 / Weighted） | **12.5×** | 1.54× | **2.9×** | — |

两轮实测的 Weighted 基线有抖动（优化前那轮 1.97 s / 3.19 GB / 864 MB，优化后同口径复测
1.95 s / 2.88 GB / 732 MB），倍数一律按**同轮**基线计。

24 MP 的 `levels = auto` = `clamp(floor(log2(4000/32)), 3, 8)` = **6**。

**推算错在哪**：

1. **内存差 2 倍多**。原式只算「输出塔 384 MB + 权重塔 128 MB ≈ 1.0 GB（含输出缓冲）」，
   漏了 Pass A 的 `best` / `gate` 两个全分辨率单通道面（各 96 MB）、掩膜塔（128 MB）、
   每帧的测度面（96 MB）与当前帧的拉普拉斯面（288 MB）。把这些加回来就是 2.1 GB 量级。
2. **耗时不是 2–3×，是 12–15×**。当时归因于 `focus::measure_plane` 每帧跑**两遍**
   （Pass A 求分位线、Pass B 算权重）——这个归因**被随后的优化证伪了一半**：见下。

**优化了一轮（2026-11-03，在判据兜底下做的）**：

1. `focus::measure_peak`：逐帧每层只算一遍改进拉普拉斯、逐像素取最大后盒平均；Pass A
   的分位线改由子采样峰值估计。`t = 0` 时与旧路径逐像素严格等价（第四轮回归实测
   128×128 夹具 49152/49152 像素 max|Δ| = 0）；`t > 0` 时**不再等价**——`box(max ml)`
   与 `max(box ml)` 不可交换，分位线也取自不同分布：纹理尺度与盒窗（radius = 2）可比
   时差异可观（块状纹理夹具 threshold = 25 实测 65% 像素不同、max|Δ| = 0.23），纹理
   细于窗宽时趋近零。金字塔判据 P-C1…P-C6 锚的是新路径自身行为；`measure_peak` 的
   盒平均窗口语义目前**没有判据锚**（把半径变异为 0 后六判据仍全绿），已开进台账。
2. `reduce` 重写为可分离行流式 + 环形缓冲，消掉每输出像素两次 `collect()` 堆分配。
3. Pass B 权重面 `.clone()` 改 `Cow::Borrowed`，省掉每帧每层一次 128 MB 纯拷贝。

结果：**29.7 s → 24.4 s（−18%），峰值内存与融合增量纹丝不动**。两个教训：其一，把测度
从两遍压到一遍只省 18%，说明 15× 的大头根本不是测度计算，而是塔本身的逐层下采样/上采样
/展开与逐像素混合的内存带宽工作；其二，Cow 省的是拷贝期的瞬时分配，没碰到 `best` / `gate`
全分辨率面与掩膜塔的驻留基线，所以峰值不降。再往下压要动算法结构（减层数、块处理、
多线程），不在这轮范围。QA 独立复测（探针开 `lto = thin` + `cgu = 1`）得 28.6 s →
26.4 s（−7.8%），峰值与增量逐 MB 不变——方向一致，绝对值随机器与构建配置抖动（±20% 内），
结论以**同轮**倍数（12.2–12.5×）为准。

**多线程一轮（2026-11-03，同日第三轮）**：

策略是「只改谁算哪块，不改任何浮点运算的结合顺序」——`std::thread::scope` 按行带切分
（新私有模块 `par.rs`，零新依赖），把**同层内逐像素独立**的运算全部并行：

1. 测度链：γ2.0 亮度、改进拉普拉斯、盒平均的**输出趟**（积分图构建是行间串行归约，
   保持原样）、`measure_peak` 的跨帧取最大（帧循环串行，帧内三趟按行带并行）；
2. 塔操作：`reduce`（按输出行带切，每带自带 5 行环形缓冲，只在带界上重复算一两行
   横向卷积——同一行两次算出的值逐位相同，只是重复劳动）、`accumulate_upsample`、
   `laplacian_from_gaussian`（**逐像素融合**上采样与减法，不再先写一张 288 MB 全分辨率
   `up` 中间面再整面读回相减）、`accumulate_level`（输出塔 + 权重和塔两份互斥行带）、
   Pass B 的权重四次方。
3. 保持串行不动的：帧循环（out_tower 的 f32 累加顺序）、积分图构建、直方图分位、
   塌缩的层间顺序。每个输出像素的浮点加法序列与串行版逐一相同。

**逐位不变判据**：默认阈值 `t = 0` 下，探针 `T10_DUMP` 改前改后各 288 MB 输出逐字节
`cmp` 相同；Weighted 的校验和（4413.644521）改前改后一致；另有阶段性校验和差分
（reduce 两层 / 拉普拉斯 / 塌缩 / 两法融合全部逐位一致）钉住每一级。本轮没有引入
任何漂移——不是「漂移很小」，是**零**。

实测（同口径同机，3 次取中位）：

| 方法 | 墙钟 | 进程峰值 | 融合增量 |
|---|---|---|---|
| Weighted（本轮基线） | 2.285 s | 3.09 GB | 768 MB |
| Pyramid（改前，旧二进制复测） | 25.8 s | 4.43 GB | 2.10 GB |
| Pyramid（改后） | **5.97 s** | **4.14 GB** | **1.82 GB** |
| 倍数 | 11.3× → **4.56×** | 1.39× → **1.34×** | 2.9× → **2.7×** |

两点说明：其一，峰值内存**不升反降**（4.43 → 4.14 GB）——融合拉普拉斯省掉的那张
288 MB 中间面是驻留基线的一部分，并行没有新增任何常驻开销（每带环形缓冲合计
< 3 MB）；其二，优化后 Weighted 自己也从 2.285 s 降到 1.31 s——测度链并行它同样
受益，所以倍数按**同轮同态**（改前基线 11.3×、改后 4.56×）各自成对计算。耗时构成
也变了：单线程轮里「测度已不是主要项」，多线程轮后测度与塔操作同时被摊薄，剩余
5.97 s 里已没有单一的串行大头。`levels = 1` 的 P-C1 退化路径（`fuse_single_scale`）
一字未动。

**给用户看的结论**：24 MP × 8 帧，金字塔从「慢一个数量级、多吃一倍多内存」优化到
**约 4.6 倍墙钟、1.34 倍峰值**（多线程轮后），换来的是低频光晕的抑制。所以界面默认仍
是深度图法/加权；金字塔是「有光晕、且不想等太久」时的选项——这个取舍写进了面板的
hover 文案。

### 第三轮（同日）：测度链一遍化 + 三条滑杆悬崖 + 内存收口

性能与功耗审计（2026-11-03）指出多线程轮后的剩余大头：Pass A 与 Pass B 各跑一遍
测度链、每帧 288 MB 的 `Plane::from_rgb` 拷贝与逐帧 fresh 分配。本轮：

1. **测度链只算一遍**：Pass A 一趟同时产出峰值面（分位线）与每帧盒平均后的测度面
   缓存，Pass B 从缓存取、用完即释放；第 0 层 reduce/拉普拉斯直接借用交错 RGB 帧，
   省掉 288 MB/帧 拷贝；拉普拉斯面（384 MB）不再落盘——`fine − upsample(coarse)`
   逐像素现算直接累加（f32 减法两版都只舍入一次，逐位等价）；`gate`/`weak` 两趟
   合成一趟。`focus::measure_peak` 退出生产路径（保留为 D1b 判据的参照实现）。
2. **三条用户滑杆可达的悬崖**（24 MP×2 帧，UI 上限即可触发）：`feather = 64`
   9.87 s → **1.70 s**（行带并行 + 缓冲复用）；`smooth_z = 16` 的模值滤波
   36.4 s → **0.34 s**（按列增量直方图把 O(n·k²) 降到 O(n·k)，投票与 tie-break
   逐字保持，新增判据对照朴素实现）；加权/深度图的混合循环并入行带并行，
   Weighted 8 帧并行倍数 2.8× → **5.9×**。
3. **内存收口**（堆栈/HDR/对齐）：σ 截尾的逐像素 `collect` 提到循环外复用并并行；
   Mertens 的全帧权重面驻留改流式两趟；对齐的 luma 代理从「全量驻留」改链式
   （只留上一帧）。

实测（同机同口径，min-of-N，与多线程轮同基线 Weighted 0.95 s）：

| 项 | 改前 | 改后 |
|---|---|---|
| Pyramid 8 帧墙钟 | 5.60 s | **4.05 s**（−28%） |
| Pyramid 峰值 | 4.14 GB | **3.86 GB** |
| 进入多尺度固定开销（levels=2 − levels=1） | 4.11 s | **2.14 s**（−48%） |
| Weighted 8 帧并行倍数 | 2.8× | **5.9×** |
| 倍数（同轮） | 5.9× | **4.3×** |

**逐位不变**：Pyramid 288 MB 输出逐字节 `cmp` 相同；feather/smooth_z/加权混合的
输出面与深度图逐字节相同（含 3 帧 feather+smooth_z 组合与 HEAD 基线对照）；
`levels = 1` 的 P-C1 退化路径与所有金字塔契约判据全绿。没有引入任何漂移。
